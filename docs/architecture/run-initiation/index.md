# Run initiation

Two accepted behaviors from 2026-11-10 decide how runs start. **Run Now** first resumes the oldest Run Now run stopped by its time limit ([BR-017 AC7–12](../../requirements/yuhaul/br-017-manual-run-initiation.md)). **Backtest and Replay** can filter retained videos by YouTube published date, as UTC days with both ends included ([BR-027 AC8–13](../../requirements/yuhaul/br-027-historical-backtesting.md)). Example: run 30 stops at its 30-minute limit. The next Run Now returns run 30 marked `resumed` and continues from its checkpoint under its original rules. A Backtest over `2026-10-01`..`2026-10-31` evaluates only videos whose locally eligible published date falls on those days.

- [ADR-001 — Run Now Resumes the Oldest Time-Limit-Interrupted Manual Run](decisions/adr-001-run-now-resumes-time-limit-interrupted-manual-run.md) — explicit `interrupt_cause` and `initiated_by` run fields, not parsed diagnostic text. The admission runs under the production lock, and a press during an active run is refused with `409` instead of waiting. Unusable candidates fail closed. Startup recovery is unchanged.
- [ADR-002 — Backtest and Replay Select by Locally Eligible YouTube Published Date](decisions/adr-002-backtest-replay-published-date-range.md) — immutable range columns on the run row, validated before anything is created. Only an eligible (unexpired) local metadata row supplies the date, and filtering happens in Go with no provider call. Consequence: ranges over periods with expired metadata select little.
- [ADR-003 — Discard the Unusable Time-Limit Run in One Transaction Under the Production Lock](decisions/adr-003-discard-unusable-time-limit-run.md) — the user discards the run Run Now refuses as `resume_unavailable` ([BR-017 AC13–21](../../requirements/yuhaul/br-017-manual-run-initiation.md)). Eligibility uses Run Now's own selector and validator inside the discard transaction; the ADR-006 sweep, the `failed` write and the counter recompute commit together or not at all (not `retainThenFail`, which commits retention first). A short `initiationMu` in front of the production lock makes a discard and a press, or two discards, serialize. Escalated finding: startup still exits on such a run, so Discard is unreachable after a restart.
- [ADR-004 — Stop an Active Run and Hand Unfinished Work to the Deferred Queue](decisions/adr-004-stop-active-run-and-deferred-handoff.md) — [BR-035](../../requirements/yuhaul/br-035-stop-active-run.md), plus BR-017's AC17 (amended), AC11 startup rule and AC22.
  - A stop writes a durable `stop_requested_at` marker and cancels the run's context with `ErrRunStoppedByUser`; ADR-007's guard rules decide each addition.
  - The run settles on unwind, under the production lock, to the new status `stopped`, in one transaction with `handOffUnfinishedTx`. Discard uses the same handoff, so unfinished work goes to the deferred queue, eligible at once.
  - A `stopped` claim owner is reclaimable.
  - Startup settles marked rows and skips (logs) unusable time-limit Run Now rows.
  - Run reads carry `discardable`.
  - Migration 025 widens `run.status` through a guarded `writable_schema` step (spike first; rebuild fallback).
- [ADR-005 — Mark a Stuck Legacy Run as Ended](decisions/adr-005-mark-legacy-run-as-ended.md) — [BR-036](../../requirements/yuhaul/br-036-mark-legacy-run-as-ended.md). `POST /api/runs/{id}/end` changes only `status` (to `failed`) and the reason (closed `end_legacy_run` diagnostic) of a version-0 production run that is `running` or `interrupted`, has no run control and is not stopping. It takes Discard's locks (`initiationMu`, then `productionMu`). A lock-free precheck makes repeats always answer `run_ended`. No handoff, counters, `completed_at` or provider call. Startup classification already excludes the row, so it needs no change. Run reads carry `endable` and `executing`. Implemented 2026-11-11, review pending.
- [ADR-006 — Re-queue Stranded Videos](decisions/adr-006-requeue-stranded-videos.md) — [BR-037](../../requirements/yuhaul/br-037-requeue-stranded-videos.md) AC1–19, BR-035 AC14 and BR-032 AC1 (amended 2026-11-11). Not implemented.
  - **Prerequisite:** `GET /api/deferred` and the Deferred view become paged. Next and Previous use keyset cursors (`after_id`/`before_id`). Jumps use `page=n` or `page=last`. The response carries `total`, `queue_total`, `by_reason`, the page number, `total_pages` and exact positions. A server-side `reason` filter is added (reconciled 2026-11-11).
  - `GET /api/stranded-videos` previews; `POST /api/stranded-videos/requeue` confirms. The confirm takes Discard's locks, scans read-only (phase A), then inserts every `requeued_by_user` item in one short write transaction with a cheap recheck (phase B).
  - *Blocked* is computed from `ClaimPlaylistSend`'s own legacy-veto SQL, extracted into a shared predicate with a nullable target, plus held guards without success.
  - Runs claim in the existing created-at order, in batches of 500. They keep claiming while quota remains and never pass over an earlier-eligible item. **F3 decided 2026-11-11: variant K.** A non-quota provider failure suspends fetching but not claiming; BR-035 AC14 is unchanged. Variant S is kept in ARS-005 Appendix A only as a rejected alternative. **F4 does not apply:** version-0 runs 17 and 21 in `action_execution` have 0 open retry rows.
  - *Blocked* evaluates veto branch 3 as at send time (`assume_acted`). *Absent* comes from YouTube's raw response ids, and a returned but unparseable item is released unchanged (critic review, 2026-11-11).
  - A retried video's metadata is fetched through the shared quota admission before evaluation; it is never rejected on empty metadata.
  - A **re-queued** video that YouTube no longer returns gets the final outcome `unavailable_on_youtube`: no routing, its item is completed, and nothing processes it again. Other retried videos keep `failed`/`video_unavailable`.
  - Migration 026 adds the reason, two `(video_id, status)` indexes and `run.videos_unavailable`. It lands before any other migration and owns those indexes. A `writable_schema` step widens the two final-outcome CHECKs, skipping each table that is already widened. Rolling back the binary once the new outcome exists is unsafe.
- [ADR-007 — Final Outcomes Are Never Reprocessed](decisions/adr-007-final-outcomes-are-never-reprocessed.md) — [BR-039](../../requirements/yuhaul/br-039-final-outcomes-are-never-reprocessed.md). Revised after critic review (2026-11-12). Not implemented.
  - One classification (final = the four final outcomes; partly done; open) is applied in the claim transaction and in one production main-loop input filter, `RoutableByRun`. The filter also drops videos held by the queue or partly done under another run, which covers the resume case.
  - A claim of a final video closes its items with `closed_reason='final_outcome'` (migration 027). A run's own just-finalized video is acknowledged. A user retry gets `409 video_already_final` from a single transaction.
  - A partly done video sends only its missing additions under its original run's decisions. Routes come from a status-free `decisionAuthority` loader, and `DecisionRunID` passes through `loadActions` and `ClaimPlaylistSend`. The sends are shown as `continued_actions` and counted in the sending run's route statistics.
  - Handoffs exclude final videos.
  - Immutability triggers are in migration 028 (with a down file), shipped with or after the claim classification. Continuation ships in the same release or behind an interim hold. ARS-005 step 6 comes last.
  - Amends ADR-006 (Decision 10), ARS-003 and authorization ARS-001.
