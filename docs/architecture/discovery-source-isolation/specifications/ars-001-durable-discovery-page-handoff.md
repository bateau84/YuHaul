**Status:** proposed technical contract for accepted behavior; no implementation or runtime proof.

A committed uploads page leaves real video work that survives the source, process and run. In a mixed run, a video from B's first page can be processed even if B's third page fails. If the server crashes before loading that video's metadata, the originating run can recover it. If all sources fail and the run must end, a fresh receiving run can claim the same video through Deferred even if YouTube never lists that ID again. Re-polling B and processing that known video are separate obligations.

## Implements

- [Discovery source isolation ARD-001](../design/ard-001-isolate-uploads-source-failures.md).
- User decision, relayed in Loom answer `f190b26f-3e88-49b0-a1c2-5d62992c2479` to `d69a1aba-447b-4dc0-bbf8-517b913219e7`: in the narrow only-source restart case, complete with explicit incomplete coverage and hand off saved work without routing it in the origin. The specifier records the authoritative requirements separately.

## 1. Commit boundary and records

Use the existing SQLite writer and production lock. `DiscoverVideoTx` currently creates the native video and its original `run_video_outcome` together; production's selector and terminal/stop sweep can find this ownership without any route decision. Extend that boundary, not the API call, to accept a page. No SQLite transaction spans provider I/O.

| Fact | Exact meaning |
|---|---|
| `video.discovery_page_observation` | Integer boolean, default `0`, only `0` or `1`, immutable after creation. Emit `1` only for new native IDs admitted by the new page transaction. `0` is existing or unrelated producer behavior, not a claim about inputs. This identifies exactly which videos can be exposed before enrichment, even after Store A eviction or in a receiving run. Do not promote older videos/observations on a re-poll. |
| Existing native identity and origin | Uniqueness is the YouTube `video.video_id`; engine-local existence checks are advisory. Winner records the scanning run as `discovered_in_run_id`, original source/video attribution, discovery time, run-local `not_yet_evaluated` membership, a native fingerprint when the title is available, and one increment to channel discovery statistics. Imported fingerprint for that ID is not a native video and retains existing monotonic reference eligibility. |
| Listing metadata | Store A only: when a real listing title is available, keep it, the published date and other allowed listing values under existing expiry/write rules. Description and duration are `NULL` until reliably provided. If no title is available and the Store A title constraint prevents insertion, retain the video and membership without a Store A row or a fabricated fingerprint; the readiness step can create them from a usable detail. Never materialize an absent/invalid field as `""` or `0`. Valid empty description and valid zero duration from a decoded detail are non-null values. TTL applies equally to listing and enriched values. |
| `deferred_item.deferral_reason = discovery_processing_pending` | New registered reason for a real, released observation awaiting a later processing pass where there is no more specific existing reason. Not a phase, new outcome, source Errors entry, or `requeued_by_user`. `run_id` is the releasing origin run, `video_id` the existing native row, `status=pending`, `retry_run_id=NULL`, `retry_after=NULL`, `retry_count=0` on first creation. `created_at` is release time in existing queue timestamp format. If already retained, keep the original queue row, reason, age and receipt lineage; do not insert a sibling to restate a reason. |

The **obligation at page commit is durable original ownership, not premature queue eligibility**. A committed marked video is either (1) owned for processing by its originating unfinished run, (2) settled under existing outcome/retained-removal contracts, or (3) released to the existing real-video queue with a receivable row. Page commit creates (1), not a claimable queue item. This reuses ordinary mixed-run routing without adding a held-queue state or letting a sibling claim hide the video from `RoutableByRun`.

Take the writer before native admission and related read-check-write arbitration. Within one transaction persist all newly admitted page observations and, only for the last successfully traversed page, source completion and the cutoff as specified by ARD-001. Duplicate IDs within the page, on a repeated page, or already known from another run are no-op for video/metadata origin, fingerprint, discovery count and processing entitlement. They still count as observed for traversal, and do not invalidate valid end-of-scan completion. A replay of an uncertain commit reconciles from durable native identity and source records before another provider call; it never retries side effects by guessing. Rejected/rolled-back page work advances neither ownership nor cutoff.

When sealing scope, persist each source's input floor (latest completed coverage, else its frozen legacy floor or null) and the run's start cutoff. Use that same floor on every page and every compatible same-run rescan, beginning at page one. Reconsider a tie against modern coverage and deduplicate by native ID; preserve the old compatibility filter for the legacy floor. The run-start cutoff is no later than its first source request. Completion commits its cutoff only with the final page and published coverage is the maximum of completed cutoffs, never a regression if an older run resumes after a newer run. A refused or failed source, successful intermediate page, receiver action or metadata result does not move coverage. Fresh polling uses its newly selected still-eligible source scope, regardless of whether earlier video work has already been processed. Empty successful scans count as completion. A crash cannot turn an untraversed list into an empty success.

### Durable pass settlement

Reuse the run acquisition assessment and run/source relation. Before the first uploads request, in one writer transaction persist `scope_ready` and its full source inventory for the run. This is a fixed set of subscribed, resolved uploads sources from a successfully traversed enumeration, not inferred from attempts. No partial subscription pagination, channel batch refusal, or empty in-memory list is proof of a ready scope. For both scope and successful source completion, require accounted, structurally valid results: an explicit valid items array and a valid continuation when supplied, with all pages traversed. A malformed response must not become empty or terminal by default. A ready, genuinely empty scope is representable. Do not store uploads URLs, credentials, or page tokens. Key source rows by `(run_id, channel_id)`; initial `unsettled` is not evidence of an attempt. Record `has_committed_page` (integer boolean, initially `0`) on the existing source row in the same transaction as the first successfully committed page, even if it adds no new native rows. A terminal `complete` or `local_failure` row also proves an attempt. A source proven no longer eligible on supported recovery may settle `no_longer_eligible`, which is not success or local failure and does not erase `has_committed_page`; a partial list or transient resolution failure cannot prove changed eligibility. No new source is added to that already captured pass on resume.

The run assessment has a nullable pre-feature/unknown state and durable `scope_ready`, `mixed`, `complete`, `no_attempts`, `all_local_failed`, or `blocked` facts. `blocked` carries the registered run-wide reason and can be written before the scope is ready. Keep a separate nullable run dispatch-stop fact (`quota`, `authorization` or `accounting_or_integrity`), with safe typed detail and separately established primary quota/auth facts where present. This is the receiving ARS-005 §6 run-scoped veto, not a user control or a provider-global lock. It may be written before the acquisition scope exists or after acquisition settles without overwriting that settlement. On compatible recovery with no settled assessment, use the sealed scope, never poll a `complete` or `local_failure` source again in that run, and restart only still-eligible unsettled sources from page one after current authority and source-resolution checks. Do not use a persisted source ID as authorization to poll an ineligible source. Reconcile an existing stop or typed provider-quota attempt before any run-owned network path. A crash before scope commit permits rerunning enumeration; a crash after the last source settlement but before run settlement permits deriving the result without an extra uploads request. `current_phase`, in-memory loop position, and zero counts are not evidence of pass settlement.

Settle only when the stored scope is ready, no applicable acquisition-wide veto took precedence, and no scope row is unsettled. `all_local_failed` needs a nonempty attempted set, every attempted source locally failed, and zero completed. `no_longer_eligible` alone does not prove an attempt; with `has_committed_page=1` it proves an earlier attempt that did **not** settle as a local failure. For the approved restart case, the sealed scope has one source, it committed a page with saved observations, and current complete eligibility evidence proves it is now ineligible, with no completed scan, local failure or global stop. Select `eligibility_changed_no_coverage`, not `no_attempts` or `all_local_failed`. This branch does not assign lifecycle policy to other scope combinations. Both `eligibility_changed_no_coverage` and `all_local_failed` become durable run assessments only in their terminal transactions below. Before commit, recover from the sealed inventory; afterwards, the run never opens a new pass. Mixed coverage remains independently visible and still does not authorize routing before normal acquisition settlement.

## 2. Origin-run ownership and release

Use the existing single production lock, run snapshot, `withoutRetryVideos`, `RoutableByRun`, final classification and guarded executor. A future run cannot discover a known ID as its own work. A run may not route a marked observation until the acquisition path durably establishes a disposition allowing routing, and the readiness check in §3 succeeds. Resume at any phase must honor that disposition and existing queue ownership, not just `current_phase`.

| Condition | Transactional disposition and subsequent eligibility |
|---|---|
| Live origin, acquisition incomplete or genuine interruption | Original membership remains the owner; no pending item merely because the run crashed. Continue only through existing compatible startup/Run Now rules, keeping the original snapshot. Persist committed mixed/complete or all-local-failure assessment before moving to its next operation. Re-entry must honor a committed assessment without running a new discovery pass. Stop/Discard remains available only under its own authority. |
| Mixed/complete assessment | Route eligible ready native admissions from every observed successful page, including pages from an incomplete source. For a new observation whose required inputs cannot be used this run, atomically retain a Deferred row and an origin `deferred` outcome with actual operational reason (`metadata_unavailable`, or existing quota/rate/auth reason). Use `discovery_processing_pending` when no existing queue reason fits. The origin's committed `deferred` outcome excludes it from further origin processing, including resume after the queue row is claimed, completed or removed. Do not pass an empty filtered slice back through a fallback that reloads released inputs. |
| All-local failure | Under the existing initiation/production ownership and SQLite writer, recheck sealed scope and dispatch stop, run nonterminal ownership, and no accepted Stop marker/Discard winner. One transaction commits the assessment, creates or preserves one pending row for every newly observed unfinished unreleased video, writes safe summary/counters, and marks terminal `failed`. Leave those videos `not_yet_evaluated`, with no new route/action evidence, and preserve earlier settled retries. Do not call the generic runtime-error sweep for these observations. Failed transaction: no terminal status, new foreign eligibility or event; recover from the still-owned observations plus sealed scope. Lost commit result: read the committed state and reconcile, never publish a contradictory status. A committed Stop/Discard first wins; if terminal failure commits first, those controls apply only their existing refusal. |
| Only source becomes ineligible after a saved page | Do not re-poll the source, advance its floor, write a source Errors entry, or enrich, route or send for these observations in the origin. Recheck the sealed scope, prior page evidence, stored eligibility result, effective dispatch stop, nonterminal ownership and Stop/Discard under the same writer rules as all-local failure. One transaction publishes `completed`, `eligibility_changed_no_coverage`, terminal time/counters and a due `discovery_processing_pending` row for each otherwise eligible unfinished observation not already retained. Keep the original membership and `not_yet_evaluated` outcome; no fabricated deferral outcome, video/source failure or action. The next eligible fresh receiving run may claim the saved work regardless of current subscription or whether the provider repeats the ID. Before commit, original ownership holds; rollback creates no terminal result or foreign eligibility. After commit, recover by reading the terminal record, not repeating the handoff, polling or reopening the origin. Existing final, removed and separately retained work is not recreated. |
| Global quota/auth or terminal local failure | Use existing lifecycle and reason precedence, never all-local-failure derivation. Before publishing a terminal result, unfinished open discovery work not itself evaluated/failed must have a durable receiving row or existing retained owner; a real failed evaluation/integrity result still follows its existing retained-error path. In global quota/auth use the actual existing deferred reason, no raw error and no continued provider dispatch. Genuine interruption retains original ownership for unreleased work. |
| Confirmed Stop or Discard | Existing handoff takes precedence under the writer and its status/stop checks. Reuse pending rows, don't duplicate them or undo user removal. If either terminal transaction above wins first, do not stop, discard or reopen that terminal run. No new provider work is authorized by either disposition. |

For release, under the writer verify the originating or current receipt owner, no incompatible claim, and no final or user-removed work; do not manufacture work for a video already owned or settled. An already committed identical release is a no-op, preserving item ID and age. Unexpected missing/contradictory membership fails visibly instead of creating a substitute. Check ownership, origin status and stop request again inside finalization. Final status, counters and queue evidence are published only after the corresponding durable write. A later release must not rewrite an origin's already committed historical outcome.

Use set-based local writes and no provider calls for the all-local transaction. Do not publish `failed` between batches. A separately committed series of queue batches would require an additional durable admission fence to prevent partially released work from being taken before finalization. Prefer the single transaction unless the assembled active-run search/write checks demonstrate it cannot meet the applicable limits. Test terminal-failure writes with a realistic large acquired set, not just an empty or single-page set.

Neither the new completion path nor its assessment is a new run status. BR-002 AC7–9 still govern fresh eligible polling, mixed runs and all-local failures. Accepted Stop/Discard, genuine interruptions and global quota/auth/accounting outcomes retain their own precedence and behavior.

For first foreign claim of a released item, normal queue due checks, production admission and snapshot capture apply. A mixed-run release is due upon release, but only the existing production gate permits foreign admission. Both special terminal handoffs become due with their terminal commits. Use the same persisted `(receiving run, video)` fence in automatic enumeration, writer-side fresh claim (including direct/manual entry), and ordinary phase/recovery selection. A receiving membership with foreign native origin is not an ordinary native input even after clearing `retry_run_id`; original native ownership may proceed only if the origin did not release it and its committed assessment permits routing. Inspect membership without giving it dispatch authority: only an exact still-owned receipt restores receiving dispatch; a released/removed/completed item is not claimed again in that run. Do not use phase fallback, a timer, `MAX(id)` or retry counts to infer ownership. Keep FIFO `(created_at,id)` among eligible groups and existing capacity-specific settlement without dispatch.

## 3. Metadata contract before evaluation

- **Who checks:** New marked native admissions before exclusion/detection/routing, and marked **open** queue recipients after `ClaimDeferredGroupReceiptTx` and BR-039 classification. A `GetDisplayMetadata` success alone is not proof of readiness. Use the locally held, unexpired inputs required by the run snapshot and normal duplicate evaluation (title), including channel name, description and duration where an applicable rule can read them. IDs come from native evidence. Readiness checks include exclusion inputs. Using real empty/zero fields is allowed; substituting for missing data is not. An ID/channel-only exclusion may use the actual identity; no fabricated metadata is needed or permitted for a predicate. If an unfinished evaluation has a persisted prefix and its inputs must be reloaded, use the existing non-recording snapshot evaluation and persisted-prefix comparison from production-authority ARS-005 before appending to it. Missing inputs yield retention; contradiction uses the existing authority-failure path. Do not overwrite an audit or append with incompatible inputs. A completed, otherwise authorized decision does not need refetching only because a display field expired.
- **How to load:** Reuse the bound, quota-accounted BR-037 §6 read seam, up to 50 distinct IDs per call. Current locally usable IDs need no fetch. Upsert a valid detail in Store A through the existing TTL/index-aware writer even if the prior metadata row was evicted; do not infer success from an `UPDATE` affecting zero rows. For the new marked population the parser and refresh writers must keep field presence/validity: use `NULL` for missing/invalid route inputs, including duration parse failures; do not let another refresh writer silently substitute defaults. A successfully returned ID without usable required fields is `unusable`, never `absent`. Establish `absent` only from a complete, successful returned-ID response. No raw payload or extra snapshot is retained. If a row expires/disappears between preflight and evaluation, the per-predicate read backstop fails closed rather than invoking existing degraded-metadata fallback.
- **Origin vs receiver:** Apply receiving ARS-005 §6's typed admission/renewal/accounting precedence and run-scope veto at origin, receiver and later phases. Expiry or loss after preflight is a **per-video** readiness result, not a fatal phase exception: stop evaluation of that marked origin video, atomically defer it under §2 with `run_video_outcome.deferred_reason=metadata_unavailable` and queue `discovery_processing_pending`, and continue independently ready work where dispatch remains allowed. Compare any persisted unfinished decision/audit prefix against reloaded inputs before appending; a contradiction is authority failure, not ordinary expiry. An upload-list failure or first enrichment pass cannot finalize a video as unavailable. For a claimed group follow receiving ARS-005 §6: ready → normal execution; quota/auth/rate → exact deferred disposition and `AcknowledgeRetryDeferralReceiptTx`; failed/unusable or late expiry → release unchanged with `RequeueRetryReceiptTx`; established absence from a validated complete envelope → ordinary **non-`requeued_by_user`** retry-failure retention. Source handoff alone never qualifies for BR-037's final absence outcome. Validate the exact receipt again before any settlement or send; losing ownership cannot recreate or acknowledge the removed item.
- **Modes and safety:** BR-039 `final` closes or acknowledges existing ownership without executing, including a final disposition committed immediately before crash; `partly_done` follows its original decision for missing actions and is not hydrated/rerouted by this contract. The normal executor checks snapshot authority, exact-target success, dispatch scope and unresolved send guards. No claim or readiness flag is permission to send. Dry-run and Replay/Backtest make no fetch through this new seam and do not claim or mutate production work. This does not repeal BR-026 AC4's allowance for dry-run read calls elsewhere; Backtest retains BR-027's no-external-calls requirement. Keep corpus/date selection and the existing selected versus decision-bearing distinction. For a marked selected input that cannot be evaluated from local data, don't synthesize a decision/action; retain the count and safe run-local unavailability evidence using existing diagnostic semantics. This does not imply a new per-selected-video history, outcome class or ability to reconstruct inputs absent from the inspection query.

- **Live status (BR-042, amended 2026-11-19):** [Live ARS-001](../../live-status/specifications/ars-001-live-status-read-classification-and-deferral.md) §4–5.
  - **Readiness gate.** The readiness step for native admissions becomes the caller of `liveGatePass`. It runs on the pass's videos left after `withoutRetryVideos` and `withoutUnroutableVideos`, before the start phase of every fresh or resumed pass. Its requirement is `Live` plus the route inputs above.
  - **Retention.** The deferral of a native admission without a current report is `retainNativeTx`. That is one transaction writing the run outcome `deferred` (`metadata_unavailable`, or the existing quota, rate or auth reason) plus exactly one pending video-scoped item (`discovery_processing_pending`, or the matching existing reason). This is the same pairing as above.
  - **Live status.** A recorded `live`, `upcoming` or `unconfirmed` → `liveSkip`. A `Live` requirement is never satisfied by a held Store A row, even when "Current locally usable IDs need no fetch" applies to the route inputs. The only clearance is the run's own `run_video_outcome.live_status = 'none'`.
  - **Prefetch.** The discovery prefetch keeps the returned IDs and records `live_status` with `RecordLiveStatusTx` for the discovering run, in the transaction of `DiscoverVideoTx`. Videos from the legacy `GetVideos` branch, and from refused or failed batches, stay `NULL`.

## 4. Dependencies and compatibility

The inspected code has receipt-based claim/release and startup recovery, but `processRetryVideo` goes directly to exclusions/duplicate/routing, `GetVideos` drops malformed item details and can turn invalid duration into zero, and `Store.Refresh` only updates a held row. Source commits must **not be enabled** before the guarded receiving readiness path and repeat-claim fence above exist.

- **True BR-037 overlap:** implement/reuse ARS-005 §6's bound fetch, complete returned-ID classification, input guard and receipt dispositions for the discovery work. Coordinate with the pending BR-037 implementation; do not create a discovery-only second fetch/claim loop. Its §5 bounded claiming/variant K is independently required by amended BR-035 AC14; this spec needs its no-repeat admission invariant, not delivery of the BR-037 backlog draining feature as a whole. The existing one-pass runner can prove this feature with the same receipt/fence. The historical stranded requeue scanner, preview/confirm, `requeued_by_user` producer and its UI, and `commitUnavailableTx` are **not** Run 52 prerequisites. This document does not amend them.
- **Schema sequence:** additive discovery migration after applied `028`, Search `029`, the source-failure migration `030` ([ARS-002](ars-002-durable-source-failure-record.md)) and the receipt-provenance migration. Its number is assigned at integration under ARS-002 §6. It adds the scope, assessment and coverage rows; it must not alter `discovery_source_failure` except by additive indexes. Widen the `deferred_item` reason CHECK for `discovery_processing_pending`, keeping all values from the actual integrated schema. A rebuild must preserve every existing row/ID, timestamps, owners, terminal fields including `closed_reason`, AUTOINCREMENT high-water, foreign keys, indexes and applicable triggers; inspect current combined DDL, not historical `026` in isolation. Register the reason in queue validation, the safe-reader and Deferred projection/filter/label; it must not be rewritten as an old reason. Coordinate with capacity if it also changes the queue table or eligibility: second migration preserves first schema changes, and either producer is enabled only with matching readers. Do not jump past reserved `029` on a deployment that still intends to run that migration later. No edits to prior migrations, historical replay or mixed-version writers. Verify clean and upgrade paths on the actual integrated chain, including search/index maintenance for Store A updates. Do not claim a binary-only downgrade can safely write new data.

## 5. Authorized inspection contract

Use the existing authorization boundary for Run Detail and Errors. No read here dispatches a provider request. Keep existing video Error list, command IDs, retry/dismiss handlers and pagination unchanged.

- `GET /api/runs/{id}` adds nullable `discovery_acquisition`: `null` is unavailable evidence, not zero coverage (also use null for unsupported modes/legacy). A present object has `state` (`scope_ready`, `mixed`, `complete`, `no_attempts`, `all_local_failed`, `blocked`, `eligibility_changed_no_coverage`), integer counts `completed_sources`, `locally_failed_sources`, `unexamined_sources` (null when the scope is not known), and nullable `blocked_reason` (safe registered run diagnostic). The first two counts are settled scan results, never video totals. An unsettled or no-longer-eligible row contributes no completed or failed result. `unexamined_sources` counts scoped rows with neither a successful committed page nor a settled attempt, including a no-longer-eligible row that was never examined. Expose settled counts even when the pass is blocked/interrupted. `all_local_failed` exists only after the fatal transaction; no client inference from zero. Read these facts and the run status in one SQLite read view.
- `status=completed` with `discovery_acquisition.state=eligibility_changed_no_coverage` is explicit **incomplete coverage after eligibility changed**, with no completed or failed scans and no global blocked reason in the approved only-source case. Never project it as complete coverage, no attempts or no new uploads; there were saved observations, not routed results for them. This combination is visible only after the handoff and completion commit.
- **Amended 2026-11-20:** the two source-error endpoints and their items are realized now by [ARS-002](ars-002-durable-source-failure-record.md) §4 over the immutable `discovery_source_failure` table (migration `030`). Items gain a nullable, current-local `channel_name`. When this specification's page and settlement transactions land, a `local_failure` settlement writes its incident row in the same transaction and reuses the same table and statement. `GET /api/errors/sources` lists permanent source failures. `GET /api/runs/{id}/discovery-source-errors` reads the same projection scoped to that run, including attributable transient failures. Both use `limit` integer `1..200` (default 50), and optional positive `before_id`; newest first by immutable numeric source record `id` descending. Success is `{items:[…],next_before_id:<positive integer|null>}`, where the cursor is the last returned ID only when another row exists. Invalid parameters use `400`, a missing requested run uses `404`, and failed storage reads use the existing safe `500` envelope rather than an empty list. Register no source write methods and reject source paths at video command parsing. Source responses have no video error ID or video retry state.
- Each item has numeric `id`, `run_id`, approved channel identity `channel_id`, UTC `occurred_at`, `category` (`permanent` or `transient`), `operation` (`playlist_items_list`), `http_status` (integer or null), and nullable `reason`. `reason` is the exact operation-appropriate token accepted by the safe diagnostic contract from trusted typed provider evidence, not a transport/body/error string; `404` plus vetted `playlistNotFound` conveys the provider's missing uploads playlist fact, not that the channel is deleted. Mandatory producer/read tests ensure a known `playlistNotFound` does not become generic or disappear after restart. Absent or invalid/unrecognized evidence is `null`, not a guessed default or verbatim text; the designer owns the plain-language rendering. Neither a later healthy poll nor inspection rewrites these records. Never return tokens, URLs, playlist IDs, raw response, renewal cause text, or authorization IDs.
