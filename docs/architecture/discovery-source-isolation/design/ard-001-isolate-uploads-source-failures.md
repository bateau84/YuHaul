It also adds the run dispatch stop (§1.2) and derives the acquisition state instead of storing it (§1.3). Needs independent critique (`run52-arch-critique`).

If YouTube lists uploads for A, returns `404 playlistNotFound` for B, and lists uploads for C, the run keeps A's videos, records why B is incomplete, and continues C through the ordinary pipeline. If B fails after a successful page, the mixed run can process its already committed videos too, but B's coverage marker does not move. The next eligible fresh run polls B again from its previous coverage boundary if B is still an eligible subscription. Run inspection will explain the gap without pretending a video or destination playlist failed.

## Problem and current boundaries

- `internal/discovery/engine.go:144–171,295–359` accumulates all upload pages across channels before metadata and writes; the first non-admission `ListPlaylistItems` error returns before either stage. The method knows the polled channel even if no video exists.
- `engine.go:396–441,510–523` commits videos individually but advances `channel.last_discovered_at` inside each completed-channel video's commit. A later per-video write failure can leave unseen durable coverage behind the new watermark. `internal/stats/store.go` also projects this field as channel discovery history, so scan completion alone must not fabricate channel activity.
- `internal/state/machine.go:77–125` already creates a real video and its run-local disposition transactionally. `internal/pipeline/pipeline.go:422–456,647–674,1199–1215` consumes run-owned discoveries and claimed retries, not arbitrary old pending rows. `internal/pipeline/authority.go:348–373` has a terminal-failure retention sweep; it is distinct from automatic deferral and must not become the quota/auth path by accident.
- `internal/youtube/client.go:767–873` already finalizes guarded read attempts and separates primary provider/transport failure from accounting/renewal errors. `engine.go:186–226` uses it for production. Some current preflight paths break on any `requireBudget` error, and provider quota during uploads can go to generic phase failure. Those are current source limitations, not semantics to copy.
- `internal/store/migrations/001_initial_schema.up.sql` ties `error_entry` and `deferred_item` to real video IDs. The ledger identifies operation/status/category, not source. A single terminal run diagnostic cannot represent more than one skipped source or report partial acquisition separately from lifecycle.

## Decision and alternatives

**Keep the full production run.** Let discovery own one uploads-source scan at a time. Reuse native video/run evidence, the guarded reader and the existing authorized Run Detail and Errors surfaces. Add one compact run/source record type for positive completion and isolated failure, not an operational event bus or video queue. The permanent-failure record doubles as its Errors entry; no dual write. *(Refined 2026-11-20 by [ARS-002](../specifications/ars-002-durable-source-failure-record.md): failure incidents are an immutable table of their own, migration `030`; the mutable run/source coverage row comes later with ARS-001's migration and is keyed by the same `(run_id, channel_id)`.)* Successful completion supplies the coverage floor even when no new video was found; no separate watermark table. *(Reconciled 2026-11-22: the coverage row is `discovery_source_scope` and the run-level seal is `run.discovery_scope_cutoff`; whether the scan finished stays ARS-002's `run.discovery_scan_outcome`. No second assessment is stored. See [ARS-001 §1.1–§1.3](../specifications/ars-001-durable-discovery-page-handoff.md#11-stored-facts-and-their-owners).)*

| Alternative | Trade-off and disposition |
|---|---|
| Continue on the typed error but persist the surviving run-wide buffer at the end | Small patch and current metadata batching, but a subsequent quota/auth/cancellation, enrichment failure or write failure can still erase successful observations. It also leaves evidence dependent on logs or a single terminal field. Reject. |
| Buffer/enrich one complete channel then commit it | Can preserve independent completed channels if committed before the next scan and can preserve the floor on a failed channel. It still buffers an unbounded source, loses successful pages if a later page or enrichment fails, and cannot recover an observed ID that vanishes upstream before re-poll. A full-channel SQLite transaction also increases contention. Reject. |
| Commit page observations and a separate source completion/failure record | Preserves observed work and authorizes no new processing mode. Costs bounded extra writes, one narrow history type and explicit metadata-readiness handling. Restart may repeat uncompleted pages but cannot erase committed observations or advance an incomplete source. Choose. |
| Durable provider cursor, one job per source or separate coordinator | Could avoid some page re-fetch or change fairness, but would add cursor validity/recovery, dispatch and ownership mechanisms. Not needed for this defect. Revisit only with evidence that restarting uncompleted scans consumes enough of ordinary run budgets to prevent expected coverage. |

## Boundaries and flow

1. **Read.** Keep subscription enumeration, channel resolution and uploads enumeration distinct. Seal the eligible run/source inventory only after successful enumeration/resolution; source rows begin unsettled and are not counted as attempts. The uploads source is the actual subscribed channel selected by the scanner, not a returned video's snippet ID or a destination playlist. Fresh polling uses the then-authorized subscriptions. Retry cannot assume channel removal from one 404 or use a persisted page token. Subscription/batch-wide failures aren't attributed to a guessed channel.
2. **Admit the page.** Snapshot the source's prior floor and a conservative scan-start cutoff before the first request. The existing timestamp eligibility rule filters against that fixed floor for *every* page; do not stop pagination at the first older item or rely on provider order. Preserve existing first-use coverage. Before another provider request, durably admit the successfully decoded, eligible observations into SQLite in a bounded page transaction: real video ID, original run membership, title fingerprint and available metadata under existing retention rules. Unique native identity is authoritative: already-known/duplicate IDs do not get a second origin, processing entitlement, fingerprint eligibility reset, or channel count increment. A failed page commit does not count as admission; propagate integrity/storage failures. Do not hold a writer across reads or enrichment.
3. **Settle the source.** A run/channel scope row (`discovery_source_scope`) has the local run, canonical source channel ID, terminal scan disposition and timestamp. A local failure also writes its immutable incident row (ARS-002's table) in the same transaction. Completeness carries the scan-start cutoff; isolated failure carries the safe typed facts instead. Write completion in the final-page transaction, including an empty or all-known final page. Only after every in-scope page has committed may the completed cutoff advance; it never moves backward. Treat an exact tie at a new cutoff conservatively (reconsider it and deduplicate), and do not skip based on a returned item's newer publication time. This still cannot prove complete historical coverage when YouTube changes visibility or timestamps for older items; no broader recovery is promised. Derive the next floor from the latest completed coverage (indexed by source and successful completion/cutoff), **never** from a failure record or discovery statistics. For a source without new coverage evidence use a frozen, nullable compatibility floor copied from the pre-change `channel.last_discovered_at`, not the mutable statistics field. This carries existing eligibility forward without claiming that legacy floors prove complete coverage, resetting them globally, or claiming recovery of historically skipped videos. Keep channel analytics separate from completion-only/empty sources; no source record creates a statistics credit.
4. **Settle enrichment before evaluation.** Keep ordinary `videos.list` batching separate from source-list success and run after durable admission. Listing-only data is explicit; missing description/duration are not a real empty string/zero. Check readiness before predicates or duplicate processing, including on supported resume and on a later receiving run. Use the existing real-video deferred handoff and receiving receipt, not the source Errors projection or a second pending selector. [ARS-001](../specifications/ars-001-durable-discovery-page-handoff.md) defines the exact ownership, readiness, release and proof obligations.
5. **Continue a mixed run.** A durably recorded source-local failure ends that channel's scan for this run, not the run's acquisition loop. After normal pass settlement, route all otherwise eligible real videos, including earlier successful pages of an incomplete source. On compatible same-run resume, trust committed settlement; if none exists, restart only unsettled, still-eligible scans from page one. Check the stored run dispatch stop ([ARS-001 §1.2](../specifications/ars-001-durable-discovery-page-handoff.md#12-run-dispatch-stop)) before any provider work. Fresh runs retry still-eligible failed sources without treating past evidence as a ban. Failed/stopped runs are not reopened.
6. **Finalize zero successful coverage explicitly.** A sealed pass with no unresolved sources, no overriding global stop, and a nonempty attempted set of all local failures selects terminal failure. One writer transaction rechecks Stop/Discard and commits retained real-video work, counters and the existing terminal `failed` status, with `discovery_scan_outcome = 'no_source_scanned'` in the same `UPDATE`. Nothing becomes claimable or publishes terminal failure before it commits. A rollback leaves original ownership and the sealed scope; resume may complete that transaction, not infer failure from zero counts or restart settled scans. Do not route those observations in the failed origin or mark them failed because a channel failed. Earlier settled retry work remains unchanged. Display “No channels were scanned successfully,” never “No new uploads.” Empty successful scans count as success; no attempts, interruption and run-wide stops remain distinct.
7. **Handle the only-source eligibility change on restart.** If the only source saved observations before interruption and is now proved ineligible, with no completed scan, local failure or global stop, end `completed` with explicit incomplete coverage. The same transaction hands off the saved observations without routing them in the origin, subject to existing Stop/Discard precedence. Unsubscribing prevents another poll; it does not cancel already-saved video work. [ARS-001](../specifications/ars-001-durable-discovery-page-handoff.md) defines the separate assessment and restart proof.

| Read or local result | Required disposition |
|---|---|
| Typed `404 playlistNotFound` at an attributed uploads read, no accounting/renewal failure; other permanent responses only where the adapter can establish the same source-local scope | Permanent **attempt and source error**. Record it as the durable read-only source entry in Errors, no watermark advance, no same-run retry of that failed source; continue independent channels. Next eligible fresh discovery poll is not an in-place retry of a permanently failed video/action. |
| Attributed temporary upstream error: an admitted 5xx or a per-request timeout on that source's uploads read while the run's context is live | Transient source interruption; retain work and old floor. The source settles `local_failure` for this run with a `transient` incident row and no same-run retry (BR-002 AC6); the next eligible fresh run polls it again. A rate limit is not a source failure: it follows ARS-005 pacing, the row stays unsettled and `cut_short` stands ([ARS-001 §1.3](../specifications/ars-001-durable-discovery-page-handoff.md#13-sealed-scope-settlement-and-the-derived-acquisition-state)). Don't convert the run's cancellation/deadline to a source timeout or broadly swallow invalid/local errors. Do not guess source locality for additional frequent 4xx variants, ambiguous response shape, or account-side failures. |
| Proactive refusal or provider `quotaExceeded` / equivalent | Global operational deferral, not an Error Queue failure. Return a distinct reason, stop further API-dependent work for the run under existing quota authority (including action dispatch), keep unresolved coverage, and durably retain already-known affected videos through the quota handoff. Never retry immediately or use a positive local estimate to override the provider refusal. |
| Authorization refusal, rejection or renewal issue | Preserve same-identity renewal/read recovery under OC-006. If unable to continue safely, stop affected account-dependent work; retain input/coverage and expose reconnect-required versus temporary-unavailable as applicable. Do not make a fresh account binding or permit a guarded mutation retry. |
| Accounting/finalization, authorization guard, SQLite, or canceled-run failure | Preserve existing guarded accounting, retention and cancellation contracts. Check typed outer `ReadError` fields before considering an inner 404/transient error; a successfully parsed rejection is not permission to continue when accounting or renewal failed. A store failure in the source-evidence write cannot be reported as a successfully isolated/inspectable skip. |

At most one debit per admitted attempt, including a failed page. Refusals that never dispatched do not create a response record. Use existing attempt facts for category and a distinct read disposition for control; do not classify by `err.Error()`, conflate all 403s or change the playlist insertion classifier. In a process death between accounting and source settlement, the ledger can outlive source evidence; the source stays uncompleted. An unavailable store cannot guarantee a fresh incident row; say that evidence was not captured rather than inventing it.

## Inspection and trust

Only settled success/failure rows are attributed attempts. The acquisition state derived from the sealed scope ([ARS-001 §1.3](../specifications/ars-001-durable-discovery-page-handoff.md#13-sealed-scope-settlement-and-the-derived-acquisition-state)) distinguishes a modern empty scope from unknown or interrupted acquisition. Preserve settled rows even when settlement cannot commit. [ARS-001](../specifications/ars-001-durable-discovery-page-handoff.md) defines the bounded authorized Run Detail and Errors projections and the typed permanent reason. Show coverage independently of lifecycle and video/action counters. Legacy runs including Run 52 show source evidence unavailable, not “no failures.” Do not infer attempted source identities from aggregate calls or present previous failures as current provider truth.

Use bounded validated channel ID only as a structured source identity on the same authorized run reader, not within diagnostic text or logs. A current/local name may be used under the existing metadata lifecycle; it is not required or snapshotted. Do not retain the uploads playlist ID as an additional historical identifier, its name, titles, page token, raw URL, credentials, provider body or error chain in this evidence. Persist and project registered operation/phase, category, status and allow-listed reason; vet at production, storage and read. Logs/SSE can correlate through the local run/incident ID; neither is historical authority or a separate release channel for source identifiers. Reuse the single-user ingress boundary, not a new public route or a claim of app-layer multitenancy.

Errors reads permanent source evidence into a separate read-only source section with a run link, not fake video/action fields or overloaded video retry status. Use a separate bounded/paged projection so video list totals, filtering, pagination, retry and dismiss commands remain unchanged. Do not allocate IDs in the video error-entry command namespace or make source entries command targets. A later healthy poll does not rewrite a historical failure or clear it as a video Retry/Dismiss side effect. Run Detail and Errors read the same record through the same vetting rules and perform no provider I/O.

## Verification and composition

Use the assembled manual/scheduled runner, guarded read path, migrated SQLite and registered Run Detail API, substituting only the external provider. Add explicit checks that video admissions reach real pipeline processing, not only that a helper returns success.

- Return A successes, B `404 playlistNotFound`, C successes. Repeat with B first or last and with B succeeding on two pages before failing on its third request. Check exact ledger attempts/category, A/C processing, ordinary processing of ready real B observations from its first two pages, unchanged B floor, separate B diagnostic, no invented video/action or video error entry, and no more upload-list calls for B after the isolated failure. Repeat with the only successfully scanned channel producing zero new videos; the run is still mixed. Reopen SQLite; inspect and later allow B to recover, including a previously unseen older-timestamp page and duplicate/known IDs. Old run evidence, origins, statistics and final outcomes stay unchanged.
- Inject failure during page commit, between page commits, before final-source commit, after commit before phase advancement, and during metadata hydration. Reopen and prove each committed ID either remains reachable by the accepted owner/queue or was already settled, uncommitted coverage can be acquired again, abandoned tokens do not advance progress, and no timestamp from an incomplete scan hides an eligible ID. Include unavailable metadata, stop/discard and permitted same-run resume; assert no false routing or silent pending orphan.
- Contrast rate limit/live timeout and 5xx with proactive quota refusal, mid-page provider quota despite positive estimate, authorization rejection with successful permitted read recovery, renewal unavailable, reconnect-required, accounting failure wrapping a 404 and execution cancellation. Trace provider requests as well as saved reasons: global stop cases must not enter later reads or sends; quota/auth work remains retained for its proper retry path and never becomes a false failure/rejection.
- Restart/read the same historical run and Errors under the shipped authorization boundary. Test old runs, multiple source incidents in one run, empty versus unavailable data and injected secret/body/URL/unknown reason markers across storage, API, logs and SSE. Verify no inspection-time lookup, no source commands, and no effect on counters or Error Queue video semantics.
- Make every attempted source fail locally, including with a successful intermediate page for one of them and with earlier run-owned retries already settled. Verify persisted terminal `failed` and “No channels were scanned successfully”; the run never routes its newly admitted observations. Crash after assessment and around retention/finalization; committed real observations reach the next eligible receiving work path after restart, even if YouTube doesn't repeat those IDs, with no fabricated video failure or lost prior result. Contrast successful zero uploads, no subscriptions, stopped or time-limit interruption, and a globally blocked scan with the same zero successful-source count.
- With real candidates in the same mixed run, verify final-video immutability, frozen snapshot, prior successful-target suppression and uncertain-send veto through restart/continuation. Verify dry-run and Replay/Backtest retain their existing mode and date semantics, make no new discovery calls or mutations, and cannot consume or grant production work. Verify the QS-001 overlap on the integrated search version; it is not a claim this proposal achieved the target.

Recommend independent architecture critique before the exact persistence/readiness/API seam is relied on. These are proposed proof obligations, not executed product tests.
