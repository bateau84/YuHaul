**Status:** accepted — implementation contract; source gaps and unexecuted verification are recorded below.

The API keeps accepting old configuration payloads while the evaluator has only one handling rule: continue. For example, an otherwise valid backtest proposal containing `duplicate_behavior: "skip"` is accepted, captured with `continue`, and evaluates a matching duplicate through the proposed routes. A historical ConfigVersion may still return its recorded `skip`; that is not an instruction to today's evaluator, and it is not proof of any past playlist insertion.

## Scope and structural constraints

- `duplicate_behavior` is a deprecated compatibility field, not an enum used by the evaluator. There is no supported `skip` branch in any mode or recovery path.
- Keep JSON field names, existing endpoint/status/error envelopes, and string input compatibility. Do not reject an otherwise valid request because its string is `skip`, `flag`, empty, or an arbitrary formerly accepted string. Omission also means continue. Existing JSON `null` admission (equivalent to omitted/zero string) is retained; malformed JSON and non-string, non-null field types keep their existing invalid-body rejection. No general request-validation weakening is authorized.
- Retiring `duplicate_behavior` needs no schema migration or new runtime component. Mutable old settings may remain inert. Never edit migration 006 in place to rewrite installed history; do not add a cleanup migration solely for this field. The separate production-recovery correction below requires nullable deferred/error retry-owner references and a run producer-version marker, not a behavior migration.
- No change to threshold ranges/defaults, snapshot threshold authority, matcher, eligibility, pairwise credit, exclusions, conditions, order/final route, completed-action idempotency, or operational failure rules.

### Administration/client contract

- Settings is not a handling selector. Keep threshold tuning. Do not add an enabled or disabled skip option or describe continue as merely a default.
- If displaying current handling, describe fixed continuation and the continued applicability of exclusions/conditions/actions. No new display control is required by this realization; Designer owns placement/copy.
- History snapshot/diff values must be labeled as **recorded legacy values**, with the explanation that current evaluation continues regardless. The existing generic diff label must not leave `duplicate_behavior: skip` looking like an active selectable policy. Do not infer old execution behavior from the string alone.
- The active Settings and threshold-response TypeScript models may narrow `duplicate_behavior` to the literal `'continue'`. Historical `ConfigVersion.snapshot.duplicate_behavior` must remain a string, not that literal. Update payload types must separately accept optional legacy strings; do not couple input compatibility to the narrower response type.
- Shipped clients can omit this field on new proposals/updates. Mocks and current-setting fixtures emit `continue`. Retain intentional legacy-string fixtures for compatibility/history tests; do not mechanically replace historical data.
- Existing client proposal omission (`web/src/api/runs.ts`, BacktestView) remains valid; no new payload field or query parameter is required.

## Evaluation and results

### Normal flow and mode boundaries

1. Preserve the all-route exclusion gate before detection. Fully excluded inputs get existing exclusion evidence and no new detector lookup/match/provenance. Partial exclusions do not remove the input globally.
2. Resolve the detector from the run's selected snapshot threshold as today. Keep detector errors on the existing failure path; continue on a **match** does not mean ignore a lookup failure.
3. Production/recovery keeps existing distinct-pair match/provenance persistence. A previously recorded match only avoids repeating detection/evidence; it does not remove the video from routing.
4. Replay/backtest must remove the `match != nil → return nil` branch in `evaluateHistoricalVideo`. After successful read-only detection, both match and no-match reach `EvaluateWithRoutes`, decision collection, and action simulation. Dry-run retains the same continuation meaning.
5. Keep mode-local decisions/condition audits and `not_attempted` simulated actions. Do not call the production match recorder from these simulations. No new persisted simulation-match/provenance model or duplicate-count response is required. Existing detector diagnostics can distinguish a match from no match; verification must independently prove the fixture really matches rather than infer this from absence of production writes.
6. Never set production `video.final_outcome`, processing state, corpus eligibility, channel totals, or idempotency because of a hypothetical route result. Do not call external APIs merely to implement continuation. Backtest's existing no-external-call requirement remains in force.

### Production authorization and deferred recovery

This section implements [ARD-001](../design/ard-001-run-owned-production-action-authority.md). It is a correction to the actual execution boundary, not permission to promote a simulation. For example, a backtest match under run H is not an executable match under production run R, even when both reference the same persisted video and route identity.

#### Run configuration and executor contract

1. A production execution is permitted only for a persisted `manual` or `scheduled` run. Both `Pipeline.Execute` and the real `Executor.Execute` enforce the mode boundary before production state transitions or provider/token calls; direct callers cannot bypass it. Completed/failed runs are not restarted as fresh work by this correction; interrupted recovery retains its existing run ID and selected version.
2. Resolve `run.config_version_id` through the existing ConfigStore and reuse `routesFromSnapshot` for exclusions and `EvaluateWithRoutes`. Threshold comes from that same snapshot. One execution/resume uses a run-local immutable value, never a shared mutable active-route override. A missing ID, missing store, missing version or undecodable snapshot provides no execution authority. Do not fall back to current routes/settings or retarget an old run. Historical inspection's incomplete-context label/fallback remains read-only.
3. `executeVideoActions` and `videosWithMatchedDecisions` MUST select `GetRouteDecisionsForVideoInRun(videoID, runID)`. No production authorization query may use unscoped video decision history or a mode-only filter across production runs. A different production run's match is no more authoritative than a simulation match.
4. The existing `ActionExecutor.Execute(ctx, runID, videoID, matches)` seam can remain. `RouteMatch.RouteDecisionID` and `RouteID` are untrusted references at the real executor boundary. Before processing any action, validate the entire supplied set against persisted decisions: each decision exists, is `matched`, has exactly this run/video/route, and resolves to an enabled route in this run's snapshot. **These reference checks are necessary, not sufficient for legacy evidence:** also enforce §Legacy production admission below, including all persisted decisions for the video, not only supplied matches. Invalid or unadmitted references fail the call before any provider work or action write; do not partially execute the valid subset. Duplicate identical references do not multiply actions.
5. Resolve `ActionType`, `TargetPlaylistID` and `ActionIndex` from the validated snapshot route's actions, not `route_action`, current route children, an inactive anchor's fields, or the caller's target. Keep internal `playlist_insert` and public `add_to_playlist` translation unchanged. Preserve snapshot route evaluation order and action index order. A snapshot match with missing/unsupported action meaning is an integrity failure, not automatic success.
6. Every newly executed action records its authorizing decision ID with the same run/video and the snapshot's action type/target. Quota ledger calls are attributed to that run. Hypothetical `not_attempted` rows remain only hypothetical; a completion lookup never treats them as success or uses them to authorize an insertion.
7. Reuse durable successful-action evidence joined to `run.run_type IN ('manual','scheduled')` for the same persisted video, internal action type and exact target playlist across runs. Route identity alone is not action equivalence: changing a target does not inherit the old target's completion. Multiple current matches selecting the same mutation do not repeat it (BR-005). A completed-action check is a veto on an otherwise authorized action, never a substitute for a current-run match. Check completion before charging/checking insertion quota for that action. Do not create a new `succeeded` call/timestamp for a skip; preserve inspectable prior completion evidence and the existing already-applied inspection obligation. This contract does not add a new action-outcome enum or certify the currently incomplete skip presentation.
8. Serialize production `Execute` paths, including scheduler resume and manual/scheduled execution, with one process-local pipeline-owned execution gate. Keep snapshot capture at `StartRun`, before any waiting for execution. Simulations/configuration edits need not acquire this gate. This prevents competing mutation paths within the supported single-process deployment, not writes from unsupported second app processes or external playlist editors.

#### Legacy production admission

**Schema and producer contract.** A new forward migration adds **`run.action_authority_version`**, integer, NOT NULL, default `0`, constrained to `0` or `1`. It may share the forward migration with `deferred_item.retry_run_id`; applied migrations remain unchanged. Existing runs, including completed history, read `0`; do not update their original columns, snapshots, decisions, audits or actions. No timestamp/ID/description/configuration-content heuristic or audit-based backfill is permitted.

| Stored value | Reader acceptance / producer emission |
|---|---|
| `0` | Legacy/unknown producer; never sufficient authority to reuse persisted evaluations. All same-run decisions, including ones appended on a corrected resume, remain subject to the independent check below. Generic low-level run creation defaults to `0`. |
| `1` | Only the fully corrected production `StartRun` path explicitly inserts this value with a newly created `manual`/`scheduled` run linked to its snapshot. It certifies producer discipline for the run, not action completion. Reuse its durable prefix without fresh metadata comparison, subject to normal reference/snapshot checks. |
| Missing/unreadable column, NULL or unsupported value | Execution fails closed; no legacy fallback or coercion to `1`. Startup must apply the forward migration before workers serve. |

The marker is write-once at run creation. Resume never changes `0` to `1`; simulations retain `0` and remain forbidden at the production boundary regardless of value. Only one corrected application writer is supported. Stop the old writer before migration/worker startup; old binaries must not resume/write this database after version-`1` runs exist. A code downgrade requires restoring a pre-upgrade database under separate operator control, not dropping the marker to make new evidence look legacy. This is a deployment restriction, not a claim the old binary enforces a new fence.

**Independent evaluation.** For an unfinished version-`0` production run R and candidate video V:

1. Resolve R's original snapshot S. Load all `(R,V)` decisions and all their condition audits, not just matches or the supplied match subset. Perform this admission before existing-decision shortcuts in exclusion/routing/recovery and again inside the real executor before actions. Global video state and run phase cannot bypass it. Completed historical runs remain inspection-only.
2. Independently compute expected evaluation **E** from S and a locally available metadata value, using the same exclusion/condition/composition/order/final predicates as corrected production. This is a **non-recording** evaluation: it must not call `EvaluateWithRoutes` with the real state machine, `RecordRouteEvaluation`, or exclusion recovery that adopts an existing row. Refactor/reuse pure predicates, not a second semantic implementation. Old decisions/audits cannot choose E's matches, exclusions or final stopping point. Audits alone are not a complete original VideoContext and cannot prove exclusion absence.
3. Metadata must be available under the normal metadata lifecycle and contain every field needed by S's applicable exclusions/conditions. IDs/channel identity come from V. Do not turn absent/expired data into empty strings or infer an absent field from one old audit. The admission checker/executor performs no network call or token access to fill gaps. Normal pipeline metadata acquisition, if needed, remains quota-accounted and outside this checker; its failure retains OC-001/002 handling. Admission itself writes no duplicate/provenance, action, counter or video result. If required data cannot be established, admission is unproven, not a negative route result.
4. E is the canonical full route vector: if at least one route is enabled and every enabled route excludes V, only those enabled routes have `skipped/exclusion` decisions with no condition audits; no detector or conditions run. Otherwise walk S's routes by captured evaluation order: after a final match every later route yields `skipped/final_route_matched` with no condition audits (including later disabled routes); before a final match, disabled routes yield `skipped/disabled`, and enabled routes evaluate exclusion then all their conditions using captured composition. Zero-enabled-route outcome accounting and duplicate lookup remain the existing contracts; this checker does not fabricate a result for missing evidence. In the survivor path, normal duplicate detection still precedes recording route evaluation; a distinct match cannot suppress it.
5. Compare **every existing row** to E's row for the same route. Require equal run/video/route identity, captured evaluation order, decision, skip reason and rejection reason (including null distinctions). Its ordered audit set must match E exactly in count, unique condition index, field, operator, expected value, actual value (including null), and matched bit. A route absent from E, an extra audit, a changed predicate/order/result, a legacy `deferred` decision with no equivalent E row, or an unsupported meaning is inadmissible. Comparing only `matched`, expected condition values, enabled state or the caller's subset is insufficient. A mismatch anywhere fails the **whole video** before any playlist action; a later final flag/nonmatch/exclusion cannot be ignored because an earlier match looks valid.
6. At pipeline admission, existing evidence may be a subset of E (for example, an interrupted route prefix or partial all-route-exclusion writes). Validate every existing row first; then perform remaining normal phases and append **only absent** E decisions/audits, atomically per route, using the snapshot and the evaluated input. Never overwrite/delete a conflicting tuple. Missing evidence is not proof of completed evaluation. If inputs change before completion, recompute and revalidate rather than combining incompatible inputs. Before any action, require the complete E decision/audit set to be durably present. Executor admission independently recomputes E from local metadata and repeats full equality/completeness plus supplied-reference validation; no caller boolean, run phase, cached pass from another invocation, or marker promotion substitutes for this check.
7. A successful check grants permission only for this invocation's independently reproduced snapshot matches and snapshot targets, referencing the equal persisted decision IDs. It does **not** establish that the legacy engine originally used S or alter its marker/history. Recheck on every subsequent legacy resume/executor invocation. Native version-`1` evidence does not need this extra comparison merely because live configuration or metadata later changes.

**Failure/work retention.** A contradiction is an internal integrity failure under BR-011 AC6 / OC-002, never a fabricated rejection/exclusion or successful empty-match disposition. Before publishing failed disposition, durably retain the affected video/work in the existing runtime error queue, with R/V, conflicting decision/route IDs and a diagnostic identifying the snapshot mismatch (avoid raw transient metadata in durable diagnostics). Preserve R's snapshot linkage and all existing decisions/audits/actions. Original discoveries, decisions, owned queue groups and the existing phase checkpoint remain recovery evidence; a failure must not remove remaining selected videos from those candidate sets. No successful-completion counter, successful-work acknowledgement or new action success can follow a failed admission; atomic retained-failure queue handoff is allowed as specified below. Independent videos may continue. If the run aborts, before making it terminal failed, retain **every** unfinished candidate from that union in inspectable error/deferred work, not only the first conflicting video. Do not infer that another candidate is finished from its global `evaluated`/`acted` state alone. Interrupted persistence/retention writes roll back or leave R interrupted and candidates recoverable; do not publish successful/failed acknowledgement before durable retention. Repeated admission failure reconciles an existing active runtime error for the same R/V instead of creating an error row on every recovery attempt.

For a contradictory legacy deferred group, atomically hand the whole group's unfinished work to the durable error entry using the existing failure handoff and acknowledge all siblings together; if that handoff fails, keep all siblings recoverable and R interrupted. Do not acknowledge any sibling without the durable handoff. Temporary quota/input unavailability instead retains the existing deferral semantics. A terminal failed owner is reclaimable under the queue contract. A contradictory old decision cannot be replaced under its unique `(video,run,route)` key. The existing manual error retry must therefore enter a **fresh `manual` production receiving run**, capture the saved configuration at that run's initiation, reevaluate the retained video even if its global state is `evaluated`/`acted`/`failed`, and record new decisions under the new run.

For this retained-failure retry, the forward migration also adds **`error_entry.retry_run_id`**, nullable integer FK to `run.id`, default NULL, no cascade deletion or inferred backfill. Its purpose is the same pre-decision ownership as the deferred owner; rewriting `error_entry.run_id` or relying on an in-memory retry dispatch is not an alternative. Keep that originating `run_id` unchanged. Under the shared production gate, a SQLite writer transaction claims the error entry with `status='retrying'` and this receiving run ID, resets current video work state once, and commits before metadata/evaluation. It arbitrates all active/retrying error entries and outstanding deferred siblings for V, so another live owner cannot receive the same video. Claim all active/reclaimable retrying sibling error entries and pending/reclaimable retrying deferred siblings participating in this manual retry together; preserve their IDs/origins/details. A losing duplicate retry request returns the existing queue response without starting competing evaluation. Receiving-run creation and claim are atomic (resolve the saved snapshot before acquiring the writer, then validate/persist the linked new run and claim together); a failed claim leaves no orphan new receiving run. A crash before the first decision is recovered by querying retrying error entries by `retry_run_id`, before normal phase dispatch, exactly once per video. Interrupted owners keep their claim; terminal-failed owners retain inspectable work and permit a subsequent manual receiving-run claim. Resolve the claimed error entries and acknowledge claimed deferred siblings only with a durable new disposition or atomic handoff to retained deferred/error work. Do not mark them resolved at dispatch. Existing retry endpoint response envelopes/status strings remain unchanged.

This is failed-work retry, **not** silently resuming R with a different snapshot or starting a new run merely to repair history. A placeholder endpoint that only changes queue status without performing this reevaluation does not satisfy this correction. Snapshot-compatible legacy recovery can resume R directly under the independent rule; incompatible/unverifiable evidence stays inspectable until retry or explicit removal. No error-queue history rewrite, new outcome or generic workload ledger is authorized. The extra nullable owner discharges a demonstrated dependent risk: quarantining work safely is insufficient if the required manual retry can disappear before its first decision.

The internal retry dispatch must carry the **queue entry ID**, not just video/external-video identity, to the transaction that claims it. `queue.Service.RetryError` currently marks retrying before invoking its video-only `RetryHandler` (`internal/queue/service.go:9–19,70–106`); replace that split ownership with the atomic boundary above, and do not resolve merely because an asynchronous dispatch returned nil. Reuse corrected production run creation/snapshot linking inside the claim transaction rather than a second producer allowed to mark unvalidated runs `1`. HTTP response/status compatibility is unchanged; the durable queue result, not a new receipt or action enum, reports retry progress/completion.

#### Durable deferred claim

The schema extension is **`deferred_item.retry_run_id`**, nullable integer FK to `run.id`, with no cascade deletion and default null. Add it through a new forward migration; do not edit old migrations or backfill guessed receiving runs. Preserve `deferred_item.run_id` as origin and all existing status strings. This field identifies the current/most recent retry owner, not a general historical run-video ledger.

| Operation | Durable boundary / result |
|---|---|
| Fresh receiving-run admission | In one SQLite write transaction, verify a production receiving run and eligible pending video group, arbitrate all outstanding items for that video against any live owner, set every pending/reclaimable retrying sibling to `status='retrying'` and `retry_run_id=receivingRunID`, and reset the deferred video's current work state once to `not_yet_evaluated` / `not_yet_evaluated` with cleared current deferred/error/completion markers. Preserve discovery identity, each row's origin, and old decisions/actions. Commit before metadata/evaluation. A competing run cannot claim work owned by a running/interrupted run. No metadata/network work occurs inside the claim transaction. |
| Same-run recovery | Load distinct videos of owned `retrying` groups using `retry_run_id` before normal phase dispatch, even at an action checkpoint. Do not reset already persisted current-run evaluation on every resume. Version-`1` evidence reuses its prefix; version-`0` evidence must first pass §Legacy production admission. Complete missing ordered evaluations, and then execute only admissible matches from that run's linked snapshot. |
| Continued quota/temporary deferral | Retain durable unfinished work and return it to `pending`; a later receiving run may claim it. It must not be picked up again immediately in this same execution's FIFO batch. Retain the most recent owner reference for diagnosis until a subsequent claim replaces it. Existing deferral origin remains unchanged; do not create unbounded duplicate active items on each failed attempt. |
| Terminal retry disposition | Persist actual new rejection/exclusion or action completion before acknowledging the item as `completed`; a crash after disposition but before acknowledgement is reconciled from that receiving run's durable evidence without repeating completed actions or counters. An empty current-run decision set does not prove rejection or successful completion. |
| Interrupted owner | Retain ownership and resume that same run/snapshot. A new run must not steal its unfinished work and thereby mix two evaluation authorities. |
| Terminal failed owner / legacy unowned `retrying` item | Retain unfinished work; it cannot stay permanently hidden from pending processing. In a write transaction, permit requeue/reclaim only when no live receiving owner exists. Existing legacy rows with no owner are not evidence of a historical receiving run; new admission assigns an owner without rewriting their origin/history. Failure/error classification remains OC-001. |

Arbitration and claim writes occur under the same SQLite writer transaction, before modifying current video state, so every contender observes either its committed claim or another live owner. A loser leaves the work untouched and continues independent work; it neither reports the item completed nor executes its decisions. The execution gate does not replace durable ownership after restart. Discarded/completed queue entries are not automatically reset or retried. Any future callback that executes a manual queue retry must enter this receiving-run boundary rather than call the executor with old decisions; this correction does not change existing retry endpoint response semantics.

**Sibling rows are aliases for one outstanding video evaluation, not independent action intents.** Group all `pending`/`retrying` entries by `video_id`; use the oldest `(created_at,id)` for FIFO placement and existing pending eligibility rules. Before a claim, any running/interrupted owner on any sibling blocks a different receiving run. Reclaim terminal-failed/unowned siblings only through the stated transaction; do not guess an old receiving owner. Multiple conflicting live owners are an integrity failure: no evaluation, reset or acknowledgement until reconciled, and work remains inspectable. No migration deletes/coalesces rows or adds a uniqueness constraint.

Owner arbitration also checks retrying error entries for the video. An error retry's live owner blocks a competing deferred claim and vice versa. Deferred FIFO admission does not itself grant manual-retry authority for an unrelated active error entry; only the explicit error retry boundary claims that entry. Normal retrying error entries from an older binary with NULL owner are not attributed to a historical receiving run; they remain inspectable/reclaimable through manual retry, not an executable match source.

One claimed group causes one evaluation, state reset, outcome/counter finalization and retry attempt per video. On further quota deferral, the executor reuses the group; it must not append another active row. Requeue **all** owned siblings to pending in one transaction, retaining most-recent owner references; on durable terminal disposition acknowledge **all** owned siblings completed together. Failure handoff to the error queue and acknowledgement, if used, are one transaction. Keep each row's `id`, `run_id`, creation/reason history and completed/discarded siblings unchanged. Re-read group status/ownership when consuming a FIFO entry, and deduplicate candidates by video across FIFO, discovery and recovery. The execution's attempted-video set includes the group even after it returns to pending, so a stale sibling entry cannot immediately retry, reset or finalize it again. Recovery also deduplicates owned groups. Repeated acknowledgement is idempotent and cannot increment counters twice. Row count is not workload/attempt count.

Deferred reevaluation uses exclusions → duplicate lookup → ordered conditions under the receiving snapshot, even if the video has prior matched decisions or its global state was previously `evaluated`/`acted`. Existing duplicate evidence may avoid duplicate evidence writes, not route evaluation. A completed identical action remains complete. A real new nonmatch or exclusion completes this retry with that new result, not yesterday's eligible actions. Same-run restart preserves its own snapshot and only an admissible evaluation prefix.

#### Recovery and inspection membership

Apply that predicate consistently to list totals, outcome filtering, pagination, and detail lookup, and load only requested-run decisions/actions. Never move discovery ownership or expose another run's decisions to make a video visible.
- Use the requested run's hypothetical result for simulation display/filtering, not the unchanged production video's primary outcome. Original discovery metadata may remain original discovery metadata. This does not introduce a general zero-route/pre-decision reporting contract.
- Never recompute an old completed production run's summary from a video's later retry outcome. The existing discovery-only recomputation is not proof of historical per-run outcomes after reevaluation. #### Original production outcome evidence

A simulation result and an original production result are different facts. The accepted US-012 **does** require each replayed video's outcome alongside its original production outcome **if available**; US-011 also requires actual-versus-proposed inspection. This is not satisfied by a disclaimer alone. BR-027 **AC5** requires comparison with historical actuals; **AC6** requires recorded, distinguishable backtest results. The newer simulation-inspection wording amendment does not remove either obligation.

For example, a replay may report hypothetical `accepted` while the persisted video currently says `failed`. The latter value may belong to a later production retry, not the original run. The API must not label it as the original result. With the currently inspected evidence, the replay's `final_outcome` remains `accepted` and its separate `original_production_outcome` is `null`.

**Availability finding (source, not runtime verification).** `video.final_outcome` is a nullable, mutable video-wide column, not a per-run outcome record (`internal/store/migrations/001_initial_schema.up.sql:74–87`; `internal/state/store.go`, `updateVideoState`). `video.discovered_in_run_id` identifies discovery, not the last outcome writer. `internal/queue/retry.go` explicitly resets the current outcome to `not_yet_evaluated`; receiving-run processing can subsequently replace it without moving discovery ownership. `route_decision` and `executed_action` retain run-scoped route/action evidence, but neither stores the video's authoritative primary outcome for that run. A match alone does not prove executed acceptance, and action failure/deferral, partial evidence and cross-run already-applied work prevent a general reconstruction without further outcome rules. `run.action_authority_version` certifies producer discipline for execution admission, not original-outcome capture. Aggregate run counts cannot identify an individual video's original outcome.

Do not add a store or backfill in this amendment.
