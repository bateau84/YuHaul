**Status:** decided technical contract; implementation and conformance proof outstanding.

**Amended 2026-11-12 by [run-initiation ARS-006](../../run-initiation/specifications/ars-006-final-outcomes-are-never-reprocessed.md) §7.3 (BR-039):** `PlaylistSendClaim` gains an optional `DecisionRunID`. When it differs from `RunID`, authority is checked against that run's decision and snapshot, whatever that run's status. It also requires all of these: a production success under a decision of that run; no production success under any other run's decision; and the receiving run holding the video's retry claim. A run can therefore finish a partly done video's missing additions under the original decision. The receiving-run, success, veto and guard checks are unchanged. Review by the send-guard owner is requested.

The authorization owner and request adapter must agree on which authorization is current, when a replacement becomes usable, and whether a request was admitted for sending. The executor must separately remember when a playlist request might have applied. For example, renewal followed by a failed encrypted save returns unavailable and sends no protected request. Renewal after an uncertain POST may restore account access, but it cannot release that POST's durable replay veto.

## Structural constraints

One application process owns auth and all database writes. All production YouTube requests use the same authorization owner; no caller retains a raw token as permission for a later request. Library token exchange may be reused, but library/per-client token caches are not the dispatch authority. `oauth2.NewClient`'s outer reuse cache must not sit outside the fence. Auth mutexes do not span provider network waits. Do not call authorization resolution from inside a held action/queue SQLite transaction.

All network work is request-owned and bounded. A renewal exchange uses the initiating context with a maximum 30-second timeout. Joined callers may abandon waiting through their own context; they do not create another concurrent flight. Initiator cancellation may end that flight; a later production invocation may resolve again. No background retry loop, new user-visible deadline or refresh schedule is introduced.

## Credential persistence

Reuse `auth_tokens` row `id=1`, existing AES-256-GCM access/refresh columns and the existing 32-byte deployment key. Extend in a forward migration; do not edit an applied migration. Migration numbering is assigned against the integrated tree's next free number, not reserved by this document.

| Field | Constraint / meaning |
|---|---|
| `authorization_id` | TEXT NOT NULL, canonical UUIDv4. Opaque identity of one deliberately accepted OAuth connection, not Google's account ID. Stable across refresh/restart, replaced by a successful new connection. Never infer two IDs mean different Google users. |
| `credential_revision` | INTEGER NOT NULL, >=1. Begins at 1 for a connection; increments once per accepted durable replacement. Never wraps or decreases; overflow fails closed. |
| `access_rejected` | INTEGER NOT NULL DEFAULT 0, constrained to 0/1. A rejection of this current access revision is known; it cannot be treated usable even before expiry. |
| `renewal_failure` | Nullable TEXT; one of `refresh_rejected`, `temporary_network`, `temporary_provider`, `persistence_failed`, `invalid_response`, `client_configuration`, `access_rejected`. Only application enums, never provider prose. Cleared by accepted durable recovery. |

A migration assigns the single existing credential row one new opaque identity/revision=1 without changing token plaintext/ciphertext, scopes, timestamps or interpreting old logs. It does not certify refresh validity. A missing row remains missing. No refresh credential is copied into a new table. Database read/decrypt/schema failure is unavailable custody, not a disconnected/no-account result.

Refresh updates access, refresh, token type, expiry, revision, rejection/failure state and updated-at in **one committed write** under the auth owner's serialization. Preserve `connected_at`, provider and authorized scopes. Preserve the prior refresh value if the response omits/empties replacement. Do not merge a refresh credential from a different authorization identity. A callback creating a new connection does not borrow an old connection's refresh value when its own is absent.

Only nonempty Bearer access with a valid future expiry is accepted from a new refresh response. Validate expiry/type before Save. Missing/unusable expiry, empty access, unsupported type or an explicitly broader/incompatible returned scope set yields `invalid_response`, not usable access. If scope is omitted, retain the previously authorized scope set; if present it must not broaden it. Existing zero-expiry rows are not proof of current YouTube validity: resolve renewal when available, otherwise report reconnect-required. No scope or account-discovery request is added to refresh.

Validity uses UTC instants and the existing OAuth library's 10-second early-expiry allowance: access is usable only when nonempty, not rejected, finite expiry and `now < expiry - 10s`. Equality is not usable. This is a dispatch safety margin, not a user-facing timer or promised remaining lifetime. A fresh response already within that margin is invalid/unusable.

Before publishing a current rejection/unavailable result, persist its safe state on the current row. If that write fails, return unavailable, keep the in-memory rejection fence and disallow further sends until the state/save can be committed or new user authority succeeds. Never reuse stored earlier connected information as fallback. An uncommitted observation cannot be guaranteed durable through simultaneous storage failure and process loss; no success claim or plaintext fallback is permitted.

On refresh-success/save-failure, keep at most one private pending replacement for that identity in memory. Subsequent resolution first retries its encrypted local save rather than spending the old rotated refresh credential again. Do not publish/use the candidate before commit. Its expiry is revalidated: if access has expired, first preserve the rotated refresh in a committed renewal-required record, then resolve again. Disconnect/replacement discards the private candidate. A crash may lose it; subsequent actual grant rejection, not the save failure alone, establishes reconnect-required.

## Authorization operations and ordering

Names below identify contract operations, not mandated exported Go method names. Auth owns their state and validation. Request/executor adapters consume bounded results; they never receive a reusable refresh capability.

| Operation | Inputs | Result / ordering |
|---|---|---|
| Bind | Request context | Current `authorization_id`, or typed unavailable/no-account. Binding alone neither refreshes nor authorizes sending. The enclosing execution/request owns and shares this binding across its API clients as defined below; a client factory must not silently bind a replacement account. |
| Resolve | Bound identity; optional rejected credential revision | Current usable durable revision, or typed safe failure. Join/start the single flight only if renewal is necessary. A rejected obsolete revision does not invalidate current access. |
| Dispatch | Bound identity, concrete fixed operation/request, current context; mutation guard identity when required | Recheck current authority, expiry/rejection and durable revision at immediate sending-adapter entry. Admit exactly one request or return `not_issued`. No permit/token escapes for later dispatch. |
| Observe rejection | Identity/revision actually dispatched, recognized typed auth result | Change state/start forced renewal only if still current. Late failure is evidence of that request only; never failure of newer authority. |
| Status | Context | Coherent local snapshot below, or read error. No token endpoint/Data API call. |
| Disconnect | Context | Immediately fence the old identity and invalidate pending OAuth attempts/renewals; delete encrypted credentials before acknowledging success. Best-effort revoke is outside the fence and cannot delay local invalidation. |
| Initiate/callback | Existing single-use CSRF state and authorization code | Bind state to a user-authority generation; callback consumes it once. Commit only if that generation remains current. No late callback can undo later Disconnect/replacement. |

The mutex protects identity, credential revision, in-flight record, safe status, pending replacement and local commit. The network exchange runs outside it. One completion re-enters the mutex and compares both identity and base revision before writing. Waiters observe the accepted shared outcome or authority-changed; no waiter performs an unconditional Save of its own snapshot. Tokens/records returned internally are private copies, not pointers later mutated by another caller.

**Binding lifetime and owner:** A production pipeline execution invocation acquires one binding when it first needs an authorized provider dependency, then passes that same identity through discovery, metadata and every per-action client created during that invocation. The pipeline execution owns it; the per-action factory does not call Bind again. A standalone metadata/playlist-listing request similarly owns one binding across all its pages/clients. Account replacement during an invocation causes its later old-binding admissions to fail with authority-changed, not a silent switch to the replacement. The binding is discarded when that invocation ends. A later fresh invocation, including a resumed run after process restart, may bind the then-current authorization; no permanent run/account pin or persisted account-recovery policy is introduced. Durable mutation guards remain independent and survive that new binding.

User-authority generation is an in-memory monotonically increasing value; process restart already invalidates the existing in-memory OAuth state store. Initiating a later explicit OAuth attempt or Disconnect invalidates earlier pending attempts. Initiation alone does not revoke the current connected account: current work may continue until a new callback is accepted. Disconnect fences immediately even if deletion fails; failure returns non-2xx, never `disconnected:true`. Retry can finish deletion. Successful callback commit replaces the authorization identity and fences old clients/renewal results. Provider revocation cannot authorize any later local dispatch and cannot reconnect anything.

Request admission is the linearization point at which the sending adapter accepts a concrete request for immediate transport. It occurs under the same short authority fence as Disconnect/replace, not at token acquisition. No queue or caller may retain an admitted request for later discretionary sending. Requests admitted before an authority change may still produce network effects; this is the contract's already-issued-call limit, not a promise to cancel socket bytes. All later admissions under an old identity return authority-changed without transport entry. Tests must control this boundary, not merely compare token getter timing.

## Access rejection and retry

Recognize access rejection only from typed Data API evidence: HTTP 401, or HTTP 403 with admitted reason `authError`. Do not turn all 403/`forbidden`/`insufficientPermissions`, unknown prose, quotas or network failures into revoked refresh consent. For a still-current rejection, mark access rejected, then attempt available renewal. For an obsolete identity/revision, do not change the current status or replace credentials; a read may continue only with the same still-current authorization identity.

- A logical read (`subscriptions_list`, `channels_list`, `playlist_items_list`, `videos_list`, `playlists_list`) may issue at most one second attempt after accepted renewal/current-newer access. Reconstruct the identical page/query; discard first-attempt partial data. A second rejection returns unavailable with `access_rejected`; it does not loop or assert refresh rejection.
- A playlist mutation is never automatically resubmitted after possibly issued application, including an auth rejection. Renewal can still be attempted to restore future access, but the original operation returns uncertainty and retains its guard.
- Typed token-endpoint `invalid_grant` means rejected refresh authorization. `invalid_client`/`unauthorized_client`/`invalid_scope`/unsupported request configuration mean configuration/unavailable, not user revocation. Timeout/network/cancellation and 429/5xx/registered temporary/server error mean temporary unavailable. Other malformed/unclassified endpoint failures mean invalid-response/unavailable, not refresh rejection. Missing refresh plus unusable access means reconnect-required. A valid nonexpired current access value need not be discarded merely because its connection has no refresh value.
- Preserve API-consumption evidence for **each actual Data API attempt**, including the rejected first read and retried read. OAuth token exchange is not a YouTube Data API operation and is not charged as playlist/discovery quota. Authorization failure before dispatch is not a Data API call. Existing quota/admission contracts apply to a second attempt too.

**Read accounting ownership:** [ADR-003](../decisions/adr-003-read-adapter-owns-actual-call-accounting.md) defines the single-owner realization. The YouTube read adapter records one outcome-aware consumption entry per admitted attempt, including transport failures without a response; request-local admission survives `httpClient.Do` errors. The standalone metadata fetcher wires that recorder; the metadata manager must not also record planned/successful calls. Local metadata persistence neither creates nor reverses quota consumption. Preserve primary read, renewal and accounting failures separately; pre-admission refusal counts zero and a recording failure is never durable accounting success. Existing guarded-mutation ownership is unchanged.

**Final quota/transport boundary:** [ADR-004](../decisions/adr-004-atomic-quota-admission-and-single-attempt-transport.md), Decision and exact contract, is normative for every production Data API admission. Resolve renewal before capacity acquisition. Within the final authority fence invoke the bounded local shared-ledger hook, atomically arbitrating committed plus outstanding cost before acceptance. Positive non-admission cancels provisional capacity and counts zero. An admitted hold survives failure until its sole accounting owner atomically commits the actual-call row and removes it; failed/unknown recording does not refund known attempted cost. Auth → quota → local database is the lock order; no lock/transaction spans network work. Production shares one capacity owner, including recovery and mutation; manager preflight remains advisory. Standard Data API transports explicitly enable HTTP/1 only and disable keep-alives; redirects/hidden replay are prohibited, including through custom transports. Capacity holds neither replace mutation guards nor solve crash-complete accounting.

## Account HTTP contract

`GET /api/account`, `GET /api/account/status` and `GET /api/auth/status` return the same local snapshot with `Cache-Control: no-store`. Existing status/provider/scope/time fields remain token-free. Keep `configured`, `connected`, `authenticated`; add required `authorization_state` and nullable required `authorization_reason`.

| `authorization_state` | Meaning; `authorization_reason` |
|---|---|
| `not_configured` | OAuth is disabled; `null`. Configured=false. |
| `disconnected` | No credentials; `null`. Never use for store/read/decrypt failure. |
| `usable` | Durable, currently locally valid and not rejected; `null`. This is not a provider uptime guarantee. |
| `renewal_available` | Access needs renewal and a stored non-rejected refresh credential exists; `null`. No flight is active, so do not render “Renewing”. |
| `renewing` | Current identity has an actual unresolved renewal/local-save flight; `null`. |
| `renewal_unavailable` | Access unusable and recovery failed; reason from `temporary_network`, `temporary_provider`, `persistence_failed`, `invalid_response`, `client_configuration`, `access_rejected`, `credential_storage_unavailable`. |
| `reconnect_required` | Access unusable and refresh missing or confirmed rejected; reason exactly `refresh_missing` or `refresh_rejected`. |

Both legacy booleans `connected` and `authenticated` are true **only** for `usable`; all other states return false. `configured` means configuration, never access validity. Priority: not configured → no row → current active flight → current refresh rejection/missing unusable refresh → current unavailable failure → usable access → renewal available. A committed rejected grant keeps reconnect-required until successful new authorization/recovery; expiry alone never selects it when refresh is available. Later accepted durable recovery clears obsolete failure. Do not leak authorization IDs, revisions, token values, token hashes or provider bodies through this response.

Store/decrypt/status-read failures return `500 {"error":"failed to read account status"}` with no stale connected fallback. `credential_storage_unavailable` is for an already known in-process failure snapshot when custody/status itself can still be coherently read; do not return 200 on an unsuccessful status read. Existing initiation/callback/disconnect response shapes/routes remain, but every failure/log is guarded; callback success redirects/messages occur only after durable authoritative commit. Failed/cancelled OAuth cannot claim connected.

Settings and Overview consume the canonical rich status, not just `GET /api/settings.account_connected` or the OAuth return query. Preserve that legacy settings boolean as `state==usable`, but do not treat false as revocation or hide permitted reconnect/renewal feedback. UI adapters reject missing/unknown state/invalid state-reason combinations as unavailable status; they do not guess from expiry or credentials. An older server lacking fields is unsupported by the shipped new feature UI until upgraded; no mock connected fallback. Ignore superseded client reads after newer reads/account actions. Status retry rereads locally; it does not restart a run or force renewal.

## Durable playlist send guard

Add **`playlist_send_guard`** in Store B. It is an operational safety veto, not proof of an attempt or successful effect.

| Column | Exact contract |
|---|---|
| `video_id` | INTEGER NOT NULL, FK `video(id)`, NO ACTION deletion. |
| `target_playlist_id` | TEXT NOT NULL/nonempty; exact captured target, same equivalence as existing production completion check. |
| `action_type` | TEXT NOT NULL constrained to internal `playlist_insert`. Public projections use `add_to_playlist`. |
| `run_id` | INTEGER NOT NULL, FK `run(id)`, NO ACTION; original claiming production run, never receiving/discovery inference. |
| `route_decision_id` | INTEGER NOT NULL, FK `route_decision(id)`, NO ACTION; actual run-owned matched decision authorizing this target. |
| `authorization_id` | TEXT NOT NULL, opaque connection identity bound for this dispatch; no FK to deletable auth row. Never credentials or a token hash. |
| `prepared_at` | TIMESTAMP NOT NULL, explicit UTC claim-commit preparation time. Not `executed_at` and not proof of transport. |

Primary key **`(video_id,target_playlist_id,action_type)`** preserves the current exact-target cross-route success veto; a route rename/new receiving run or new OAuth connection does not create a new safe retry identity. The key is deliberately not per run, route or authorization. Do not normalize/change playlist IDs during comparison. Guard rows are never cascade-deleted with configuration, queues, disconnect or history cleanup.

The executor's short SQLite claim transaction validates run-owned action authority, rechecks durable exact-target production success and guard absence, then inserts one guard. It commits before sending. A simultaneous loser either observes completed success (records existing already-completed no-attempt) or guard (records uncertain-blocked no-attempt); it must not send or claim prior success from the guard. Storage/validation failure returns not-issued and preserves work. Do not hold a SQLite transaction across token exchange or Data API response.

After claim commit the adapter rechecks auth, quota and cancellation at immediate dispatch. If it definitely refuses **before admission**, the claiming invocation may remove its own guard atomically with applicable retained no-attempt/deferred disposition. If the process loses this knowledge before recording it, leave the guard. A guard from a previous invocation cannot be removed on a new caller's assertion “I did not send”.

After admission, only these results release the owning guard:

1. Definitive provider success: in one transaction record the existing requested-run `succeeded` row with actual attempt time and remove the guard. A later quota-record/local persistence failure must not erase already known provider success; if the combined local result cannot commit, keep the guard, report uncertainty and retain work.
2. Positive **known non-application** evidence supplied by the adapter for an existing contractually recognized rejection (such as quota rejection). Record that real disposition/reason and remove the guard atomically. An auth error, transport error, missing success row, empty playlist read, timeout, canceled context, malformed body or raw error prose is **not** this evidence. If conclusive semantics have not been established for a rejection, keep the guard.

All other outcomes keep the guard, even when a failure action row or retained-work write also fails. No timeout/TTL, reconnect, retry click, completed/failed run, error dismissal or config edit releases it. A later original response may conclude only while its original nonterminal invocation still owns the result; never rewrite terminal run history. No automatic reconciliation or manual clear endpoint is added. Conclusive resolution outside that live invocation needs a separate specified recovery path.

Guard presence vetoes sending in ordinary production, same-run resume, deferred/error retry, fresh receiving runs and any lower-level executor entry. Existing `succeeded` rows remain an independent veto. A new simulation never claims/releases guards or uses them to change hypothetical outcomes.

### Guard-facing adapter contract

The following are exact contract operation/type names; exported Go spelling can follow repository conventions. These are internal interfaces, not new HTTP fields. They replace the error-only insertion seam for **all production mutations**, including lower-level executor entry. No static-token/error-only fallback may bypass them.

**Binding identity:** `BindingIdentity(binding)` returns its captured nonempty `authorization_id`, or invalid-binding failure. It never reads/rebinds the current account, renews, or returns credentials. The ID is non-secret opaque correlation data for guard storage, not a reusable authorization capability. Do not log/expose it through account/run HTTP projections. Invalid binding fails before claim. A lower-level production entry without an enclosing binding must acquire one for its own invocation and use the same guarded path; it cannot silently rebind after replacement.

**Claim request:** `ClaimPlaylistSend` takes the explicit production `run_id`, internal `video_id`, matched `route_decision_id`, internal `action_type=playlist_insert`, exact nonempty `target_playlist_id` and the binding's `authorization_id`. It validates captured run-owned authority, unfinished run, mutation safety/legacy admission, and exact-target success/guard checks in the short transaction above. Outcomes are `claimed`, `already_completed`, `uncertain_blocked`, or storage/validation failure. Only a successful fresh committed insert returns a live `ClaimReceipt`. Uncertain/failed commit returns no sending permission, even if a row might have committed. The receipt carries the immutable full guard row and invocation-local ownership; lookup/resume never constructs one from an existing row. Reuse existing production serialization; a timestamp is not an ownership lock.

**Guarded insertion request:** `InsertGuardedPlaylistItem` takes the winning receipt's immutable descriptor, the exact external `video_id` read for that internal video, and the invocation context. It uses a client bound to that same authorization identity. Check descriptor/client identity equality before any dispatch, and construct one POST whose body uses exactly that external video and target playlist. The executor is responsible for mapping internal video to its external ID and passing only a fresh owned receipt. The adapter is responsible for not substituting target/identity or issuing again. No new hostile-in-process caller or cryptographic capability threat model is introduced.

**Sending boundary:** auth's `Dispatch` receives the binding, concrete request and immediate underlying transport. It resolves/renews before admission outside any action transaction. It then re-enters the same short mutex used by Disconnect/replacement, rechecks context, identity and current durable usable revision (including in-memory rejection/save fences), installs only that current access header and synchronously accepts the request for immediate transport. That acceptance records `authorization_id`, `credential_revision` and explicit UTC `admitted_at`. If intervening same-identity revision/expiry requires resolution, resolve again before admission; never send the stale snapshot. The mutex is released before the provider wait, but the accepted operation goes directly to its one transport call, without a caller-visible permit, queue or discretionary delay. Disconnect after acceptance is the already-issued limit; before acceptance it refuses the old binding. A test hook may pause before admission, not convert an accepted request into a deferred send.

The YouTube adapter consumes this operation through an injected dispatch function; it does not import auth. The composition layer binds the function to the invocation's auth binding and maps its bounded receipt. Keep request/result types local to the existing auth/YouTube packages with a small composition mapping if needed; no shared framework/package is required. A token-resolver callback followed by an independent transport call is **not** this boundary. Auth never queries action/queue state; executor/state never hold their transaction while invoking auth.

**Mutation result:** the adapter returns `MutationResult` independently of any auxiliary error. Its required `application` discriminator is exactly one of the following. Unknown/empty/invalid results can never release a claim; absent positive non-admission evidence they are treated as uncertainty.

| `application` | Authoritative evidence | Required attempt facts | Owning executor resolution |
|---|---|---|---|
| `not_issued` | The adapter positively knows this invocation never admitted a request: local request validation/build failure, auth refusal, pre-admission cancellation or quota refusal. | No admission receipt/time; zero Data API attempts. Include bounded cause/disposition. | Atomically write applicable no-attempt/deferral and retained handoff, then remove only its own guard. Failure leaves guard. |
| `succeeded` | Admitted request has a complete successful provider response validated as the expected playlist insertion result. A malformed/incomplete body is not success. | Matching admission identity/revision/time, one attempt. | Commit current-run `succeeded` action and owned guard deletion together. |
| `not_applied` | Complete typed provider rejection on this admitted request with explicitly recognized non-application semantics. Initial whitelist: HTTP 403 with structured `quotaExceeded`, under OC-001's existing quota-rejection contract. No prose or arbitrary 403 inference. | Matching admission receipt, one actual Data API attempt, bounded status/reason. | Commit existing quota-deferred disposition and retained handoff with owned deletion; no immediate retry. |
| `uncertain` | Any admitted result without the above conclusive evidence: auth rejection, transport/read error, cancellation after acceptance, malformed response or unrecognized rejection. Invalid/missing result facts also retain uncertainty, but do not themselves prove admission. | A valid matching admission receipt is required to assert an actual attempt. Never fabricate one or its timestamp from guard preparation. | Keep guard and retain work. With positive admission evidence, record failed confirmation with `mutation_application_uncertain`; without it, follow the missing-receipt rule below. |

For `succeeded`, validate a 2xx response with a completely decoded playlist-item resource, nonempty item ID, and snippet playlist/resource video identity matching the sent request. For `not_applied`, require complete structured decoding with the quota reason and no conflicting rejection reasons; otherwise retain uncertainty. The initial whitelist does not admit rate limits, generic forbidden, `videoAlreadyInPlaylist`, 5xx or negative membership reads as non-application. Expansion requires an architectural contract/evidence update, not an error-string condition. A post-admission error must not be downgraded to `not_issued` by inspecting `context.Canceled`, a network error or an auth error.

`MutationResult` also carries the immutable request descriptor, optional admission receipt, bounded primary diagnostic and a separate optional accounting/renewal failure. Match descriptor and admission identity before accepting conclusive facts. Admission's credential revision remains internal to rejection fencing, never part of the durable guard key or public output. Auxiliary recorder/renewal failure cannot replace a known application result. Each admitted request is accounted once even on rejection/failure; not-issued is accounted zero times. Preserve OC-001's actual-call consumption evidence separately from existing action-disposition/statistics conventions. Refresh exchange is not a Data API attempt.

**Missing-receipt rule:** an empty, malformed, conflicting or custom result without positive admission evidence cannot establish either an attempt or definite non-issue. Keep the guard, expose its existing unresolved-application projection, and preserve work with the bounded uncertainty diagnostic. Do not create/overwrite an action as `failed`/attempted, increment attempt counts, invent an attempt time, or assert `not_attempted` from this absence alone. Preserve any independently known prior attempt evidence. This is the existing guard-alone-is-not-an-attempt rule, not a fifth application state or new public outcome. Positive local non-admission evidence can still support a valid `not_issued` result; a default zero value cannot.

After an admitted auth rejection, observe rejection using the **actually sent** identity/revision and attempt available renewal under the auth contract. Regardless of renewal outcome, this mutation remains `uncertain`, with its original receipt and guard; never invoke its POST again. Read retry remains the separate once-only policy above. Disable authenticated request redirects and any middleware/client POST replay; never add a synthetic HTTP idempotency key that implies provider support. Admission alone proves an attempted/possibly issued operation, not provider application or socket delivery.

### Mutation accounting and rejection-observation seam

The adapter interprets the provider response; the executor accounts for the admitted attempt **before** asking auth to observe rejection. For example, a POST returning 401 produces one auth-category consumption entry, then available renewal, then retained mutation uncertainty. Failed accounting still leaves the cost held; it does not prevent rejection observation or permit another POST. This clarifies ADR-004's existing ownership and lock order, not a new retry or accounting-recovery policy.

**Minimal realization:** Keep the admitted `quota.Hold` private to the executor's injected dispatch closure. ### State and retained-work transaction ownership

The state claim operation itself must validate mutation-safety version and legacy admission in the same SQLite transaction as captured authority, exact-target production success, guard absence and insertion. An executor preflight may avoid an unnecessary claim but cannot replace that validation, including for a direct state/lower-level executor caller. `action_authority_version=1` is not `mutation_safety_version=1`: authority-correct runs created before this guard-capable release are still legacy for mutation safety. A caller-supplied admission boolean is not evidence.

Use the existing caller-owned SQLite transaction pattern for resolution that needs retained work. The state operation validates the unchanged owned receipt/nonterminal run and writes the applicable action disposition; the executor/pipeline composes existing lifecycle, requested-run outcome and queue handoff writes in that transaction before owned guard deletion can commit. A private state commit followed by queue retention in another transaction is insufficient for `not_issued` or `not_applied`. An operation accepting only `succeeded`/`deferred` is also insufficient if it cannot express an applicable existing no-attempt disposition for a positively known local refusal. Do not add `not_issued` as a stored action outcome: it is the adapter's application fact, mapped to the existing disposition/reason. Preserve zero attempt time/count for non-issue; preserve admitted-call accounting separately for quota non-application. Unknown results cannot use this release operation.

For success, the required atomic pair remains succeeded action plus owned deletion; it does not imply that all actions or the video are complete. Retry-group acknowledgement still requires the actual receiving-run video disposition or retained handoff under ARS-006. For refusal/deferral, failure of any required handoff write rolls back action/disposition/deletion together, leaving the guard and existing recovery ownership intact. Existing queue transaction helpers may be composed without moving queue policy into state/auth or adding another store/worker.

Queue Retry, Dismiss and Remove are not guard resolution and supply no legacy non-application evidence. The mutation-admission check must not disappear when an error is dismissed, deferred work is discarded, or retry ownership moves to another run. During handoff, recheck queue status/ownership in the same writer transaction; a dismissed/discarded row is neither active retained work nor successful acknowledgement. Preserve explicit removal and existing queue history; this clarification does not define removal as cancellation of an already admitted request or authorize resurrecting removed work. The independent durable guard survives removal. Unfinished retry-group release/acknowledgement follows the existing queue contract, never merely an insertion method's nil return.

## Evidence, retention and public uncertainty

Keep existing action outcomes. An actually issued uncertain operation records `failed` with canonical diagnostic `code=mutation_application_uncertain`, preserving the actual admitted attempt time when known. This reports failure to confirm, **not** certain non-application. An operation blocked by an existing guard records `not_attempted`, reason `mutation_application_uncertain`, no executed-at. Auth failure before issue records `deferred`, reason `authorization_pending`, no executed-at. A guard alone never increments ActionsExecuted or creates an attempt timestamp.

Extend the existing deferred queue's CHECK/type/reader reason set with **`authorization_pending`**, retaining all existing quota/rate values, IDs, ownership/status/timestamps. Use it only for actual missing/rejected/unavailable authorization. Preserve the accepted `run_video_outcome` deferred classification and same reason transactionally with existing queue handoff. Uncertain mutations use existing inspectable runtime/authorization error retention as applicable, never quota deferral. Pending later actions are preserved with their actual no-attempt/authorization/prior-failure reason; no fabricated successes. Abort and finalization keep the failed/interrupted semantics. Under [ADR-006](../decisions/adr-006-per-video-action-failure-isolation-and-stranded-work-retention.md), a handled per-video failure, including a guard block, commits the video's `failed` disposition and its active retained error entry together, and independent videos continue. ### Positive pre-admission authorization refusal

An authorization refusal is handled deferral, not a failed playlist attempt. For example, an owned claim followed by unavailable renewal produces zero POSTs, deferred action/video evidence and retained pending work in one commit; only then may that invocation's guard disappear. `not_issued` alone does not mean authorization failure: local validation, cancellation and quota refusal retain their own classifications. An admitted auth rejection remains uncertain under the rules above.

### Exact retry ownership receipt

The retry selector and disposition writer must agree on which actual rows authorized this invocation. A receipt is immutable correlation evidence, not a substitute for checking current ownership. It is separate from the live playlist-send receipt: reconstructing queue ownership after restart never grants permission to resolve an earlier invocation's guard.

**Internal value contract:** Queue owns `RetryClaimReceipt`; exported spelling may follow Go conventions. Its required fields are `receiving_run_id` and `video_id` (positive internal integer IDs), plus copied, duplicate-free `deferred_rows` and `error_rows` collections. Each row reference contains its positive `id` and immutable originating `run_id`; queue kind is identified by its collection. At least one row is required. Collections are not mutable aliases shared with a caller. Reason/category and latest origin are not identity fields. The receiving owner is never inferred from originating run, current global outcome or discovery ownership.

**Construction and recovery:**

- A successful `ClaimDeferredGroupTx` / `ClaimErrorGroupTx` returns this descriptor for precisely the participating rows, as well as its existing claimed/not-claimed result. Construct it after claim writes, in the same writer transaction; expose/use it only after commit. Failed/lost claim grants no receipt. Manual claims include claimed error and deferred siblings; automatic deferred claims exclude unrelated active errors.
- New-run startup and resumed `processDeferredItems` may load descriptors from existing durable owner fields before processing a candidate. Capture all row references for that receiving run/video, including preserved terminal/removal rows, not just rows still `retrying`. Load a coherent snapshot; it grants no work permission until validation. The existing retrying-row selector still determines unfinished retry candidates; a disposed-only group must not become new work. No new receipt table or migration is introduced.
- The invocation captures the descriptor before evaluation/network waits and retains it through all callbacks/fallbacks. Do not reconstruct a replacement descriptor from whatever rows happen to be latest after the wait. If removal races descriptor loading, the selected retry candidate remains retry-origin work even if no eligible row remains. Missing descriptor/rows is removed/not-owned, never fresh.
- A fresh-origin value is constructed only by the ordinary non-retry production path. Use an explicit fresh/retry discriminator in the private execution context or callback capture. Missing/invalid retry context must fail closed, not default to fresh. Lower-level executor entry without the complete pipeline handoff must retain its guard and fail rather than privately invent a fresh queue sink.

**Writer-transaction validation:** Check the unfinished production receiving run and receipt run/video equality, then re-read every exact referenced row by its queue and ID under `WithRetryTx`'s reserved writer. Check immutable video/origin and current status/owner. Do not use `MAX(run_id)`, latest category rows, global video state or a successful zero-row insert as proof.

| Current referenced row | Meaning for this handoff |
|---|---|
| Deferred `retrying`, `retry_run_id=receiving_run_id`; immutable fields match | Still-owned deferred member. Eligible for requeue/acknowledgement only with the applicable durable disposition. |
| Error `retrying`, same owner; immutable fields match, any admitted error category | Still-owned error member. May authorize retained handoff even when no deferred member was claimed. Do not require a preexisting error with the new failure's category. |
| Deferred `discarded`/`completed`; error `dismissed`/`resolved`; or missing expected row | Not a live retention path. Leave preserved rows untouched. Missing does not prove explicit user removal, but equally cannot authorize insertion. If no live member remains and no wrong-owner/integrity conflict exists, return `ErrWorkRemoved`. |
| Deferred `pending` or error `active`, even with most-recent owner equal to receiving run | Not a live claim. A separately proven already-committed receiving-run handoff may be reconciled without dispatch or extra writes; otherwise return `ErrWorkNotOwned`. | Another/null owner on a nonterminal member, mismatched immutable identity, malformed receipt or conflicting live owner on any outstanding sibling | Return `ErrWorkNotOwned` or existing `ErrRetryOwnership` for conflicting/inconsistent ownership. Do not adopt another row or insert a replacement. |

Removed/terminal siblings alone do not veto independent still-owned members. If at least one exact live member remains and no ownership/integrity conflict exists, disposition may proceed for those members only. Recheck existing cross-queue live-owner arbitration; a new unrelated row is not automatically part of the receipt or a sink. Do not weaken the existing production gate or claim arbitration. An unexpected outstanding sibling cannot be silently adopted: fail closed for owner/integrity reconciliation.

**Retained disposition rules:**

1. With live deferred members, return all such members to `pending` in this transaction, preserving IDs, original runs/reasons/history and most-recent receiving owner. 2. With live error members but no live deferred member, create/prove one pending deferred sink for the executing run and classified reason, then resolve only those live errors atomically. 3. For genuinely fresh work, establish/prove its real pending sink in the same transaction as disposition. Unrelated removed history must not veto it. Fresh does not mean “retry lookup returned nothing.” An unexpected outstanding group must be claimed/validated through the existing boundary, not adopted as fresh work.

Propagate them through normal failure/interruption bookkeeping without changing removed rows, fabricating success or recording a playlist attempt. Revalidate exact source authority before any later disposition; a true removed/not-owned result remains distinct. #### Ordinary retry failure transaction

The pipeline's `processRetryVideo` is the single owner of ordinary generic failure handoff for retry-origin work. The executor owns action/application facts, not source queue release. Neither `retainActionFailure` nor an inner lifecycle-failure branch may consume/change retry source ownership before this handoff. This applies to action errors and pre-action failures. Existing conclusive auth/quota handoff callbacks remain their own complete compositions; their successful return is reconciled, not disposed again.

**Internal operation:** `FinishRetryFailureTx(transaction, exact_receipt, failure_facts)` returns the exact active sink ID or typed removed/ownership/storage failure. This is a pipeline composition of existing queue/state operations, not an auth/state queue-policy API or mandated exported Go spelling. Failure facts contain the safe classified diagnostic and applicable existing failure disposition, not raw provider text or authority inferred from an error category. The original cause remains available internally through wrapping. Distinguish ordinary work failure from a failed guarded-composition transaction with typed stage/cause information; do not infer that stage from strings or from deferred-only versus error-only source composition.

Under one `WithRetryTx` writer transaction, in this order:

1. Validate unfinished production receiving run and the original exact receipt, including both queues and sibling-owner arbitration. Use only the returned still-owned members. Removed siblings remain untouched; no live member means `ErrWorkRemoved`, and any conflicting owner/integrity evidence blocks the transaction. Do not relax `retrying` plus owner validation to accept an inner layer's premature release.
2. Establish one inspectable active `runtime` error sink with `run_id=receiving_run_id` and the exact video. This preserves the existing outer retry-failure classification; the bounded underlying API/uncertainty diagnostic remains available without recategorizing historical sources. A preexisting runtime-category source is not required. Reuse transaction-scoped runtime retention only after step 1. Verify the returned positive ID and actual active row/run/video/category; an existing row may be reused only when it is proven to be this receiving-run retained failure, not an unrelated latest category row. Never use a dismissed/resolved row, a retrying source, an unchecked insertion result or a zero-row lookup as the sink.
3. Capture the existing failed global lifecycle and requested-run failure together in this transaction, reusing the existing state machine/transaction writer. Reconcile identical already durable receiving-run failure without another transition/counter update; never rewrite a prior run. Move an early retry-origin failure transition in `executeVideoActions` into this composition rather than publish a new disposition before retention. This changes transaction placement, not the accepted classifier or run terminal policy.
4. Complete only the validated deferred source members and resolve only the validated error source members, checking each exact ID/origin/video/`retrying`/receiving owner. Preserve source diagnostics, reason, origin and creation history, and most-recent `retry_run_id`; do not turn sources into the active sink or include the new sink in broad acknowledgement. The new sink stays active and outside the receipt.
5. Acknowledge the handled failed-video disposition only after commit. Any validation, sink, lifecycle, source-write or commit failure leaves the exact original claims recoverable through rollback and returns the typed/wrapped cause, not successful acknowledgement. No automatic second retention transaction or POST follows.

The admitted action's failed confirmation/time, preceding successes, tail no-attempt facts and actual-call accounting remain truthful. Already committed attempt evidence is not undone because later failure retention rolls back; any new disposition-dependent evidence writes join the transaction. Without positive admission evidence, this operation cannot fabricate an attempted action. Generic failure never deletes/releases a send guard, and sink creation is never replay permission. Later same-run guard-blocked entry cannot downgrade the earlier attempted row.

After committed failure handoff, reconcile using the receiving-run failed disposition, exact terminal source rows with their preserved receiving owner, and the actual active receiving-run sink. Do not revalidate disposed sources as a new live claim, resend, append another sink or finalize twice. If sink removal or inconsistent provenance prevents that proof, fail closed without replacing removed work; absent live source authority is not fresh work. A crash before commit instead leaves the original live receipt recoverable. No additional persisted handoff ledger is required.

**Exclusion:** A guarded auth/quota composition that failed and rolled back is not ordinary work failure. Preserve its original claims and guard and propagate its local failure under rule 6, even if error siblings exist. This operation must not be invoked to replace that failed composition. Likewise removed/not-owned failure is never permission to create a fresh sink. A lower-level executor entry with no complete retry disposition owner must fail closed, not silently switch to fresh-origin retention.

Keep the current action/tail evidence, global/requested-run disposition, exact queue handoff and owned guard deletion in one writer transaction. Validation or any later write failure rolls the whole composition back. The original guard remains after removal/ownership refusal; removal is neither cancellation of an admitted call nor positive non-application evidence. Actual admission/accounting remains truthful even when local retention cannot commit. Definitive success still uses its existing success-plus-owned-guard-deletion contract; queue removal does not negate a known provider success.

## Compatibility and legacy admission

Add `run.mutation_safety_version` INTEGER NOT NULL DEFAULT 0 with CHECK IN (0,1). Existing runs stay 0. Only new corrected manual/scheduled runs explicitly created by this guard-capable pipeline set 1; simulations remain 0 and cannot claim guards. No promotion/backfill. The marker attests guard-capable production, not successful execution, config authority or complete history.

An empty new guard table is not proof that pre-upgrade work was never issued. Before allowing a target for a video that has version-0 production action-eligible history, validate safe admission independently: durable exact-target success supplies a veto; trustworthy evidence that the old execution never reached mutation may permit first issue. A failed/missing action row, replayed config evaluation or absent guard is not such evidence. In this bounded release, **do not automatically admit any new mutation for a video with unresolved version-0 production action eligibility**. This includes interrupted/retry work and a fresh run encountering that video again. Retain it with a safe uncertainty reason for evidence-gated recovery, not silent retry. Read-only discovery/evaluation may proceed; terminal history is unchanged.

For this admission check, version-0 production with a persisted matched route decision is action-eligible unless its immutable snapshot proves the route has no playlist actions. Version-0 production that reached action execution for that video without complete trustworthy matched-decision/target evidence is also unresolved. If snapshot/checkpoint evidence cannot establish the absence of such eligibility, fail closed for that legacy recovery item; do not use today's routes to prove old non-application. Fully resolved recorded successes suppress their targets but do not clear an unresolved different eligible target. No broad historical target/cause backfill is authorized. This conservatism does not diagnose old runs or add a live repair operation.

Stop old writers before migration/startup. New schema/diagnostic readers and real-client UI ship together. Migration preserves old ciphertext, completed actions, snapshots, run results and queue origin/retry ownership. A down migration may not discard nonempty guards or allow an old writer to bypass them; downgrade requires an explicit separately authorized recovery/restore decision. Protecting new sends does not certify all preexisting history or all legacy recovery.
