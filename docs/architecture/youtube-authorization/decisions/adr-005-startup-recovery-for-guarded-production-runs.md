It found no material defect. Not permission for live operations.

At exclusive server startup, make abandoned guard-capable production runs discoverable by the existing interrupted-run recovery path. Resume their saved work, not a newly captured run. For example, a new manual run committed immediately before a process kill becomes interrupted on restart, then continues under its original configuration. An existing send guard still blocks the affected playlist POST, even if no action result was saved.

This repair does not recover Run 14, promote legacy rows, restart failed runs, reconcile provider effects, or establish crash-complete quota accounting.

## Decision question

How can a new guarded run saved as running become recoverable after process loss without treating a live invocation, historical run, terminal result or possibly applied POST as safe to restart?

## Drivers and constraints

Source reads on 2026-11-07 show `pipeline.StartRun` commits running before its caller starts `Execute`; `scheduler.resumeInterruptedRuns` selects only interrupted; `state.ListInterruptedRuns` excludes running. `Execute` already serializes production, rejects failed/completed, resumes interrupted checkpoints and restores owned retries first. Manual queue retry commits an actions checkpoint expressly to avoid discovery on resume. These are source findings, not runtime proof. Semantic lookup was degraded by a gopls test-symbol failure; bounded direct reads supplied evidence.

One application process owns this database and all production dispatch. `k8s/deployment.yaml` declares `replicas: 1` and `strategy.type: Recreate`. This deployment contract must include actual termination of the former owner, not merely deletion of a Pod object. A detached old process, forced node failover with uncertain old-owner liveness, rolling overlap, a second local binary, or a separate writer violates the premise. Do not attempt automatic classification in such an environment until exclusive ownership is established operationally. The manifest alone does not prove live exclusivity.

## Options considered

| Option | Benefits | Costs, failures and obligation impact |
|---|---|---|
| Exclusive startup normalization using existing versions/status/checkpoints — chosen | Closes both pre-worker and mid-run crash windows; reuses durable guards, snapshots and retry ownership; no migration. | Requires stop-before-start ownership and startup ordering. Cannot infer which volatile instruction ran or recover lost accounting. Checkpoint/guard correctness must be demonstrated end to end. |
| Persist launch flag/process identity | Can distinguish whether a worker recorded entry; useful diagnostics. | A flag before/after entry still leaves a crash window and does not prove old owner is dead or POST non-application. Both flag states need the same guarded continuation. Adds migration/writes and compatibility burden without resolving this defect. |
| Durable lease/heartbeat plus fencing | Supports overlapping deployments if every dispatcher honors effective fencing. | A timeout alone cannot revoke an already issued provider request; complete multi-owner fencing is a substantially larger protocol. Not needed in the accepted single-owner deployment. Revisit before supporting overlap, not as a speculative prerequisite. |
| Leave running rows stranded or normalize every running row | Smallest local edits. | First fails BR-011; second includes historical/simulation rows and accepts unsupported recovery risk. Neither is viable. |

## Decision and exact contract

### Ownership and startup boundary

1. Run one explicit startup recovery operation in server composition, after database migration and dependency construction, **before** scheduler workers/ticks, HTTP mutation handlers, queue retry workers or any other run producer/executor can act. Do not put it in generic database Open, store construction, migrations or a periodic sweep. Opening a database for tests/inspection must not activate recovery.
2. Its precondition is established exclusive ownership of the database/provider-dispatch process: the former owner has stopped, and no other writer/worker can continue. Existing deployment stop-before-start is the selected mechanism; no launch column, lease, heartbeat, PID or new owner table is required. Version 1 is not liveness evidence. If exclusivity cannot be established, do not classify/resume; operator must establish it before this server is started in production mode. An elapsed time or stale running row is insufficient.
3. Classify synchronously under one short SQLite writer transaction. Eligible rows have all of: `run_type` manual or scheduled, `mutation_safety_version=1`, `action_authority_version=1`, `status=running`, `completed_at IS NULL`, a linked readable admissible immutable configuration, and a recognized or null checkpoint. Recheck these predicates at write time. A corrupt/missing snapshot, unknown checkpoint, contradictory terminal timestamp/status or incompatible version is reported safely and blocks startup production admission pending diagnosis; do not silently fall through to new scheduled work or rewrite it as resumable. Read/write/commit failure likewise prevents scheduler/production admission; rollback is not success. Read-only diagnostic serving is optional, not required by this decision.
4. For eligible rows, change only `status` to interrupted and `interrupt_reason` to a registered closed diagnostic with unknown original cause. Preserve ID, phase, all times/counters/selected count, snapshot/version fields, videos, decisions/audits/actions, queues/owners, success vetoes and send guards. Reuse the existing safe diagnostic grammar with operation `load_run`, code `unknown_error` and the saved recognized phase, or `unknown` when null; optional status/reason/sqlite fields are absent. A fixed application log message may identify startup recovery with the run ID, but the persisted tuple deliberately does not distinguish all interruption sources. No new diagnostic code, guessed original cause, completed timestamp or terminal accounting is required or synthesized.
5. Already interrupted eligible rows need no normalization write. Startup selection resumes only manual/scheduled, safety-version-1, authority-version-1 nonterminal rows with the same valid authority/checkpoint requirements. Version-0 rows, including already interrupted historical rows, are not automatically selected by this startup path. Never promote/backfill either version. Failed/completed rows and simulations are neither modified nor executed. This explicitly narrows the old unfiltered interrupted selector; filtering only the newly normalized rows would leave a legacy automatic-recovery bypass.
6. After confirmed classification commit, resume eligible interrupted rows in stable oldest-first order (started time, then ID), with one owner per run through the existing shared production gate. Startup recovery must not enqueue duplicate invocations, and new producer admission must not overtake that initial recovery set. Normal producers may be enabled after it has been drained through the gate. [ADR-007](adr-007-asynchronous-startup-resume-and-shutdown-interruption.md) realizes this ordering. Classification stays synchronous before the listener. Resume runs on a background worker after HTTP starts. A pipeline-level producer gate refuses manual starts and queue retries with `503` until the worker drains, and the scheduler starts only after that. Resume no longer blocks HTTP. A restart during classification leaves either the original running row or interrupted row, both eligible next startup; a restart during resume repeats the same guarded recovery, not a fresh run creation.

### Amendment 2026-11-10 — stopped runs and unusable time-limit Run Now runs

Source: [BR-017](../../../requirements/yuhaul/br-017-manual-run-initiation.md) AC11 "At process start", [BR-011](../../../requirements/yuhaul/br-011-processing-state-persistence.md) AC7 and [BR-035](../../../requirements/yuhaul/br-035-stop-active-run.md) AC9. Realized by [run-initiation ADR-004](../../run-initiation/decisions/adr-004-stop-active-run-and-deferred-handoff.md) Decision 5 and [ARS-003](../../run-initiation/specifications/ars-003-stop-run-and-deferred-handoff.md) §3.7. Not implemented. Rules 3–6 change only as follows:

- **3a. Stopped runs settle, never resume.** In the same classification transaction, before the per-row loop, every row with `stop_requested_at IS NOT NULL` and status `running` or `interrupted`, of any run type, is settled to `stopped`. Production rows also get the deferred handoff. These rows are excluded from the recovery selection. A settle failure blocks startup (`stop_settlement`), because such a row may neither resume nor be skipped.
- **3b. One exception to "blocks startup".** A row that fails the terminal-timestamp check or the shared snapshot/checkpoint validator is skipped if it is exactly `run_type='manual' AND initiated_by='run_now' AND status='interrupted' AND interrupt_cause='time_limit' AND mutation_safety_version=1 AND action_authority_version=1`, oldest or not. Startup leaves the row unchanged, logs `startup recovery left unusable run` with its ID, closed cause and validator reason, and continues. The run is then discardable in-process (run-initiation ADR-003). Every other failing row still blocks startup, exactly as rule 3 says.
- The rest of rules 3–6 is unchanged: version rules, the normalization write, oldest-first resume of the remaining rows, and gate ordering.

### Position and safe continuation

7. Null checkpoint means **no persisted phase checkpoint**, not proof of never-started execution. It uses the existing initial discovery entry after recovering owned retries. A recognized checkpoint resumes that saved phase, including any necessary reconstruction of surviving inputs; it is never reset to discovery merely because status changed. Manual retry's persisted actions checkpoint stays actions-only and cannot add discovery. Partial discovery can repeat reads under the existing read/quota policy, but must preserve committed discoveries and progress without duplicate ownership; do not invent a page cursor or completeness claim.
8. Use the original run ID and captured snapshot. Reconstruct membership from that run's discoveries, decision evidence and exact durable retry ownership as required by the existing contracts, not global pending-video state or current routes. Recovered retry receipts describe exact queue rows, never playlist-send permission. Removed/disposed work stays removed and committed handoffs are reconciled without resurrection, duplicate sinks or duplicate counters. Completed targets stay skipped; partial successes remain intact.
9. A new invocation may obtain the current auth binding under ARS-001. It **cannot** reconstruct an old send ClaimReceipt, remove an old guard, or infer non-issue from null checkpoint, missing action row, missing admission receipt, elapsed time, successful refresh, or its own lack of sending. Guard presence blocks the exact target across all runs/connections. Guard-only evidence does not increment attempts, create attempt timestamps or overwrite a previously recorded attempted failure with no-attempt evidence. Preserve the existing version-0 video-history veto even inside a new version-1 run.
10. Resumption grants permission only to attempt the existing validated pipeline path, not certainty that every video can be executed or that the run will complete. Unknown application remains unresolved and retained under ARS-001. Ordinary newly observed phase failure still follows accepted failed/interrupted retention rules. No durable failed evidence may be erased to make it resumable. A running row alone cannot reconstruct an uncommitted original phase failure or its cause; record process-loss interruption only, without claiming the original phase succeeded or never failed.

### What the marker proves

`mutation_safety_version=1` plus the other eligibility predicates and exclusive startup boundary is sufficient for this bounded recovery. It proves the creator used guard-capable mutation paths; it proves neither worker launch nor safe replay of every target. Launch evidence is unnecessary because both never-entered and partly-entered workers can follow the same durable, guard-preserving continuation. A lease is unnecessary because liveness is established by the supported deployment lifecycle, not by row age. If that lifecycle is no longer enforceable, stop using this realization and design multi-owner fencing before enabling overlap.

## Consequences

The immediate benefit is discoverability after real process loss without a new persistence model. The cost is one startup composition boundary, strict eligibility/reporting and integration/crash tests. Under ADR-007, only migration and classification delay the listener. Production producers are refused while recovery runs. No zero-downtime or fixed-time recovery guarantee is introduced. A SIGTERM during resume leaves the run `interrupted` (ADR-007 §3). No historical migration or cleanup is needed. Corrupt eligible rows prevent silent production continuation and require diagnosis. Existing legacy startup resumption is deliberately excluded, not repaired by this change.

The remaining unknown external effects stay blocked rather than automatically reconciled. Outstanding quota holds are process-local; this decision neither reconstructs lost debits nor proves a strict crash-spanning request budget. That independent boundary is not a reason to remove guards, reset quota history or claim complete accounting.

## Confirmation and reconsideration

Required evidence, not executed by this document. Use disposable SQLite plus real server composition/pipeline/auth/queue/YouTube adapter and controlled local OAuth/Data API endpoints only; no live credentials or database.

- Kill a child server after a real registered manual start has committed but before worker entry. Restart through the actual startup composition. Same ID/snapshot survives, running becomes interrupted then legitimately resumes; no extra run, snapshot, claim, input-count reset or duplicate worker. Repeat for a scheduled start.
- Kill mid-discovery after committed input; and after exclusion, duplicate, routing and actions checkpoints. Restart uses each saved position, immutable configuration despite live edits, correct survivors and once-only counters. Partial discoveries/owned retry groups survive. Kill a manual error/deferred retry after claim before first decision: resume its saved actions checkpoint with zero discovery calls, exact source ownership, no removed-work resurrection and no duplicate sink.
- Kill after guard commit before POST, and after controlled provider application before success commit. Both restart paths retain the guard and send **zero further POSTs for that target**, regardless of renewed auth. A definitive success committed before kill suppresses replay and preserves its attempt/history; a previously attempted uncertain row is never downgraded by blocked re-entry. The blocked video is recorded `failed` with an active retained error entry, and independently eligible videos continue under [ADR-006](adr-006-per-video-action-failure-isolation-and-stranded-work-retention.md). This is not a blanket success claim.
- Crash before classification commit, after commit and during resume; inject classification read/write/commit failure. No partial successful acknowledgement or scheduled/manual bypass. Race attempted new start during the startup boundary; it cannot become part of the abandoned cohort or overtake recovery. Repeated startup selection creates no duplicate owner. Prove supported process supervision actually stops the old child before replacement; do not use sleeps or row age as evidence. An overlapping-owner configuration is rejected operationally, not certified by this suite.
- Seed a synthetic Run 14-shaped **version-0** running discovery row with 19,615 pending inputs, original snapshot, mixed later successes/queues and additional legacy interrupted/failed/completed rows. Snapshot full logical rows before/after classification and recovery. They, their cohorts and unrelated terminal/simulation runs remain unchanged; no legacy worker/provider request is launched. This is a fixture, not a current observation of live Run 14. Include a separate new version-1 run to prove filtering is not merely an empty recovery set.
- Missing snapshot, unknown phase, contradictory completed timestamp, invalid marker combination: no automatic action or silent new-run fallback, safe error reported. Simulations never classify, bind auth or dispatch. Check diagnostic sentinels across SQLite/API/logs. Reopen confirms snapshots, guards, exact queue history and genuine outcomes remain unchanged except authorized new-run recovery writes.

Independent contract critique is recommended before reliance; implementation review must establish the assembled startup path, not just a manually changed status or direct `Execute` call. Reconsider launch/lease machinery only if deployment overlap becomes required or real single-owner enforcement fails. Historical recovery remains separately evidence-gated and authorized.

## Open questions and operational boundary

No new user-owned product choice blocks the new-run repair: restart continuation and uncertain-mutation suppression are already accepted. **User/operator still owns any live rollout/restart and all Run 14 intervention.** Before applying a tested build to the incident environment, establish actual exclusivity and inspect later runs/unfinished ownership through an authorized procedure; deployment may itself resume newer version-1 work. This artifact is not that procedure or authorization. Run 14's current 19,615 count, provider effects and later ownership are unverified here. Do not mutate its status, promote its version or resume it to test this repair.
