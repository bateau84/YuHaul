**Status:** proposed technical realization of accepted requirements; the receiving-run primary outcome after an evicted sibling is blocked on product direction. No implementation or runtime verification.

Check the destination playlist before each otherwise eligible production add. If Study is full and Lofi has room, the run defers the Study add, can still add to Lofi, and shows both results. A later run rechecks Study and, if eligible, sends only the missing add under the decision that authorized it. If the Study waiting list already has 5,000 distinct videos, the next distinct enrollment displaces its oldest entry. That entry remains visible in history but no later automatic path can revive it.

The two 5,000 limits are independent: one is the product threshold for items on YouTube; the other bounds active local waiting work **per actual playlist**. No space is reserved on YouTube. The read is an observation, not a guarantee about concurrent edits or provider consistency. A refusal or lost result does not authorize a second POST.

## Decision and alternatives

- **Provider count:** Use `playlists.list` by exact `id` with the documented `contentDetails.itemCount`. An unfiltered `playlistItems.list` for the exact `playlistId` documents `pageInfo.totalResults` as the result-set size, not a separate target capacity field. Counting all item pages at 50 per page costs about 100 units at the threshold and is not a point-in-time snapshot. Neither pagination nor a video-filtered membership check is a fallback for a failed or insufficient count. A POST used as a probe would violate BR-040.
- **Local space accounting:** Reuse the production execution gate and a short-lived per-target observation in that run's execution pass. Maintain local consumption against it and fail closed on missing evidence. Reading once per add is simpler but repeats valid reads and does not by itself protect against an unresolved prior send or a stale response. A cross-run count cache or mirrored inventory would add sync, expiry, restart and reconciliation work without supplying a YouTube reservation or stronger provider evidence.
- **Waiting work:** Extend the existing SQLite Deferred Queue with a target-scoped row form and keep evictions as terminal history of those rows. A separate capacity table with a union reader can also model the two scopes, but would have to duplicate row identity, history, removal and retry/recovery machinery or add a second ID namespace; it does not eliminate the common admission fence. A reason-only column change with video-wide disposition cannot enforce exact-target ownership, the cap or non-resurrection.
- **Scope:** Keep the existing production gate and credential/quota admission. Add a short local ownership fence because queue/lifecycle writes can overlap dispatch preparation; never hold it across provider I/O. No worker, polling schedule, distributed lock, provider delete, manual restore/guard clear, or broad replay or backfill. Revisit coordination only if concurrent mutation writers replace the current single-process execution model.

## Provider evidence and send admission

**Count:** Under the same captured authorization binding as the add, request `GET /youtube/v3/playlists` with one exact `id`, `part=contentDetails` and a partial response containing `items(id,contentDetails(itemCount))` and `nextPageToken`. [The list method](https://developers.google.com/youtube/v3/docs/playlists/list) defines the exact ID filter; [the resource](https://developers.google.com/youtube/v3/docs/playlists#contentDetails.itemCount) defines `itemCount` as the number of videos in the playlist. Accept only a complete successful response with one matching resource and a present unsigned integer count, distinguish explicit zero from missing/null, and reject unexpected pagination, duplicate or mismatched IDs, malformed or incomplete responses and unconfirmed read accounting. No title, picker result, subscriptions/uploads ID, local action total or HTTP cache hit from an earlier pass supplies this fact. A read error keeps its own quota, authorization, temporary or failure meaning; a missing resource is neither empty/full nor a missing **video**.

**Spend:** The serialized mutation owner maintains an observation scoped to exact playlist ID, captured binding and one live execution pass. New run, resume/restart, authority replacement or loss of observation requires a new authorized read; do not restore a cached slot. Within the pass debit one at local add admission, retain it on success or unknown application, and restore it only on positively known non-admission/non-application. A definite full refusal invalidates prior room and establishes fullness for this target in the pass, not a future retry. A result for a different video/route targeting the same playlist uses that same local allowance. Only observations still within a short freshness window, bounded by the live pass, can authorize a send. Use 60 seconds from the successful provider observation as an initial technical maximum, not a provider freshness guarantee or a public setting; recheck at admission. An ordinary eligible add may demand a fresh read after expiry. No timer refresh, immediate recheck of the same full add or extra read simply because another eligible video shares its still-usable observation.

**Across observations and restart:** An updated count covers a prior success only if provider evidence ties that specific add to the count's view, for example a documented causal read barrier covering that insert or a consistent snapshot binding the count to membership that includes the inserted item. The cited API establishes neither. A later request, elapsed time, a higher or unchanged count, an ETag, a separate membership read or a restart does not establish coverage. Other clients' edits can offset local adds. Do not make extra probe calls to try to infer coverage.

Start both bounds at the usable reported count. Confirmed local adds admitted **after receipt of that observation** count in both bounds; that observation could not have included them. Prior successes with unknown coverage and potentially applied sends count only in the upper bound, even on a later refresh or after restart. Use an exact-playlist lookup of durable production successes and unresolved guards, plus unsettled live admissions. Count each possible add once, distinguishing an admitted send from the current invocation's positively unissued preparation. Do not clear an allowance when a successful insert's guard is removed; its success row now supplies the evidence. Do not assume zero prior effects at migration, age out an allowance or treat a later count as proof of non-application. Existing legacy and exact-target mutation vetoes remain independent.

With arithmetic capped at 5,000: full if the lower bound reaches 5,000, room if the upper bound is below 5,000, and insufficient evidence otherwise. These are bounds for applying the observation, not a live guarantee against external edits. A 4,999 observation followed by one confirmed local add projects full on that same observation; a refreshed 4,999 with unknown coverage of that add gives 4,999–5,000, even after reopen, and proves neither room nor full. A usable 4,998 plus one unresolved allowance and no others gives room for one guarded add; usable raw 5,000 proves full without any allowances. If the count itself is known stale or contradictory, do not use it for either conclusion.

**Availability limit:** Uncovered successes can accumulate, potentially making room impossible to establish even after actual slots open. An unconditional promise to send whenever a slot physically opens, or to always accept an updated 4,999 as room, is infeasible on the documented interface. BR-040 says not to send on insufficient evidence, and BR-041 makes continuation conditional on established room; the dispatcher confirmed no stronger premise was agreed (Loom reply `2c8636bc-6432-45fe-b1b3-1c6d4dba35b0`). Revisit with the product owner if the resulting availability is unacceptable; do not claim false fullness or drop the allowance on a timer.

**Fence:** Only a production mutation-authority path may start an add. Check final video, exact decision/target scope, matched snapshot authority, known success, legacy and independent guard vetoes before using capacity as a disposition; reject stale authority without relabeling it full. Avoid a guard on a proved full/no-send path where possible; if prepared, clear only the current invocation's positively unissued guard in the retention transaction. On the room path keep the [existing guard contract](../../youtube-authorization/specifications/ars-001-authorization-state-dispatch-and-send-guard.md): commit the exact guard before admission. After any renewal and immediately before irreversible local call admission, revalidate the unchanged guard, exact live work receipt or proven fresh work, target suppression, production run and stop marker, finality and local room. Neither a prepared guard nor a preflight read is the fence. Use a short process-local gate shared by this validation/admission and all writes that can invalidate it (including exact Dismiss, eviction, ownership transfer, terminal/final writes and the durable Stop marker). Verify writes share the gate or are already serialized by the production gate; do not rely on eventual context cancellation after Stop's marker.

The gate spans the final local check and commitment of the quota hold to an admitted attempt, not OAuth renewal, `RoundTrip`, response parsing, or outcome accounting. Acquire it before auth/ledger/SQLite work in this local admission segment; acquire it before the writer on invalidating paths, and never acquire the gate or quota/auth locks from an existing writer transaction. Do not perform SQL in the ledger's pure `AdmitIf` validator; use transaction-consistent local checks under the outer gate and use the final validator for expiry, freshness and other already-captured facts. No auth/quota/SQLite lock spans a network call. If the invalidating write wins, there is no admission, no POST and no resurrection. If admission wins, stop/removal/eviction can affect future authority but does not recall the admitted operation. The existing single-attempt transport and accounting ownership remain binding.

**Fence both capacity GETs:** The initial count GET and the one permitted credential-recovery GET must each enter that same lifecycle gate afresh, after any renewal and before admitting their own one-unit hold. Check the receiving production run, no committed Stop marker and no lifecycle/ownership loss under the gate, alongside normal authorization and quota checks. `StopRun` takes the gate before its run-control mutex and durable marker write; no caller holding the run-control mutex may acquire the gate. Cancellation arriving after the marker is not the fence. If Stop wins, cancel any provisional hold: no GET and no debit. If admission wins, account that attempt once; Stop can still veto the recovery GET or POST, and the late count cannot grant another call. Release the gate before transport; no lock spans OAuth exchange, response handling or accounting. This obligation covers both new capacity read admissions, not a claim about existing read callers.

**Live-status gate (BR-042, amended 2026-11-19):** [Live ARS-001](../../live-status/specifications/ars-001-live-status-read-classification-and-deferral.md) §6.1 and §7. The live check comes before every capacity step (BR-042 AC13).

- Before the first count GET for a claimed capacity row's video, the planner calls `liveGateClaimed` with a `Live`-only requirement. If the receiving run's recorded status is not `none`, the result is `liveSkip` with the receipt:
  - no GET and no POST;
  - no room check, enrollment, eviction or change to the cap count;
  - the capacity row is released to `pending` unchanged (same ID, enrollment, age and owner history).
- A live video that is not confirmed is never admitted to a waiting list.
- The final POST admission fence checks `LiveClearedTx(sending run, video)` alongside the checks above. A refusal there is the live deferral of authorization ARS-001 (*Live-status clearance at the send*), not a capacity disposition.

**Admitted full refusal:** [YouTube's `playlistItems.insert` error table](https://developers.google.com/youtube/v3/docs/playlistItems/insert#errors) and [error catalog](https://developers.google.com/youtube/v3/docs/errors#playlistItems_insert) specify `403 playlistContainsMaximumNumberOfVideos` for this insert because the playlist **already** contains the maximum allowed number of items. [HTTP 403](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.4) means the server understood the request and refuses to fulfill it. Together these support the documented method-specific refusal of this insert on a preexisting capacity condition, not a generic claim of rollback on a 4xx. Recognize only the trusted, complete, unambiguous error response from the single admitted POST whose claim/receipt and sent video and playlist exactly match: actual 403, one fully parsed provider reason equal to `playlistContainsMaximumNumberOfVideos`, no competing reasons, malformed, duplicate or contradictory evidence fields, redirects, or transport/body-read failures. The adapter produces the private `not_applied` capacity fact; a diagnostic enum, exported error value, status, substring or later count is not evidence for guard release. If the provider semantics or attributable response shape do not hold, keep the branch uncertain; a fixture cannot make an undocumented shape conclusive. The method's documented maximum need not equal a returned count; a genuine refusal suffices on its own.

## Disposition and accounting

| Fact | Required effect |
|---|---|
| Known full, positively no POST | Current target `deferred / playlist_full`, no add attempt/time/insert charge; enroll or retain this target and continue eligible siblings. The count request remains a real read. |
| Exact admitted full refusal | Same target deferral with actual admission time, one attempted add and one 50-unit insert debit with existing ledger category `permanent` (the provider response category, not the application's retry disposition). Clear only the live owned guard, atomically with the capacity handoff. No immediate repeat. |
| Count cannot establish room | No POST, do not enroll new work as full on that basis. Use the applicable quota/auth/temporary/failure policy, retaining existing capacity waiting at its original age. An insufficient otherwise successful read uses a bounded `capacity_evidence_unavailable` diagnostic, not a second capacity reason. |
| Admitted application unknown | Preserve actual attempt evidence and independent durable guard; use existing uncertainty and failure retention. Do not create evictable capacity work as substitute. If the target already had an authorized capacity wait, preserve its enrollment separately; it cannot send while guarded, and later eviction cannot remove the uncertainty or its independent protection. |
| Known success | Record actual success under the sending run and authorizing decision; settle only the authorized live target. If evicted after admission, do not change the eviction history; the real success is independent evidence and still vetoes all repeats. |

Each admitted count GET is 1 unit (including any allowed read retry as a separate call); each admitted insert is 50. Sources: [YouTube quota costs](https://developers.google.com/youtube/v3/determine_quota_cost) and [authorization ADR-004](../../youtube-authorization/decisions/adr-004-atomic-quota-admission-and-single-attempt-transport.md). The single read adapter owns `playlists_list` accounting; the guarded insert owner finalizes its one `playlist_items_insert` hold, including transport errors, before any rejection observer. No recorder on the side, debit for a refused admission, reserved budget or special quota pool. An uncached check plus insertion normally costs 51 units; known-full checks use the read cost only. Do not perform a whole-video 50-units-per-target reservation or let known-full targets inflate the remaining send estimate. Use existing quota precedence for due work and per-operation admission, with costs for required reads in preflight estimates when relevant; actual admission remains authoritative. A capacity wait is not permission to retry repeatedly in the same pass. Each eligible target gets a bounded consideration per ordinary pass; later eligible work is not starved solely because a preceding target remains full.

Failure to record a real call remains a separate accounting failure, not new room, failed application, erased success or permission to resend. Preserve conservative held cost and the existing run-failure reporting without overwriting a committed primary disposition. Existing crash-complete accounting limits still apply; neither this design nor the send guard is a new transactional quota journal.

## Durable target work and continuation

**Store and identity:** In the existing `deferred_item` namespace, distinguish legacy video-scoped rows from `playlist_full` rows with required exact case-sensitive YouTube playlist ID and authorizing `route_decision` ID. The decision's run is derived from that decision, not from the waiting row's enrollment run or the current receiver. Preserve the row ID, origin run (the enrollment run), original reason, creation time and most-recent retry owner. Keep a separate `evicted` terminal queue status and eviction time with a closed reason such as `capacity_evicted`; neither user removal (`discarded`) nor processing completion (`completed`) is eviction. Legacy rows require no target backfill. Active means pending **or retrying**. Enforce active uniqueness on `(target playlist ID, video ID)`, and index exact pair history and the active oldest-for-playlist lookup. Use monotonically allocated queue ID as settled enrollment order; wall-clock adjustment or tied timestamps cannot rearrange it. The queue cap is enforced by the common writer, not count-then-insert in separate transactions.

**Video-scoped uniqueness (BR-042, amended 2026-11-19):** The one-active-row guard for **video-scoped** (non-capacity) rows ignores capacity rows. A live skip therefore always leaves exactly one active video-scoped item, even when the claimed receipt owns only capacity rows. A later eviction of a capacity row can never leave the video with no active item ([Live ARS-001](../../live-status/specifications/ars-001-live-status-read-classification-and-deferral.md) §6.1 step 5). Capacity rows never carry `live_hold`, and they never count as the live sink.

**Atomic transition:** Under `WithRetryTx` validate production ownership, required target and saved decision, and existing success, removal and guard boundaries. Repeated evidence for an existing eligible pair keeps its original row/authority and age, and never triggers eviction. For a new distinct eligible pair at 5,000, transition only the oldest active row of that playlist to evicted; retain its origin/owner and record the time, then insert the new row. Commit that transition, exact source or target handoff, requested-run target evidence, and any permitted owned guard release together. A stale evicted/dismissed receipt cannot authorize a replacement, a no-op insert is not a valid sink, and an unrelated live sibling cannot substitute. Index and writer rules apply to all activation paths, not only insert. Preserve old rows and attempts. No deletion, revival of evicted history, or reinterpretation of `evicted` as a success or an explicit dismissal.

**Claim versus authority:** Keep video-group arbitration and once-per-video processing/membership. Extend the exact retry receipt in [authorization ARS-001](../../youtube-authorization/specifications/ars-001-authorization-state-dispatch-and-send-guard.md) with a discriminator for scoped capacity rows; carry exact immutable row ID, origin, video, target and decision alongside receiving run. Capture under writer after claim, use only after commit, reload durable queue ownership on resume without recreating any live send receipt. A capacity-only receipt (even before the first success) can execute only its live captured targets against their frozen decision. `DecisionRunID` still needs the validated matched production snapshot, nonfinal sender, existing legacy/success vetoes and unique original decision when partly done; replace the current video-wide “has any retry row” condition for capacity sends with exact target ownership. If a necessary snapshot, decision or authority is missing/inconsistent, retain with the existing safe authority-failure reason; do not re-evaluate to guess a target. A valid source for A cannot authorize B. A manual retry of an active capacity row, if exposed, scopes to that item; existing video-wide manual Retry must not be used as a target control. Dismiss, if exposed for capacity, uses the exact existing row ID and never discards siblings.

**Mixed work:** Keep the remaining actions of a decision independent of capacity rows. A whole-video retry receipt grants only its independently eligible ordinary work, not ownership of a capacity row. The decision/action planner partitions required targets into recorded successes, held/evicted targets, live owned capacity targets, uncertain targets and ordinary remaining work. The same target held elsewhere, evicted, or dismissed from its capacity row cannot be redispatched through an ordinary sibling, the discovery/main action loop or recovery. Check suppression by exact pair, not by “latest queue row” and not by excluding every target of that video. Whole-video work continues under its existing rules, but cannot replace the captured capacity decision, finalize a video while a required add is still missing, or turn an evicted-only obligation into a new decision. For a partly done video use the original decision for all its remaining work. For ordinary residual actions from the **same** already-evaluated decision, persist a reference to that decision in the existing handoff/receipt so remaining work is derivable after restart from its exact targets, action evidence and scoped dispositions. Do not send those actions from a different decision simply because no success exists yet. Do not create a second inventory of done targets. A genuinely independent pre-evaluation source remains governed by its existing rules and cannot supply contradictory authority for a pinned action. If persisted decision authorities for a video conflict, retain the affected work as unreadable/inconsistent authority, not guesses at new targets. Settle each ordinary source only against its own residual outcome; a capacity-only handoff never acknowledges the entire group. Release rechecked full capacity claims back to pending without changing enrollment, and leave the pending sink outside broad acknowledgement. A separate quota/auth/temp problem does not transfer or de-age that capacity waiting row. The waiting cap counts the distinct rows in that form only, not the ordinary siblings.

**Complete the video after the targets:** Record actual per-target evidence, receiving-run membership and durable retention as each target settles, not an unconditional video-finalization transition in the capacity callback. If the process dies after that commit and before the aggregate result, the run/decision and exact action/queue records are the checkpoint: honor settled targets, resume only authorized unsettled work, and still produce the single aggregate disposition when allowed. Recovery must enumerate that incomplete receiving-run membership even when every capacity claim is now pending or terminal and no live retry row remains; this grants settlement, not dispatch. A returned-pending or later-evicted row is never a new live claim of the interrupted invocation. When the pass finishes, the pipeline commits the single requested-run/global video disposition under existing outcome rules and the exact remaining ordinary handoffs. Capacity by itself gives `deferred / playlist_full`; independent uncertainty/failure and stopping conditions retain their existing classifications and evidence. Do not publish an interim final or count the video twice. An original required target that is evicted remains missing. Eviction does not write a new video outcome or assert current fullness; if a later pass resolves separate work, do not turn an earlier nonfinal result into accepted merely because every still-active target has succeeded. Reconcile success or a committed deferral by its exact receiving-run evidence on resume: no same-run repeat after a handled capacity result. Preserve earlier results and attempts on save failure or later re-entry.

**Pinned authority for ordinary sibling B:** When the same saved decision has a capacity target A and unrelated remaining ordinary work for B, B keeps its own scoped receipt, even if neither target has succeeded. Persist the exact B target and matched route-decision reference on B's durable ordinary retry work; preserve its own queue kind, original reason and row identity. It does not count toward the capacity cap. In the state writer, before guard preparation, verify the exact row ID, immutable origin, video, B target, decision, live `retrying` status and receiving owner. Verify B in that decision's matched production snapshot. If previous production success exists, the pinned decision run must also agree with BR-039's unique original decision; with no success, the validated B receipt supplies the cross-run authority instead of the success-derived lookup. The final admission fence rechecks that same B receipt and applies all existing finality, success, legacy and guard vetoes. Neither A's row nor an unrelated video-level retry row, caller-supplied decision ID, or current configuration can authorize B. B cannot authorize A. A transfer of B to capacity waiting, if B itself is proved full, validates B's own receipt and establishes its exact sink before acknowledging the source. Restart reconstructs B's queue ownership, never a live mutation receipt.

**Receiving run when B succeeds after A was evicted:** Store B's actual success in the later run under its original decision and settle only B's source. Preserve A's eviction history and automatic-retry veto. The video stays partly done and nonfinal, with no active retry if no other eligible work remains. These lifecycle facts are settled under BR-039 and BR-041. No existing primary outcome fits the receiving run under BR-032 and OC-002, per the specifier finding relayed in dispatcher answer `fc33dbca-30a2-48df-8ce3-af2dad9e7c6f`. The product decision remains open. Neither an amended Deferred meaning nor an omitted primary outcome is authorized. This blocks the receiving-run aggregate contract and feature release, not the design of the independent action/queue transitions. Do not claim acceptance, failure, current fullness or automatic retry for this case.

**Other entry points:**

- **Stop, discard and run-failure sweep:** Release or retain the exact outstanding capacity claims, with age and scope intact; do not make room checks unnecessary. No generic handoff just because an evicted target is missing, and no broad `has pending row for video` that uses capacity A to drop independent unfinished B. These paths may still hand off independently eligible ordinary work; none modifies old evidence or silently releases guards.
- **Pending BR-037 scan/confirm and batch claim:** ARS-005 must count live capacity rows as active without claiming evicted history. An evicted-only missing add is not evidence of stranded work and is not counted as user removal; guard blocking and committed deferred/failed exclusions keep their existing priority. Preview and confirm/transactional insert use the same scope-aware eligibility checks; shared action admission still suppresses evicted targets even if a valid independent source is requeued. The control is local, never checks room, and never turns a capacity error into BR-037 `unavailable_on_youtube`. Preserve the existing requirement for paged Deferred and for guarded batch processing/readiness. BR-037 can ship separately before capacity produces rows, or together with these predicates; a later BR-037 implementation on a capacity-capable schema cannot omit them.
- **Simulation and inspection:** No production count, claim, eviction, insert, guard change, retry inference or production-capacity disposition. Preserve simulation-only results and existing metadata/date semantics.

## Recovery, inspection and compatibility

- **Before admission:** No network effect is authorized by a prepared guard or a queue claim. A crash with a prepared guard but without durable conclusive proof leaves the guard veto intact; no reconstructed receipt can release it. **After admission:** Preserve accounting and any known attempt result through the existing receiving-run resolution boundary. Failure/unknown commit of handoff gives no acknowledgement, fresh work or permission to re-send. Reconcile committed work only by matching exact rows and requested-run evidence. If eviction/removal won after admission and a refusal has no live authorized sink, retain the guard under OC-007 and record the actual admitted refusal as available; do not claim that it was retained as deferred, resurrect an entry or touch terminal history. If storage/lifecycle prevents confirmation, report the independent local failure. A failure sweep cannot override this boundary.
- **Projection:** Use the requested run's existing action and `continued_actions` paths, with the exact target and recorded attempt time (null for positively unissued). A validated `deferred / playlist_full` row has exactly two producer paths: the confirmed no-send path writes null; the confirmed admitted refusal path writes its receipt's time. Those invariants let the consumer distinguish the branches without inferring a result from an arbitrary or missing timestamp in other rows. Register `playlist_full` in action, video and queue reason fields, `capacity_evicted` only for queue closure/history, and `capacity_evidence_unavailable` as a bounded diagnostic code with no optional raw detail. Existing `playlists_list`/`playlist_items_insert` operation registrations and the provider reason allow-list do not grant send authority. Update writers, storage guards, readers, events and SPA together. `ActionsExecuted` counts the newly recognized **attempted** capacity deferral as one, not a success or `ActionsFailed`; keep other existing historical/legacy classification and don't count reads, evictions, no attempts or simulations. Do not infer an attempt solely from arbitrary timestamp presence or a provider error code.
- **Queue reads:** Extend `GET /api/deferred` with `reason=playlist_full` for current work and a separately paged selection for eviction history (use `include=evicted`, with its own count and cursors).
