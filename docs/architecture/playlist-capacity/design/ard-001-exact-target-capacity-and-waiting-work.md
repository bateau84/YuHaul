Check the destination playlist before each otherwise eligible production add. If Study is full and Lofi has room, the run defers the Study add, can still add to Lofi, and shows both results. A later run rechecks Study and, if eligible, sends only the missing add under the decision that authorized it. If the Study waiting list already has 5,000 distinct videos, the next distinct enrollment displaces its oldest entry. That entry remains visible in history but no later automatic path can revive it.

If Study's add was evicted and a later run adds the video to Lofi, that run records Lofi's success under the original decision and classifies the video **deferred** with reason `missing_add_removed`. Its inspection shows both facts: added to Lofi, and the Study add was removed from the queue and won't be retried automatically. The run sends nothing to Study, checks no room for it, creates no queue item, and the video is never accepted or final.

The two 5,000 limits are independent: one is the product threshold for items on YouTube; the other bounds active local waiting work **per actual playlist**. No space is reserved on YouTube. The read is an observation, not a guarantee about concurrent edits or provider consistency. A refusal or lost result does not authorize a second POST.

## Decision and alternatives

- **Provider count:** Use `playlists.list` by exact `id` with the documented `contentDetails.itemCount`. An unfiltered `playlistItems.list` for the exact `playlistId` documents `pageInfo.totalResults` as the result-set size, not a separate target capacity field. Counting all item pages at 50 per page costs about 100 units at the threshold and is not a point-in-time snapshot. Neither pagination nor a video-filtered membership check is a fallback for a failed or insufficient count. A POST used as a probe would violate BR-040.
- **Local space accounting:** Reuse the production execution gate and a short-lived per-target observation in that run's execution pass. Maintain local consumption against it and fail closed on missing evidence. Reading once per add is simpler but repeats valid reads and does not by itself protect against an unresolved prior send or a stale response. A cross-run count cache or mirrored inventory would add sync, expiry, restart and reconciliation work without supplying a YouTube reservation or stronger provider evidence.
- **Waiting work:** Extend the existing SQLite Deferred Queue with a target-scoped row form and keep evictions as terminal history of those rows. A separate capacity table with a union reader can also model the two scopes, but would have to duplicate row identity, history, removal and retry/recovery machinery or add a second ID namespace; it does not eliminate the common admission fence. A reason-only column change with video-wide disposition cannot enforce exact-target ownership, the cap or non-resurrection.
- **Scope:** Keep the existing production gate and credential/quota admission. Add a short local ownership fence because queue/lifecycle writes can overlap dispatch preparation; never hold it across provider I/O. No worker, polling schedule, distributed lock, provider delete, manual restore/guard clear, or broad replay or backfill. Revisit coordination only if concurrent mutation writers replace the current single-process execution model.

## Provider evidence and send admission

**Count:** Under the same captured authorization binding as the add, request `GET /youtube/v3/playlists` with one exact `id`, `part=contentDetails` and a partial response containing `items(id,contentDetails(itemCount))` and `nextPageToken`. [The list method](https://developers.google.com/youtube/v3/docs/playlists/list) defines the exact ID filter; [the resource](https://developers.google.com/youtube/v3/docs/playlists#contentDetails.itemCount) defines `itemCount` as the number of videos in the playlist. Accept only a complete successful response with one matching resource and a present unsigned integer count, distinguish explicit zero from missing/null, and reject unexpected pagination, duplicate or mismatched IDs, malformed or incomplete responses and unconfirmed read accounting. No title, picker result, subscriptions/uploads ID, local action total or HTTP cache hit from an earlier pass supplies this fact. A read error keeps its own quota, authorization, temporary or failure meaning; a missing resource is neither empty/full nor a missing **video**.

**Spend:** The serialized mutation owner maintains an observation scoped to exact playlist ID, captured binding and one live execution pass. New run, resume/restart, authority replacement or loss of observation requires a new authorized read; do not restore a cached slot. Within the pass debit one at local add admission, retain it on success or unknown application, and restore it only on positively known non-admission/non-application. A definite full refusal invalidates prior room and establishes fullness for this target in the pass, not a future retry. A result for a different video/route targeting the same playlist uses that same local allowance. Only observations still within a short freshness window, bounded by the live pass, can authorize a send. Use 60 seconds from the successful provider observation as an initial technical maximum, not a provider freshness guarantee or a public setting; recheck at admission. An ordinary eligible add may demand a fresh read after expiry. No timer refresh, immediate recheck of the same full add or extra read simply because another eligible video shares its still-usable observation.

**Across observations and restart: trust the count (BR-040 AC1, amended 2026-11-22 by user decision).** A count YuHaul received after it received the response of a recorded successful add covers that success. The success is treated as already included and is not counted again. Realization: when the count GET is admitted, under the lifecycle gate and the SQLite writer, snapshot the videos with a committed production success for that playlist. Each was committed after its response arrived, and the GET is sent only after the snapshot, so the count was received after those responses. A success recorded later is not covered. An unresolved send guard is never covered by any count. Do not make extra probe calls to try to infer coverage.

Start both bounds at the usable reported count. Count each other possible add once, by first match:

- confirmed adds admitted in this pass after the observation was received count in both bounds;
- adds admitted after it with no result yet, or with unknown application, count only in the upper bound;
- covered successes count in neither;
- other successes and other unresolved guards count only in the upper bound.

The invocation's own guard is excluded, because it is the add being decided. Do not clear an allowance when a successful insert's guard is removed; its success row now supplies the evidence. Existing legacy and exact-target mutation vetoes remain independent.

With arithmetic capped at 5,000: full if the lower bound reaches 5,000, room if the upper bound is below 5,000, and insufficient evidence otherwise. These are bounds for applying the observation, not a live guarantee against external edits. Examples:

- A usable 4,999 with no history gives room for one add. That confirmed add then projects full on the same observation.
- A later count that includes the add covers it, so the add is not counted twice.
- A usable 4,998 plus one unresolved guard gives room for one guarded add.
- A raw 5,000 proves full.

If the count itself is known stale or contradictory, do not use it for either conclusion. [ARS-001 §4.2](../specifications/ars-001-capacity-schema-queue-and-send-path.md) is the exact rule.

**Backstop when the count lags.** YouTube's count may not yet include an add it already confirmed. YuHaul can then send while the playlist is actually full. The user accepted that YouTube's documented `403 playlistContainsMaximumNumberOfVideos` refusal is then the backstop. It is one attempted add (50 units) with truthful playlist-full evidence, the add waits under BR-041, and nothing is replayed. YouTube enforces its limit, so a playlist never exceeds 5,000. The earlier "never covered" alternative is withdrawn: critic `ses_dff707369ffe3UAV2Ns6K4abw0` (finding 4) showed it would stop YuHaul's adds at about 2,499 per playlist.

**Fence:** Only a production mutation-authority path may start an add. Check final video, exact decision/target scope, matched snapshot authority, known success, legacy and independent guard vetoes before using capacity as a disposition; reject stale authority without relabeling it full. Avoid a guard on a proved full/no-send path where possible; if prepared, clear only the current invocation's positively unissued guard in the retention transaction. On the room path keep the [existing guard contract](../../youtube-authorization/specifications/ars-001-authorization-state-dispatch-and-send-guard.md): commit the exact guard before admission. After any renewal and immediately before irreversible local call admission, revalidate the unchanged guard, exact live work receipt or proven fresh work, target suppression, production run and stop marker, finality and local room. Neither a prepared guard nor a preflight read is the fence. Use a short process-local gate shared by this validation/admission and all writes that can invalidate it (including exact Dismiss, eviction, ownership transfer, terminal/final writes and the durable Stop marker). Verify writes share the gate or are already serialized by the production gate; do not rely on eventual context cancellation after Stop's marker.

The gate spans the final local check and commitment of the quota hold to an admitted attempt, not OAuth renewal, `RoundTrip`, response parsing, or outcome accounting. Acquire it before auth/ledger/SQLite work in this local admission segment; acquire it before the writer on invalidating paths, and never acquire the gate or quota/auth locks from an existing writer transaction. Do not perform SQL in the ledger's pure `AdmitIf` validator; use transaction-consistent local checks under the outer gate and use the final validator for expiry, freshness and other already-captured facts. No auth/quota/SQLite lock spans a network call. If the invalidating write wins, there is no admission, no POST and no resurrection. If admission wins, stop/removal/eviction can affect future authority but does not recall the admitted operation. The existing single-attempt transport and accounting ownership remain binding.

**Fence both capacity GETs:** The initial count GET and the one permitted credential-recovery GET must each enter that same lifecycle gate afresh, after any renewal and before admitting their own one-unit hold. Check the receiving production run, no committed Stop marker and no lifecycle/ownership loss under the gate, alongside normal authorization and quota checks. `StopRun` takes the gate before its run-control mutex and durable marker write; no caller holding the run-control mutex may acquire the gate. Cancellation arriving after the marker is not the fence. If Stop wins, cancel any provisional hold: no GET and no debit. If admission wins, account that attempt once; Stop can still veto the recovery GET or POST, and the late count cannot grant another call. Release the gate before transport; no lock spans OAuth exchange, response handling or accounting. This obligation covers both new capacity read admissions, not a claim about existing read callers.

**Live-status gate (BR-042, amended 2026-11-19):** [Live ARS-001](../../live-status/specifications/ars-001-live-status-read-classification-and-deferral.md) §6.1 and §7. The live check comes before every capacity step (BR-042 AC13).

- Before the first count GET for a claimed capacity row's video, the planner calls `liveGateClaimed` with a `Live`-only requirement. If the receiving run's recorded status is not `none`, the result is `liveSkip` with the receipt:
  - no GET and no POST;
  - no room check, enrollment, eviction or change to the cap count;
  - the capacity row is released to `pending` unchanged (same ID, enrollment, age and owner history).
- A live video that is not confirmed is never admitted to a waiting list.
- The final POST admission fence checks `LiveClearedTx(sending run, video)` alongside the checks above. A refusal there is the live deferral of authorization ARS-001 (*Live-status clearance at the send*), not a capacity disposition.

**Admitted full refusal:** [YouTube's `playlistItems.insert` error table](https://developers.google.com/youtube/v3/docs/playlistItems/insert#errors) and [error catalog](https://developers.google.com/youtube/v3/docs/errors#playlistItems_insert) specify `403 playlistContainsMaximumNumberOfVideos` for this insert because the playlist **already** contains the maximum allowed number of items. [HTTP 403](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.4) means the server understood the request and refuses to fulfill it. Together these support the documented method-specific refusal of this insert on a preexisting capacity condition, not a generic claim of rollback on a 4xx. Recognize only the trusted, complete, unambiguous error response from the single admitted POST whose claim/receipt and sent video and playlist exactly match: actual 403, one fully parsed provider reason equal to `playlistContainsMaximumNumberOfVideos`, no competing reasons, malformed, duplicate or contradictory evidence fields, redirects, or transport/body-read failures. The adapter produces the private `not_applied` capacity fact; a diagnostic enum, exported error value, status, substring or later count is not evidence for guard release. If the provider semantics or attributable response shape do not hold, keep the branch uncertain; a fixture cannot make an undocumented shape conclusive. The method's documented maximum need not equal a returned count; a genuine refusal suffices on its own.

## Disposition and accounting

| Fact | Required effect |
|---|---|
| Known full, positively no POST | Current target `deferred / playlist_full`, no add attempt/time/insert charge; enroll or retain this target and continue eligible siblings. The count request remains a real read. |
| Exact admitted full refusal, waiting entry live or not yet created | Same target deferral with actual admission time, one attempted add and one 50-unit insert debit with existing ledger category `permanent` (the provider response category, not the application's retry disposition). Clear only the live owned guard, atomically with the capacity handoff. No immediate repeat. |
| Exact admitted full refusal, waiting entry already evicted or dismissed (R3; OC-007 G2 and BR-040 AC3, amended 2026-11-22) | Record the add as attempted and **not added** because the playlist was full (`failed / playlist_full`, with its admission time), and release the owned guard with that committed result. One attempted add and 50 units, as above. No waiting entry, replacement, eviction or retry; the pair stays suppressed. It is not a deferral and not an independent action failure: the video's outcome follows the removed-add aggregate below. Anything short of a definite refusal keeps the guard (OC-007 G3). |
| Provider `quotaExceeded` on a count GET or an insert | The existing typed quota refusal, never a capacity fact. PR #9 on `main` (`f6ce39b`, [quota-stop ARS-001](../../quota-stop/specifications/ars-001-provider-quota-stop-pacific-reset.md)) records it at 1 unit, and the ledger then refuses every later admission for that run in the same Pacific quota day. Capacity GETs and POSTs go through the same `Acquire`, so they are covered by that stop with no extra check. Waiting capacity rows are released unchanged. |
| Count cannot establish room | No POST, do not enroll new work as full on that basis. An add already waiting keeps waiting at its original age (`deferred / playlist_full`). A first-time add takes the existing failure retention with the bounded `capacity_evidence_unavailable` diagnostic, not a second capacity reason ([ARS-001 §4.6](../specifications/ars-001-capacity-schema-queue-and-send-path.md)). Quota, authorization and temporary read failures keep their own policies. |
| Admitted application unknown | Preserve actual attempt evidence and independent durable guard; use existing uncertainty and failure retention. Do not create evictable capacity work as substitute. If the target already had an authorized capacity wait, preserve its enrollment separately; it cannot send while guarded, and later eviction cannot remove the uncertainty or its independent protection. |
| Known success | Record actual success under the sending run and authorizing decision; settle only the authorized live target. If evicted or dismissed after admission, do not change that history; the real success is independent evidence and still vetoes all repeats. |

Each admitted count GET is 1 unit (including any allowed read retry as a separate call); each admitted insert is 50. A call refused by YouTube for quota is recorded at 1 unit (PR #9). Quota days run from midnight Pacific (PR #9); a hold that crosses the reset is refused before admission, and a count's freshness does not depend on the quota day. Sources: [YouTube quota costs](https://developers.google.com/youtube/v3/determine_quota_cost) and [authorization ADR-004](../../youtube-authorization/decisions/adr-004-atomic-quota-admission-and-single-attempt-transport.md). The single read adapter owns `playlists_list` accounting; the guarded insert owner finalizes its one `playlist_items_insert` hold, including transport errors, before any rejection observer. No recorder on the side, debit for a refused admission, reserved budget or special quota pool. An uncached check plus insertion normally costs 51 units; known-full checks use the read cost only. Do not perform a whole-video 50-units-per-target reservation or let known-full targets inflate the remaining send estimate. Use existing quota precedence for due work and per-operation admission, with costs for required reads in preflight estimates when relevant; actual admission remains authoritative. A capacity wait is not permission to retry repeatedly in the same pass. Each eligible target gets a bounded consideration per ordinary pass; later eligible work is not starved solely because a preceding target remains full.

Failure to record a real call remains a separate accounting failure, not new room, failed application, erased success or permission to resend. Preserve conservative held cost and the existing run-failure reporting without overwriting a committed primary disposition. Existing crash-complete accounting limits still apply; neither this design nor the send guard is a new transactional quota journal.

## Durable target work and continuation

**Store and identity:** In the existing `deferred_item` namespace, distinguish legacy video-scoped rows from `playlist_full` rows with required exact case-sensitive YouTube playlist ID and authorizing `route_decision` ID. The decision's run is derived from that decision, not from the waiting row's enrollment run or the current receiver. Preserve the row ID, origin run (the enrollment run), original reason, creation time and most-recent retry owner. Keep a separate `evicted` terminal queue status and eviction time. The status is the closed reason, so no `closed_reason` value is added; neither user removal (`discarded`) nor processing completion (`completed`) is eviction. Storage refuses to move a row out of `evicted`, to change a capacity row's target, decision, video, origin or creation time, and to insert an active capacity row for a pair that has eviction history. These are the durable form of non-resurrection, not only writer discipline. Legacy rows require no target backfill. Active means pending **or retrying**. Enforce active uniqueness on `(target playlist ID, video ID)`, and index exact pair history and the active oldest-for-playlist lookup. Use monotonically allocated queue ID as settled enrollment order; wall-clock adjustment or tied timestamps cannot rearrange it. The queue cap is enforced by the common writer, not count-then-insert in separate transactions.

**Video-scoped uniqueness (BR-042, amended 2026-11-19):** The one-active-row guard for **video-scoped** (non-capacity) rows ignores capacity rows. A live skip therefore always leaves exactly one active video-scoped item, even when the claimed receipt owns only capacity rows. A later eviction of a capacity row can never leave the video with no active item ([Live ARS-001](../../live-status/specifications/ars-001-live-status-read-classification-and-deferral.md) §6.1 step 5). Capacity rows never carry `live_hold`, and they never count as the live sink.

**Atomic transition:** Under `WithRetryTx` validate production ownership, required target and saved decision, and existing success, removal and guard boundaries. Repeated evidence for an existing eligible pair keeps its original row/authority and age, and never triggers eviction. For a new distinct eligible pair at 5,000, transition only the oldest active row of that playlist to evicted; retain its origin/owner and record the time, then insert the new row. Commit that transition, exact source or target handoff, requested-run target evidence, and any permitted owned guard release together. A stale evicted/dismissed receipt cannot authorize a replacement, a no-op insert is not a valid sink, and an unrelated live sibling cannot substitute. Index and writer rules apply to all activation paths, not only insert. Preserve old rows and attempts. No deletion, revival of evicted history, or reinterpretation of `evicted` as a success or an explicit dismissal.

**Claim versus authority:** Keep video-group arbitration and once-per-video processing/membership. Capacity rows are ordinary members of the exact retry receipt that is now on `main` ([authorization ARS-001](../../youtube-authorization/specifications/ars-001-authorization-state-dispatch-and-send-guard.md#exact-retry-ownership-receipt), stored by migration `031` as [run-initiation ARS-005 §5.1.1](../../run-initiation/specifications/ars-005-requeue-stranded-videos.md#511-durable-retry-claim-provenance) provenance version 1). The receipt keeps its `{id, origin_run_id}` members unchanged; no provenance version 2. The discriminator, exact target and decision are immutable columns of the referenced row, which the existing writer-time validator already re-reads by ID. Storage enforces their immutability, so the copy in the row is as trustworthy as a copy in the receipt and needs no second store. An `evicted` member is terminal, like `completed`; it is never a live retention path. Capture under writer after claim, use only after commit, reload durable queue ownership on resume without recreating any live send receipt. A capacity-only receipt (even before the first success) can execute only its live captured targets against their frozen decision. `DecisionRunID` still needs the validated matched production snapshot, nonfinal sender, existing legacy/success vetoes and unique original decision when partly done; replace the current video-wide “has any retry row” condition for capacity sends with exact target ownership. If a necessary snapshot, decision or authority is missing/inconsistent, retain with the existing safe authority-failure reason; do not re-evaluate to guess a target. A valid source for A cannot authorize B. A manual retry of an active capacity row, if exposed, scopes to that item; existing video-wide manual Retry must not be used as a target control. Dismiss, if exposed for capacity, uses the exact existing row ID and never discards siblings.

**Mixed work:** Keep the remaining actions of a decision independent of capacity rows. A whole-video retry receipt grants only its independently eligible ordinary work, not ownership of a capacity row. The decision/action planner partitions required targets into recorded successes, held/evicted targets, live owned capacity targets, uncertain targets and ordinary remaining work. The same target held elsewhere, evicted, or dismissed from its capacity row cannot be redispatched through an ordinary sibling, the discovery/main action loop or recovery. Check suppression by exact pair, not by “latest queue row” and not by excluding every target of that video. Whole-video work continues under its existing rules, but cannot replace the captured capacity decision, finalize a video while a required add is still missing, or turn an evicted-only obligation into a new decision. For a partly done video use the original decision for all its remaining work. For ordinary residual actions from the **same** already-evaluated decision, the derived decision pin (below) makes remaining work derivable after restart from the decision's exact targets, action evidence and scoped dispositions. Do not send those actions from a different decision simply because no success exists yet. Do not create a second inventory of done targets. A genuinely independent pre-evaluation source remains governed by its existing rules and cannot supply contradictory authority for a pinned action. If persisted decision authorities for a video conflict, retain the affected work as unreadable/inconsistent authority, not guesses at new targets. Settle each ordinary source only against its own residual outcome; a capacity-only handoff never acknowledges the entire group. Release rechecked full capacity claims back to pending without changing enrollment, and leave the pending sink outside broad acknowledgement. A separate quota/auth/temp problem does not transfer or de-age that capacity waiting row. The waiting cap counts the distinct rows in that form only, not the ordinary siblings.

**Complete the video after the targets:** Record actual per-target evidence, receiving-run membership and durable retention as each target settles, not an unconditional video-finalization transition in the capacity callback. If the process dies after that commit and before the aggregate result, the run/decision and exact action/queue records are the checkpoint: honor settled targets, resume only authorized unsettled work, and still produce the single aggregate disposition when allowed. Recovery must enumerate that incomplete receiving-run membership even when every capacity claim is now pending or terminal and no live retry row remains; this grants settlement, not dispatch. A returned-pending or later-evicted row is never a new live claim of the interrupted invocation. When the pass finishes, the pipeline commits the single requested-run/global video disposition under existing outcome rules and the exact remaining ordinary handoffs. Capacity by itself gives `deferred / playlist_full`; independent uncertainty/failure and stopping conditions retain their existing classifications and evidence. Do not publish an interim final or count the video twice. An original required target that is evicted remains missing. Eviction does not write a new video outcome or assert current fullness; if a later pass resolves separate work, do not turn an earlier nonfinal result into accepted merely because every still-active target has succeeded. Reconcile success or a committed deferral by its exact receiving-run evidence on resume: no same-run repeat after a handled capacity result. Preserve earlier results and attempts on save failure or later re-entry.

**Pinned authority for ordinary sibling B:** When the same saved decision has a capacity target A and remaining ordinary work for B, B runs under that decision, even if neither target has succeeded (BR-041 AC4 and AC7). The decision is **derived**, not stored again on B's row. A video is *decision-pinned* when it has a production success or any capacity row in any status. Its pinned decision run is the single run among the decision runs of its production successes and of its capacity rows. More than one such run is inconsistent authority: retain with the existing safe authority-failure reason and send nothing. This extends BR-039's original-decision lookup ([ARS-006](../../run-initiation/specifications/ars-006-final-outcomes-are-never-reprocessed.md) §2 `OriginalDecisionTx`) from successes to successes plus capacity rows. A pinned video goes through original-decision continuation, never fresh evaluation, and the main-loop filter `RoutableByRun` drops it for any run other than its decision run, so rediscovery cannot re-route it.

B's own live receipt row (an ordinary Deferred or Errors member, any reason) supplies send permission for the **ordinary** remaining targets. Those are the pinned decision's targets minus recorded successes and minus every target that has a capacity row in any status. A capacity row supplies permission only for its own exact target. So A's row cannot authorize B, B's row cannot authorize A, and an evicted or dismissed A is never sent through B. B does not count toward the cap. In the state writer, before guard preparation and again at final POST admission, the cross-run decision check accepts the pinned run when either a production success or a capacity row of the video names it, and no success or capacity row names a different run. All existing finality, success, legacy, guard, Stop and live-clearance vetoes still apply. A caller-supplied decision ID or current configuration cannot replace the derived one. A transfer of B to capacity waiting, if B itself is proved full, validates B's own receipt and establishes its exact sink before acknowledging the source. Restart reconstructs B's queue ownership, never a live mutation receipt.

*Why derived:* the earlier draft persisted B's target and decision on B's ordinary row. That needs new columns on both `deferred_item` and `error_entry` and a second copy of a fact that capacity rows already hold immutably. The derived pin gives the same authority, and it also stops rediscovery from re-routing an evicted-only video. Revisit if a capacity row can ever be created under a decision run that differs from the video's existing pin; the enrollment writer refuses that today.

**Receiving run after a removed add (BR-041 AC7: eviction decided 2026-11-19, Loom answer `fb9c7283`; Dismiss and the derived cases decided 2026-11-22).** A *removed* add is one whose capacity row was evicted, or dismissed by the user. Both suppress the add for good, and queue inspection keeps them apart.

*When it applies.* At the end of a production run's pass over a decision-pinned video, classify each required target of the pinned decision. The required targets are the `playlist_insert` targets of its matched routes in the decision's production snapshot.

| Target state | Meaning |
|---|---|
| `succeeded` | A production success exists for this video and target. |
| `removed` | No success; the target's capacity row was evicted or dismissed; no unresolved send guard for this video and target. An R3 target is `removed` once its guard is released. |
| anything else | Active capacity waiting, a guard or uncertainty, a failure, a quota/auth/rate/live deferral, or not reached. |

If every target is `succeeded` or `removed` and at least one is `removed`, the run commits the **removed-add aggregate**. This covers the requirement's derived cases: the other adds succeeded in this run, or in earlier runs, or no add succeeded at all. If any target is in "anything else", the existing classification and precedence decide, **over the targets that are not `removed` only**. A removed target, including an R3 `failed / playlist_full` row, is never an input to that classification: it is not an action failure, writes no `prior_action_failed` and creates no Errors entry. So if A got R3 and B is proved full, the video is `deferred / playlist_full`. AC7 never overrides capacity waiting, uncertainty, failure, live, quota or authorization results of the other targets. If all targets succeeded, the existing accepted result applies.

*The removed-add aggregate.* One writer transaction:

1. validate the live receipt by the existing writer rules;
2. for each `removed` target without a row for this run, write one `executed_action` with outcome `not_attempted`, reason `capacity_evicted` or `capacity_dismissed`, no `executed_at`, and the pinned decision's route decision. This is run-scoped evidence for the explanation. It is not a capacity read, playlist-full finding, capacity deferral, attempt or failure;
3. set the run video and the global video to `deferred` with reason `missing_add_removed`;
4. acknowledge the receipt by completing owned video-scoped Deferred rows and resolving owned Errors rows. Create **no** sink. Leave the removed rows unchanged.

Any success is the one recorded when it settled, under the original decision. Nothing rewrites it. The video then has no active queue item. It is not final, it is not stranded, and no rule retries the removed add. The explanation comes from this run's rows. It never says this run added B unless this run recorded B's success. `ActionsExecuted` and `ActionsFailed` do not count the `capacity_evicted` or `capacity_dismissed` row. The run makes no capacity read for a `removed` target, because the planner drops it before any count GET.

*A removed add that no run processes.* If the row is evicted or dismissed while no run holds it, and nothing else is left for the video, no run claims the video again. Its last committed outcome stays, and the queue's eviction or Dismiss history is the visible new fact (BR-041 AC7, derived case 3).

*Other entry points apply the same aggregate.* Stop, run Discard, the run-failure sweep and startup recovery settle a member whose targets are all `succeeded` or `removed` with the same local transaction, instead of handing it off. This needs no provider call. Without it, a Stop between B's success and the aggregate would create a `stopped_by_user` item that exists only to rediscover A's removal. A later run never sees the video again: it has no active item, and `RoutableByRun` drops pinned videos.

*Removal while claimed.* If A's capacity row is evicted or dismissed while this run holds it, the fence refuses A before admission, as BR-041 AC5 requires. The refusal is a typed per-target result (`evicted` or `dismissed`), not `ErrWorkRemoved`. Dismiss of a capacity row removes only that add (BR-041 AC7), so it never ends the run as user removal and never produces `retry_work_removed`. The invocation proves non-admission, so it releases only its own positively unissued guard and records `not_attempted / capacity_evicted` or `capacity_dismissed`, through the same detached owned resolution as the Stop path. A guard kept here would be false uncertainty. If A's POST was admitted before the removal committed, its actual result stands: success, R3 for a definite full refusal, or uncertainty.

*Dismiss on capacity rows.* The Deferred view's Dismiss (`POST /api/deferred/{id}/discard`) is allowed on a live capacity row. It removes only that video-and-playlist add; the video's other rows stay. Re-queue ignores capacity rows when deciding whether the user removed a video's work, so the video's other stranded work can still be re-queued. [ARS-001 §5.3](../specifications/ars-001-capacity-schema-queue-and-send-path.md) gives the exact contract.

**Other entry points:**

- **Stop, discard and run-failure sweep:** Release or retain the exact outstanding capacity claims, with age and scope intact; do not make room checks unnecessary. No generic handoff just because a removed target is missing, and no broad `has pending row for video` that uses capacity A to drop independent unfinished B. A member whose targets are all `succeeded` or `removed` gets the removed-add aggregate locally instead of a handoff (above). A dismissed capacity row does not mark the video's work as removed by the user. These paths may still hand off independently eligible ordinary work; none modifies old evidence or silently releases guards. The receipt-aware handoff of [ARS-003 §2.1](../../run-initiation/specifications/ars-003-stop-run-and-deferred-handoff.md#21-claim-ownership) and the [ordinary retry failure transaction](../../youtube-authorization/specifications/ars-001-authorization-state-dispatch-and-send-guard.md#ordinary-retry-failure-transaction) treat an evicted or dismissed capacity member as terminal: never requeued, never a sink, never counted as user removal of the video.
- **BR-037 scan/confirm and batch claim ([ARS-005](../../run-initiation/specifications/ars-005-requeue-stranded-videos.md) as built):** One predicate change: `RemovedByUser` keeps capacity rows in its recency ordering but counts a discard as user removal only for a video-scoped row, so a dismissed capacity row does not hide the video's other stranded work (BR-041 AC7: Dismiss removes only that add). Video search uses the same predicate and so stops showing a capacity-row Dismiss as "removed by user". `ActiveQueueItem` already counts every `pending` or `retrying` row, so live capacity rows are active and their videos are `already_queued`. `evicted` is neither active nor `discarded`, so `RemovedByUser` never counts eviction. An evicted-only add does not make a video stranded: a video in the evicted-add state has a committed `deferred` outcome, so the scan's `unfinished` set excludes it, and it appears only in `retained_without_queue_item`, which BR-037 AC4 defines as counted, never re-queued. Guard blocking keeps its priority. A re-queued video (some other unfinished video with eviction history) gets a video-scoped row; the pinned-decision rule and exact-pair suppression still refuse its evicted target. The control is local, never checks room, and never turns a capacity error into BR-037 `unavailable_on_youtube`. `InsertRequeuedTx` writes only video-scoped rows.
- **BR-042 live holds ([Live ARS-001](../../live-status/specifications/ars-001-live-status-read-classification-and-deferral.md) §6.1, §6.3):** The live gate runs before the target partition, so a live, upcoming or unconfirmed video takes `liveSkip` and the AC7 aggregate is not reached in that run. `liveSkip` keeps capacity rows unchanged and leaves eviction history untouched. Eviction never touches `live_hold`, which lives only on video-scoped rows. Hold clearing happens in the transaction that starts continuation, before the aggregate can run. After the aggregate, the video has no active item, so the BR-042 AC7 check window has nothing to check.
- **Simulation and inspection:** No production count, claim, eviction, insert, guard change, retry inference or production-capacity disposition. Preserve simulation-only results and existing metadata/date semantics.
