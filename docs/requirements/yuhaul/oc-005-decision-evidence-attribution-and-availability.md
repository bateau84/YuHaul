**Status:** accepted clarification of cited obligations and delegated ordinary specification detail; long-term evidence/expiry conflict remains unresolved below. Not implementation acceptance.
**Priority:** MUST

The user must be able to identify the video and understand the recorded cause. For example, a route exclusion should identify the exclusion that actually matched, not just say that some exclusion matched. An old record containing only a generic skip must say that its specific rule is unavailable. Displaying that limitation is truthful, but does not make the missing explanation complete.

## Participants

- **Evaluation evidence producer:** determines and records the actual route/exclusion/condition/action path.
- **History custodian:** preserves attributable run evidence and enforces the applicable data lifecycle.
- **Inspection provider and consumer:** make the same run/video evidence available in the video list and decision detail, including safe context and honest availability.

These are responsibilities, not selected services, tables, endpoints or interfaces.

## Preconditions

- A user inspects a specified run and video, including a backtest, replay or dry-run.
- A recorded fact can be presented as such only when retained evidence supports its attribution. No precondition assumes that legacy records are complete or that metadata is available.
- Existing outcome, route identity, configuration snapshot, simulation isolation and diagnostic safety obligations remain in force.

## Guarantees

### 1. Identity and display context

1. Inspection SHALL expose permitted locally available video title, source-channel display name and duration when known, with the video/channel identifiers remaining identifiable as identifiers. Missing title/name/duration SHALL be explicit; an ID, hash, empty string or unexplained dash is not a title/name or proof of a duration. Known zero duration and missing duration remain distinct. No additional subscription identity or name is inferred from a channel association.
2. **Display context** means metadata available at inspection time, not necessarily metadata evaluated by the selected run. **Evaluated input** means the value actually used in that run's comparison, supported by captured evidence. Display context lacking that historical attribution SHALL be identified as current/local display information, not historical input. A known observation/fetch time may be shown; unknown times are not invented. Publicly accessible YouTube metadata is still provider data, not permission for indefinite retention or unrestricted release.
3. Current title/channel/route/playlist names may help recognition, but SHALL NOT rewrite the captured decision or be presented as historical labels without historical support. A run snapshot can establish configured route identity/name and predicates; today's mutable configuration cannot establish what was evaluated. IDs remain usable when a historical label is missing. Playlist display names are not newly required by this contract.

### 2. Specific causal evidence

4. For an exclusion that actually prevents a route's evaluation, the producer SHALL retain attributable evidence identifying the route/scope and the particular exclusion predicate that caused the skip: field/type, comparison meaning, configured value or threshold, and match result. An identity is sufficient only if it resolves unambiguously to the unchanged predicate used then. Safe permitted compared input SHALL be available as evaluated input; absence or withholding is explicit, never a fabricated empty or zero value. This does not grant permission to retain restricted raw input beyond its authorized lifecycle; the unresolved reproduction obligation below still applies.
5. Where several exclusions match, identifying the causal match used to skip is sufficient; enumeration of every possible match or changing evaluation order is not required. This specification choice bounds explanation without changing matching behavior. A generic `exclusion` reason or a list of all configured exclusions does not identify which predicate caused the skip. Historical recomputation SHALL NOT be represented as a captured match.

   For every newly evaluated exclusion skip in production and simulation, **causal match** means the first exclusion occurrence whose actual match caused that route to stop before condition evaluation, in the unchanged configuration used by the selected run. Preserve occurrence identity even when two configured entries have identical type/value. No new type priority is imposed. Identity, route scope and recorded match SHALL belong to the same durable decision; a successful generic-only new skip followed by later enrichment is not conformance. A capture/persistence failure follows existing failure handling and SHALL NOT be reported as successfully retained precise evidence. Reuse of an existing decision preserves its original evidence rather than enriching a generic legacy row from a new evaluation.

   The explanation SHALL state that the recorded comparison matched and prevented this route's condition evaluation, identify the configured field/type and comparison as used then, and show its permitted configured value/threshold. For example, “title contains configured phrase ‘live’” states a substring comparison, not whole-word matching; a strict duration maximum comparison does not become greater-than-or-equal in the explanation. This clause preserves the comparison actually used; it does not select or change matcher semantics. The recorded branch is evidence of which rule was causal, not an independent reproduction of the original comparison. If historical input is supported and permitted, show it as evaluated input under Guarantee 4. Otherwise state that compared input is unavailable; do not substitute current/local metadata, another route's condition audit, an empty value or zero. Withholding a configured value leaves a valid captured identity/type/comparison inspectable and explicitly marks the value unavailable; it does not mean no rule was captured.
6. For evaluated conditions, inspection SHALL expose the recorded field, comparison, configured expected value, actual value when permitted and retained, and match/non-match result in their recorded route order. Explain route acceptance/non-match using the run's supported composition, not “no condition matched” when an AND route had a passing condition. Distinguish exclusion, disabled/final-route skip, condition non-match and evaluation failure. An excluded route's unevaluated conditions are not failed conditions; empty condition evidence alone proves neither that no conditions existed nor that all failed.
7. A route-scoped exclusion SHALL NOT be used to claim that the whole video was excluded from every route. List summaries and detail SHALL preserve the recorded video outcome separately from its route/condition/action evidence and its coverage limits. If one route is excluded and another matches, the exclusion is not a whole-video rejection. Incomplete route evidence cannot justify an all-routes causal claim beyond the recorded outcome category. Duplicate status remains supporting provenance, not a replacement outcome or cause.

### 3. Availability, safety and mode

8. List and detail SHALL refer to the same requested run/video and SHALL NOT contradict each other's outcome, mode or evidence attribution. A concise list summary may omit detail, not invent a more specific cause. Display context may change or expire between reads; that may change recognition information, not recorded run evidence. A difference with historical input is identified, not silently reconciled. This does not require atomic reads across pages.

   Whenever either surface presents an exclusion skip, it SHALL include its route-scoped exclusion reason and specific causal-rule identity when supported, or explicitly state that the specific rule is unavailable. A list may abbreviate comparison detail, but SHALL NOT replace an available causal identity with only a generic skip or require opening detail to discover which rule caused it. Neither surface may use a different route's non-match to explain this route's skip. An overall rejected outcome alongside one route's non-match and another's exclusion retains those distinct meanings; it is not proof of all-route exclusion.
9. Inspection SHALL distinguish available evidence, absent evidence and a failed read. It may assert expired, never recorded, or withheld only when that cause is known. Otherwise it states only unavailable. Under the user-approved BR-015 AC13 boundary, legacy generic-only exclusion evidence remains explicitly incomplete: list/detail display “rule unavailable” and preserve the supported skip and overall outcome. It is not backfilled from current or snapshot rules, metadata or reevaluation, even when a single candidate seems plausible. This acceptance applies to reuse of that old decision, not to any newly evaluated exclusion, even for the same video. Partial evidence remains inspectable with its limitations rather than becoming a fabricated complete explanation.
10. Display and evidence SHALL respect the existing privacy/expiry and safe-diagnostic boundaries. Retaining a provider value inside an audit, exclusion explanation or configuration snapshot does not exempt that value from applicable policy. Only relevant user-configured routing values that are permitted for inspection belong in the explanation; OAuth secrets, authorization material, raw provider/request bodies and arbitrary error chains never do. Configured predicates are domain evidence, not raw failure diagnostics; diagnostic restrictions must not replace every safe predicate with a generic error sentence. Unsafe values are withheld with explicit unavailable context, not copied into another surface. No full metadata/configuration dump is required.
11. Backtest execution and its inspection SHALL NOT call YouTube to repair missing context/evidence. Inspection retry only rereads local retained information. A newer provider response would not recover historical evaluated input in any event. This contract introduces no external-refresh control for any inspection mode.
12. Simulation evidence SHALL remain explicitly hypothetical in list and detail. A recorded simulated action is not attempted, not an insertion or proof of what production would successfully do. A route excluded before condition evaluation explains the absence of that route's action, not an intended playlist target fabricated from current configuration. Missing action evidence alone proves neither success, failure nor a particular intended target.

## Semantic inputs and outputs

- **Inputs:** requested run/video identity and mode; captured route/condition/exclusion/action evidence; the run's immutable configuration context; separately attributable, permitted local display metadata; evidence/read availability.
- **Outputs:** recognizable context where supported; run-specific outcome and causal path; specific predicate and comparison evidence where captured; explicit provenance and completeness limits; safe read recovery. These meanings do not prescribe a wire format or storage model.

## Failure semantics

- A terminated failed inspection read SHALL end loading with safe failure feedback and a retry path. A conclusive not-found SHALL be distinguishable from read failure and loading. Both retain a way back to the specified run. A read failure says nothing about evaluation success/failure.
- If only display-context loading fails, already available decision evidence remains usable and the context failure stays explicit. This is a semantic partial-failure rule, not a requirement for separate requests.
- Retry SHALL preserve requested run/video identity, make no new evaluation/mutation, and not substitute another run's evidence. A late response for a previously selected run/video SHALL NOT be presented as the current selection's explanation.
- Missing run mode SHALL NOT default to production language. Safe context recovery precedes any mode-dependent interpretation.

## Invariants

- Recorded evidence, display context and inference are not interchangeable.
- Absence of evidence is not a negative routing outcome, zero input, action execution or successful completion.
- A new exclusion decision is not complete causal-rule evidence unless its first causal occurrence remains attributable through durable history and inspection. Truthful degraded inspection is required when evidence fails, but is not acceptance of losing evidence for new decisions.
- Renaming, expiry, refresh, restart and inspection retry do not change the historical decision's meaning.
- The accepted generic-only legacy boundary in BR-015 AC13 permits explicitly incomplete old exclusion explanations; it does not make them reproducible. Outside that boundary, truthful unavailable copy does not waive BR-015 AC1–7 or satisfy missing reproducibility. It never excuses generic-only capture of a new exclusion.

## Verified by

Observe the composed producer → persisted history → inspection list/detail path, including restart. Shaped UI responses alone cannot prove capture or attribution.

1. Evaluate a video with a permitted title/channel/duration and a specific route exclusion. After restart, list/detail identify the same video and show the actual exclusion predicate, scope and compared evidence. Rename the route/change the rule and local title afterward: recorded cause/input stays unchanged; current recognition context is not mislabeled as that input.
2. Exercise channel-ID, video-ID, exact-title, word/phrase and duration exclusions; two matching exclusions need only identify the causal one used. A route excluded alongside a matched route retains distinct route causes and the correct shared outcome. Exercise partial AND success with overall non-match and disabled/final-route skips without invented condition failures.
3. Inspect legacy generic-only exclusion, absent audits/actions, known expired metadata, missing metadata, withheld unsafe text and unknown availability cause. Show each supported limit without inventing a rule/value/title/target. Do not claim reproduction from these incomplete records. A valid local display title may still help recognition without proving historical input.
4. Fail then recover detail/context reads; test not-found, direct navigation, unknown run mode and delayed responses after changing selection. Loading terminates appropriately; retry/back work; no other run/video is substituted. Stored run status/outcome remains unchanged.
5. Across Backtest execution and inspection/retry, observe zero YouTube calls and no change to production idempotency/statistics. Simulation list/detail stays hypothetical, and no missing action is called a successful insertion. Safe predicate text remains inspectable while credentials/provider-body sentinels and expired restricted values are absent from released context/evidence/diagnostics.
6. In production and each supported simulation mode, evaluate exclusions for channel identifier, video identifier, exact title, phrase/substring and minimum/maximum duration. Observe the actual first causal occurrence, route and immutable run configuration survive restart and appear in both list and detail, with the recorded match/comparison and permitted configured value. Equality at a strict duration bound is not explained as excluded by that bound; substring behavior is not called whole-word matching. New generic-only skips fail this case.
7. Supply two matching exclusions, including identical entries and different types. Observe the first actual causal occurrence rather than a type-priority guess or a later equal-value match. Edit/reorder/remove current rules and rename the route afterward: the recorded occurrence and comparison remain those of the original run. Exercise fully excluded and partially excluded inputs; each newly recorded exclusion skip must carry its own actual cause. Disabled/final-route skips must not gain exclusion evidence.
8. Inspect a recorded overall rejected video with route A condition non-match and route B exclusion skip. List/detail preserve that overall outcome and separately identify A's condition cause and B's causal rule. Repeat with another route matching: B's skip never becomes whole-video exclusion. In simulation all these decisions remain hypothetical, not external actions.
9. Inspect a legacy generic-only record such as the reported Run15 shape, even when only one current/snapshot rule seems plausible. Both list and detail display “rule unavailable”, preserve the supported skip and overall outcome, identify the explanation as incomplete, and leave history unchanged. This passes the user-approved legacy boundary, not complete-reproduction verification. Inspect a valid reference with missing/unresolvable definition or unsupported interpretation separately from a failed read; the legacy exception does not excuse losing a new captured rule. Inspect a valid identity whose configured value is withheld and whose evaluated input expired: retain the supported identity/reason, label each unavailable part only as specifically as evidence permits, and do not claim complete reproduction. This grants no retention exception.
10. Interrupt/fail causal-evidence persistence or race reuse of a prior decision. No successful newly evaluated exclusion may expose a generic-only or mismatched contender's cause. A retry/restart observes the persisted decision unchanged, including unchanged legacy absence. Separately evaluate the same video in a new decision: it must capture the actual first causal rule, comparison and permitted configured value under cases 6–7; old incomplete history is no exemption. On inspection read failure, show safe terminal failure/retry rather than “no exclusion”; missing evidence is not read failure. Test separate permitted historical input versus changed current title: only captured attributable input may be labeled evaluated input.

## Reconciliation and unresolved boundary

- **Aligned:** accepted diagnostic [ARD-001](../../architecture/run-outcome-diagnostics/design/ard-001-durable-run-diagnostics-and-input-visibility.md) preserves requested-run evidence, safe diagnostics, simulation labels and no live reconstruction. OC-005 clarifies what its “existing route decisions and audits” must mean, not a new architecture.
- **Missing coverage, not new authority:** source inspected 2026-11-06 shows list/detail projections omit title/channel name/duration (`internal/server/run_handlers.go`); exclusions retain generic skip only (`internal/router/engine.go`); detail missing/failing reads lack terminal handling (`web/src/views/DecisionDetailView.tsx`). `metadata.Manager.GetDisplayMetadata` is a local active/unexpired lookup, not historical run input. These observations and the [designer's proposed refinement](../../ephemeral-reports/designer/backtest-decision-comprehension/implemented-experience-validation.md) do not choose a schema or authorize retroactive facts. No live Run15 response or screenshot was independently inspected here.
- **Conflict, still blocking complete reproduction outside the accepted legacy boundary:** accepted [system architecture](../../architecture/yuhaul-system-architecture.md) INV-5/Two-Store lifecycle and §Evidence display do not establish how historical evaluated values remain reproducible after expiry. Fingerprints/current refresh cannot reconstruct arbitrary title/description comparisons. Existing BR-009 durable-title obligations also remain unreconciled. Only BR-015 AC13's generic-only legacy exception is accepted here; no other reproduction obligation is weakened, no retention extension is accepted, and unavailable states do not establish reproduced input.
- **Owner/next decision:** compliance/research establishes the applicable provider permission and retention constraints; Architect chooses a permitted evidence realization and records its limitations. If no realization meets the accepted durable explanation/reproduction promise, the product owner must decide the precise bounded-history/scope amendment. That user decision is contingent, not permission to bypass policy. Safe local context, explicit absence, read recovery and truthful existing evidence can proceed meanwhile. API shape, capture mechanics, batching and migrations are technical choices; date meaning and Run15 SQLite contention are separate tasks.
- **2026-11-07 reconciliation:** the accepted [causal-exclusion ADR](../../architecture/decision-evidence/decisions/adr-001-capture-causal-exclusion-snapshot-reference.md) aligns with first-causal occurrence, unchanged run configuration, no legacy backfill and safe reference-only explanation. Its persistence/API realization remains architecture, not a new source of weaker product meaning. The subsequent explicit user answer settles acceptance of incomplete generic-only legacy history under BR-015 AC13. Architecture statements that this choice is still open are stale and require Architect-owned maintenance. New raw compared-input capture remains blocked on retention authority; the independent causal-rule reference need not wait. The user's “always” still requires actual cause capture for every new exclusion, not permission to archive restricted input. Full historical reproduction outside the accepted legacy boundary and BR-009 durable-title preservation remain unresolved, not satisfied by branch identity.
