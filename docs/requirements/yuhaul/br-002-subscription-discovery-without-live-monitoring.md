**Status:** accepted
**Priority:** MUST

## Statement

The system SHALL discover newly published videos from the user's subscribed YouTube channels by polling the YouTube Data API at intervals, without maintaining continuous or real-time monitoring connections.

## Acceptance criteria

1. On each run, the system enumerates the user's subscribed channels and queries for videos published since the last known state for each channel.
2. The system does not maintain persistent WebSocket, Server-Sent Events, or equivalent real-time push connections to YouTube.
3. Newly discovered videos are queued for route evaluation and are not lost if a run is interrupted before evaluation completes.
4. The system handles YouTube API pagination correctly when a channel's publication volume exceeds a single API response.
5. Channel subscription list is refreshed from the YouTube API at a user-configurable interval; stale channel data is not silently used beyond its freshness window.
6. The system tolerates partial channel enumeration failures: channels that fail are skipped in the current run and retried in the next run without losing already-discovered videos from successful channels.
7. For an uploads scan failure confined to one channel, continue scanning other eligible channels subject to existing run-wide limits. Preserve successful channels' discoveries for downstream processing, and report partial discovery coverage on Run Detail when some attempted channels were scanned successfully and others failed. Poll the failed channel on the next eligible fresh discovery run without requiring manual intervention. Do not treat a failed scan as covered or advance its last-known state past observations that the system has not durably saved. For permanent uploads-source failures, see the failure semantics in [OC-001](oc-001-youtube-api-quota-and-failure-semantics.md).
8. If the run attempted to scan at least one channel's uploads and none of the attempted channels could be scanned successfully because of source-local failures, end the run in terminal `failed` under the existing run lifecycle. Run Detail shows **Failed** and explicitly reports that no channels were scanned successfully, not that no new uploads were found. A successful scan that finds zero new uploads, a run that attempted no channels, a genuine resumable interruption, and a run-wide failure or deferral (such as an authorization or quota stop) do not meet this condition. This criterion does not change their existing handling. A failed run is not resumed to satisfy AC7.
9. Preserve actual upload observations from successful pages even if a later page fails locally. In a mixed run with at least one successfully scanned channel, skipping further scanning of the failed channel under AC6 does not skip its already-saved videos: route those from its earlier successful pages in the same run when otherwise eligible, under normal readiness, routing and send safeguards. A successful channel scan counts toward this condition even if it returns no new uploads. The failed channel's coverage remains incomplete and the next eligible poll still follows AC7. If AC8 applies, keep the observations available for later eligible work; the failed run does not route them. This criterion does not change run-wide failure or interruption handling.
10. If a run resumes discovery after a restart with a saved page, its only source is confirmed ineligible for polling (for example, the user unsubscribed), and the run has no completed scan, source-local scan failure, or run-wide stop, end it as terminal `completed` only after handing off its saved upload observations durably for a later eligible run. Run Detail shows **Completed** with explicitly incomplete discovery coverage. The recovering run does not route these observations or issue playlist actions for them, poll the ineligible source's uploads, advance that source's recorded coverage, or record a source or video failure because of the eligibility change. Losing source eligibility does not cancel saved work; normal processing safeguards still apply in the later run. This case does not change AC7–9 or existing run-wide failure or interruption handling. AC11 covers a run with more than one source.
11. **Multi-source recovery with a now-ineligible source.** *(Added 2026-11-22 by user decision.)* If a run resumes discovery after a restart with more than one source, and a source saved at least one page without completing its scan or recording a source-local failure and is now confirmed ineligible for polling, treat that source exactly as in AC10. The run hands its saved upload observations off durably for a later eligible run, and never routes them or issues playlist actions for them. It does not poll that source's uploads, advance its recorded coverage, or record a source or video failure because of the eligibility change. Such a source counts as neither a completed scan nor a source-local failure. The run's outcome is decided by its other sources, or by this rule when there are none:
    - **At least one source completed its scan:** the run ends terminal `completed`. Run Detail shows **Completed** with explicitly incomplete discovery coverage. AC9 still applies to saved pages of any source that failed locally.
    - **No source completed its scan and at least one failed locally:** the run ends terminal `failed` under AC8. Run Detail shows **Failed** and reports that no channels were scanned successfully. The failed run routes none of its saved observations.
    - **Every source is in this ineligible-after-page state:** the run ends terminal `completed`, with explicitly incomplete discovery coverage, as in AC10.

    In every case, the ineligible sources' observations are handed off durably before the run's terminal outcome is saved. A run-wide stop, failure or genuine resumable interruption keeps its existing handling and is not replaced by this criterion.

Verify durable discoveries and same-run route evidence for eligible saved videos from both channels, normal safeguards for ineligible work, and partial discovery on Run Detail after restart. Repeat with the successfully scanned channel yielding no new uploads. In the next eligible fresh discovery run, verify that the previously failed channel is polled and uploads not saved before the failure can still be discovered.

A later eligible run can process S's saved observations without polling S.
