**Status:** accepted
**Priority:** MUST

## Statement

The system SHALL allow the user to manually initiate a processing run at any time through the administration interface, independent of the configured schedule.

## Acceptance criteria

1. The user can trigger a manual run from the administration interface.
2. A manual run processes the same pipeline as a scheduled run (discovery, evaluation, action execution).
3. Manual runs are recorded in the run history with a manual trigger indicator.
4. The user can inspect the outcome of a manual run.
5. A manual run does not interfere with or reset the configured schedule.
6. The system prevents concurrent runs (manual and scheduled) from executing simultaneously.

### Resuming a manual run stopped by its time limit

A manual run that hits its execution time limit stops as `interrupted` with its work saved. For example, Run Now starts run 30, which stops after its time limit during action execution. The next Run Now press continues run 30 from that checkpoint under its original rules. It does not start run 31.

**Definition.** A *time-limit-interrupted manual run* has all of these properties:

- it was started by Run Now (manual trigger);
- its saved status is `interrupted`;
- its saved interruption reason is that its execution time limit expired;
- it was created with the current guarded mutation-safety and action-authority versions, not version 0 or another legacy version.

7. When the user presses Run Now and at least one time-limit-interrupted manual run exists, the system SHALL resume the **oldest** one instead of starting a new run. Oldest means the earliest saved start time; ties go to the lowest run identifier. The press SHALL NOT create a run or capture a configuration snapshot.
8. Each accepted press SHALL resume exactly one run. If several time-limit-interrupted manual runs exist, the others stay `interrupted` and unchanged, and each later press resumes the next oldest. Run Now starts a new run, as before, only when no time-limit-interrupted manual run remains.
9. The resumed run SHALL keep its run identifier, its original configuration snapshot and its saved progress, and SHALL continue from its saved checkpoint. It SHALL NOT repeat a playlist addition already recorded as successful. It SHALL NOT send a playlist addition to a target that is blocked by a retained send guard: an earlier attempt whose outcome is unknown stays blocked and unresolved, as required by [BR-012](br-012-idempotent-playlist-actions.md) and [OC-006](oc-006-refresh-authorization-and-call-safety.md). Resuming does not reconstruct, release or bypass a guard. If the time limit stops the resumed run again, it becomes eligible again with all committed progress kept.
10. Run Now SHALL NOT resume, change or act on any other run, including: version-0 or other legacy runs; runs interrupted for another reason, such as shutdown or process loss; runs stopped by the user ([BR-035](br-035-stop-active-run.md)); scheduled runs; queue-retry receiving runs; `failed` or `completed` runs; and dry-run, replay or backtest runs. These keep their existing recovery behavior. Startup recovery is unchanged, with one exception: the startup rule for an unusable time-limit-interrupted manual run in AC11.
11. If the oldest run that meets the definition cannot be continued safely because its configuration snapshot is missing or unreadable, or its saved checkpoint is not recognized, the press SHALL NOT resume it and SHALL NOT start a new run instead. It SHALL report a safe reason that identifies the run, and it SHALL make no YouTube call. The run stays `interrupted` and unchanged until the user discards it (AC13–21).
    - **Which conditions count.** Every condition that makes such a run unsafe to continue counts as one of the three causes above. This includes a snapshot that exists but is not admissible, which counts as unreadable, and saved state that contradicts itself, such as a completion time on an `interrupted` run, which counts as checkpoint not recognized. The full assignment of conditions to causes is the one in [run-initiation ADR-003](../../architecture/run-initiation/decisions/adr-003-discard-unusable-time-limit-run.md), Decision 2. Every press refused under this AC therefore names a run that the user can discard (AC13).
    - **At process start.** When startup recovery finds a time-limit-interrupted manual run, oldest or not, that cannot be continued safely for one of these causes, it SHALL NOT resume, change or discard that run. The run SHALL NOT stop the process from starting or from serving. Startup recovery SHALL record a log entry that identifies the run and its cause, with no raw error text, database text, credential or provider payload. It SHALL then finish as it would without that run: other recoverable runs are recovered, and the administration interface, Run Now, the schedule and queue retries become available as usual. The run then behaves as in-process: a Run Now press is refused for it under this AC while it is the oldest, and the user can discard it (AC13–21). Any other invalid saved state that startup recovery finds still blocks startup, as before ([BR-011](br-011-processing-state-persistence.md) AC7).
12. The acknowledgement of a resuming press SHALL identify the resumed run and say that it is a resumption, not a new run. [BR-033](br-033-honest-manual-run-progress.md) progress follows that run. Existing refusals still apply first: concurrent production (AC6), startup recovery in progress and shutdown in progress. A refused press resumes nothing and changes no run. Resuming does not change or reset the schedule (AC5).

### Discarding a manual run that cannot be resumed

Without this, a run that AC11 refuses would block Run Now for good. For example, run 30 stopped at its time limit and its configuration snapshot is now missing, so every Run Now press is refused for run 30. The user opens run 30, chooses Discard and confirms. Run 30 becomes `failed`, with a reason saying that the user discarded it because its snapshot was unavailable. Its 12 unfinished videos get pending items in the deferred queue, and no YouTube call is made. The next new run, Run Now or scheduled, continues those 12 videos automatically. The next Run Now press resumes the next eligible run, or starts a new run if none is left.

**Definition.** The *discardable run* is the run that a Run Now press would refuse under AC11 at that moment. It is the oldest time-limit-interrupted manual run (AC7 order), and only while it cannot be continued safely for one of the AC11 causes. At most one run is discardable at any time.

13. **Who and which run.** The user SHALL be able to discard the discardable run through the administration interface, with the same access that allows Run Now. The system SHALL refuse to discard any other run (AC20). This includes a time-limit-interrupted manual run that can be resumed, a younger time-limit-interrupted manual run even if it is also unusable, and every run listed in AC10. The system SHALL check eligibility again when it carries out the discard, not only when it shows the control or asks for confirmation. Only the user discards: Run Now, the schedule, startup recovery, shutdown and queue retries SHALL NOT discard a run.
14. **Confirmation.** A discard SHALL take effect only after the user explicitly confirms it for a named run. Before the user confirms, the interface SHALL say which run will be discarded, that it will be marked failed and never resumed, that its unfinished videos will go to the deferred queue for the next run, and that discarding sends nothing to YouTube. Cancelling or leaving the confirmation SHALL change nothing. A confirmed discard applies only to the run named in it.
15. **Result.** A successful discard SHALL save all of these together, or none of them: the run's status becomes `failed`; the discard reason (AC16) is recorded; and its unfinished work is retained (AC17). If they cannot all be saved, the run SHALL stay `interrupted` and unchanged, and the user SHALL be told that the discard did not take effect. The run keeps its identifier, trigger, start time, saved phase, committed per-video outcomes and action evidence. A successful discard's acknowledgement SHALL identify the run and say that it is now failed and that its unfinished videos are in the deferred queue for the next run. When the user cannot tell whether a discard took effect, for example because the connection dropped, the run's saved state SHALL show one of the two outcomes above and never a mixture.
16. **Safe reason.** The saved reason SHALL say that the user discarded the run and SHALL name the AC11 cause that made it unusable: configuration snapshot missing or unreadable, or saved checkpoint not recognized. It SHALL contain no raw error text, database text, credential or provider payload. Run history and run inspection ([BR-028](br-028-historical-run-inspection.md)) SHALL show this reason, so a discarded run can be told apart from a run that failed by itself.
17. **Unfinished work goes to the deferred queue (amended 2026-11-10).** An *unfinished video* is a video in the run's candidate set that is not completed and has no committed final outcome for this run. The discard SHALL hand every unfinished video to the deferred queue exactly as a stop does under [BR-035](br-035-stop-active-run.md) AC10–16, with the discard reason in place of the stop reason:
    - each unfinished video has exactly one pending deferred item, eligible at once; an existing pending or claimed deferred item for it is reused, keeping its identity, origin, reason and history;
    - an Errors-queue entry that the run had claimed for the video is no longer active, and its history is kept;
    - an item the user removed stays removed;
    - no queue item stays claimed by the discarded run;
    - the next new production run, manual or scheduled, claims and processes these videos although discovery does not report them as new, and the discarded run never makes a later run start fail.

    Videos with a committed outcome are not queued again. After the discard, every retained item can also be retried or removed as described in [BR-014](br-014-failed-work-retention-and-retry.md). This replaces the earlier rule that sent unfinished videos to the Errors queue under [authorization ADR-006](../../architecture/youtube-authorization/decisions/adr-006-per-video-action-failure-isolation-and-stranded-work-retention.md) §3.
18. **No YouTube call; guards stay.** A discard SHALL make no YouTube call. It SHALL NOT create, release, change or bypass any send guard. It SHALL NOT add, remove or change action evidence, and SHALL NOT mark any action as successful or as not applied. A later retry of a retained item is blocked by any retained guard, as [BR-012](br-012-idempotent-playlist-actions.md) and [OC-006](oc-006-refresh-authorization-and-call-safety.md) require.
19. **An uncertain playlist addition stays visible.** If the discarded run has an action whose outcome is uncertain, then after the discard that action SHALL still be shown as uncertain in run inspection, its send guard SHALL still block that target, and its video SHALL still have an active queue entry, either one it already had or one the discard created, unless the user removed that entry. The discard SHALL NOT resolve, hide or reclassify the uncertainty.
20. **Refusals.** The system SHALL refuse a discard, change nothing and make no YouTube call when any of these applies: the run does not exist; the run is already `failed` or `completed`, including a run already discarded; the run is not the discardable run; a production run is active (AC6); startup recovery is in progress; or shutdown is in progress. The refusal SHALL identify the run and give a safe reason that says which of these applies. A repeated or double-submitted discard of the same run SHALL leave exactly the result of one discard.
21. **Never replayed; Run Now proceeds; concurrency.**
    - A discarded run SHALL never run again. Run Now, startup recovery, the schedule and queue retries SHALL NOT resume, restart or continue it. Its retained work is processed only by later runs or queue retries, under their own send guards.
    - A discard SHALL NOT start or resume a run itself, and SHALL NOT change or reset the schedule. On the next Run Now press, AC7–12 apply to the remaining runs: the next oldest time-limit-interrupted manual run is resumed, or refused under AC11 if it is also unusable, in which case it becomes the discardable run. A new run starts only when no time-limit-interrupted manual run remains.
    - A discard and any production run start, including a Run Now press, SHALL behave as if one of them happened completely before the other. A press made at the same time as a discard either is refused for the run under AC11 or proceeds after the discard as stated above. It never resumes the run being discarded. A run that starts first causes the discard to be refused. Of two discards of the same run made at the same time, at most one succeeds; the other is refused because the run has already ended.
22. **Inspection shows whether a run can be discarded.** When the user inspects a run ([BR-028](br-028-historical-run-inspection.md)), the system SHALL say whether that run is the discardable run at the time of reading, so the interface can offer the discard control on that run's own view and not only after a refused Run Now press. Exactly one run, or none, is shown as discardable at a time. This indication is advisory: the recheck in AC13 still decides when the discard is carried out, and a stale indication never makes another run discardable.

## Verified by

- Unit test: manual run triggers full pipeline.
- Unit test: manual run recorded in history with manual indicator.
- Concurrency test: concurrent run attempt is prevented or queued.
- Time-limit resume (AC7–9): through the registered Run Now path with real SQLite and a controlled provider, let a manual run's time limit expire mid-run. The next press returns the same run ID, creates no run and no snapshot, resumes from the saved checkpoint and uses the original rules despite later rule edits. Seed a target with a retained send guard and one with a recorded success: zero further additions are sent to either.
- Several candidates (AC8): create three time-limit-interrupted manual runs, two with the same start time. Successive presses resume them oldest first, with the lower ID first on the tie, one per press. A new run is created only by the press after the last one finishes.
- Exclusions (AC10): seed version-0, legacy, shutdown-interrupted, scheduled, queue-retry, `failed`, `completed` and simulation runs. A press changes none of them; with no eligible run it starts a new run as before.
- Unusable candidate (AC11): a missing snapshot or an unrecognized checkpoint on the oldest candidate yields a safe reported refusal, no new run, no YouTube call and an unchanged row. Repeat for each of the five unusable conditions: each refusal names a run that can then be discarded, with the cause from the ADR-003 assignment.
- Startup with an unusable run (AC11, AC10): through the real startup path with real SQLite, seed an unusable time-limit-interrupted manual run (oldest and, separately, younger), a recoverable run and a usable time-limit run, then start the process. It starts and serves; the unusable run's row is byte-for-byte unchanged; the log names the run and cause and contains no raw error or database text; the recoverable runs are recovered and the schedule starts. Run Now is then refused under AC11 for the oldest unusable run, and a discard of it succeeds. Seed any other invalid saved state instead, such as a corrupt scheduled run: startup still blocks, as before.
- Discardability on inspection (AC22): with the seeds above, inspecting the discardable run shows it as discardable, and inspecting every other run, including a younger unusable one, shows it as not discardable. After a discard, or after an older time-limit run appears, the indication changes on the next read.
- Acknowledgement and refusals (AC12): the acknowledgement names the resumed run as a resumption; a press during an active run, startup recovery or shutdown is refused and resumes nothing; the next scheduled time is unchanged.
- Discard eligibility (AC13, AC20): with real SQLite, seed an unusable oldest candidate, a usable candidate, a younger unusable candidate and each AC10 run kind. Only the unusable oldest candidate can be discarded. Every other discard request is refused with its safe reason, and its run row, queue rows and guards stay byte-for-byte unchanged. Make the candidate usable or remove it between showing the control and confirming: the discard is refused.
- Confirmation (AC14): through the administration interface, cancelling the confirmation leaves every row unchanged. The confirmation names the run and states the four facts.
- Discard result and atomicity (AC15–17): discard a candidate that has accepted, failed, unfinished and retry-claimed videos. Afterwards the run is `failed` with a safe reason naming the cause. Each unfinished video has exactly one pending deferred item that is eligible now, and none is in the Errors queue because of the discard. The retry-claimed deferred item is pending again with its original identity and history. A claimed Errors-queue entry is no longer active, with its history kept. A removed item stays removed. No queue item is still claimed by the run. Then start a new scheduled run, and separately a new Run Now run, whose discovery returns none of these videos: the run start succeeds and the run claims and processes every one of them (BR-035 AC14–15). Committed outcomes and action evidence are unchanged. Inject a failure into the save: the run is `interrupted` and every row is unchanged.
- Guards and uncertainty (AC18–19): a controlled provider records zero calls during the discard. A seeded uncertain action still shows as uncertain, its guard row is unchanged, and a retry of its entry sends zero additions.
- No replay and Run Now proceeds (AC21): after a discard, restart the process and press Run Now. The discarded run is not resumed. The next oldest candidate is resumed or refused, or a new run starts when none remains. The next scheduled time is unchanged.
- Concurrency and repeats (AC20–21): a discard during an active run, startup recovery or shutdown is refused and changes nothing. Race a discard with a Run Now press, and two discards with each other: the result always matches one serial order, and at most one discard succeeds. A double submit yields one discard and one set of queue entries.
