# YuHaul — Behavioral Requirements & Obligation Contracts

**Status:** accepted

A new video matching an earlier one still goes through eligible routes and playlist actions. For example, a different upload of the same song may be flagged as a duplicate and added to a matching playlist, while its pairwise provenance is retained. A duplicate match does not override exclusions, conditions, final routes, completed-action idempotency, or operational failures. The user's 2026-10-25 “Continue, yes” settles this policy; it does not create a selectable skip mode. [BR-008 AC9–AC11](br-008-exact-and-fuzzy-duplicate-detection.md) specifies continuation and compatibility with the retired setting. No user-owned choice remains for this bounded amendment; native-reference eligibility and fully excluded-video evidence are separate questions below.

For the user's own operational analytics, old activity should keep contributing rather than aging out. For example, 10 action executions followed by 2 later executions remain 12 in the lifetime count, while both periods are still available. [BR-023](br-023-historical-statistics-over-time.md) records the user's 2026-10-25 no-expiration preference. It does not authorize indefinite YouTube metadata, playlist-membership, or provider-derived metric retention; any required permission and a conflicting metric's product treatment remain separate decisions.

## Reconciled Interfaces

- **Duplicate handling — fixed continuation with compatibility:** The user's “Continue, yes” settles BR-008 AC9. BR-010 provenance and OC-002 outcome semantics still apply, including for OC-004 imported matches. The accepted Admin Interface Design's threshold tuning and provenance inspection are aligned and do not promise a handling selector. Legacy `duplicate-detection.md` AC6's configurable-handling promise is explicitly superseded only for that clause. Source inspection found settings/threshold responses, settings writes, configuration snapshots/history/restores, and proposal inputs carrying `duplicate_behavior`; the service defaults it to `skip` and accepts arbitrary strings, while the pipeline run detector reads only threshold. Current Settings renders threshold, not a behavior selector. Production records matches without removing videos from later routing, and dry-run continues simulation; these are source observations, not new implementation verification. **Conflict:** `internal/pipeline/replay.go`, `evaluateHistoricalVideo`, returns on a match before routing, so replay/backtest do not conform to the new continuation obligation. Active `skip` readback/effective-setting descriptions also conflict. BR-008 AC10–AC11 specify retiring the choice without breaking existing configuration/proposal use or rewriting immutable history. Architect owns exact compatibility representation/realization and reconciliation of the system architecture's stale open-policy/rationale notes and historical-mode early return; Designer owns any explanatory presentation. An attempted architecture-document status reconciliation was denied by edit permissions, so those downstream notes remain unchanged. Neither owner needs another user decision to introduce or choose skip, which is not authorized. No API/schema/code is changed here.
- The accepted [ADR-007](../../architecture/adr-007-canonical-route-action-type-api-boundary.md) and [ARS-001](../../architecture/ars-001-route-and-playlist-api-contracts.md) settle the action-type naming seam: public API representations use `add_to_playlist`; internal persistence/execution may retain `playlist_insert`. BR-004 remains phrased in user-visible action semantics and does not prescribe either serialized value.
- BR-032 AC5 is approved as part of the obligation baseline and is also represented in the accepted [Admin Interface Design](../../design/yuhaul-admin-ui-design.md), §View: Run Detail, as filtering the video's outcomes by type. This is distinct from the Run List's date, run-type, and status filters; those filters alone do not satisfy AC5.
- **BR-009 / corpus import:** Anchor AC9 requires durable preservation/import of the existing corpus, not a particular preview, progress display, or export. The user's direct-SQLite/no-export decision is recorded in the accepted [Corpus Import amendment](../../design/amendment-corpus-import-sqlite-reconciliation.md), which amends SC-004; accepted [ARS-002](../../architecture/ars-002-web-corpus-import-api.md) specifies direct SQLite input and append accounting. Title and video identifier are required source data; channel identifier is optional. The accepted [ADR-009](../../architecture/adr-009-web-corpus-import-job-lifecycle.md) and ARS-002 settle the web import lifecycle, cancellation/append semantics, upload cap, and same-process status recovery. The input has no video publication-date field. The user-approved BR-009 clarification defines corpus recency separately as the completion timestamp of the latest successful import; it does not fabricate or infer publication dates and is not an Anchor AC9 obligation. Accepted [ADR-015](../../architecture/adr-015-durable-corpus-import-completion-timestamp.md) and ARS-002 provide durable recency independently of process-local job status; the [Settings recency amendment](../../design/amendment-settings-corpus-import-recency-display.md) specifies its presentation. The older corpus-import amendment still calls ARS-002 proposed and recency unresolved and retains obsolete API/access-boundary questions; Designer-owned maintenance does not reopen the accepted contracts or satisfy outstanding deployment verification.
- **Duplicate-reference eligibility and import provenance:** BR-009 AC4 and BR-008 AC5 require valid newly added imported records to remain eligible historical references; OC-004 defines the shared import/native-observation/detection/provenance semantics. A same-ID native observation does not revoke eligibility, but BR-008 AC8 and OC-004 require that the observation not match the imported record as its own duplicate. Same-video-ID import retries do not change the existing entry. Eligibility is not route completion or discovery-credit evidence; under BR-010 AC6 and OC-004 Guarantee 3, an imported `channel_id` remains an association only. This reconciliation is closed across requirements and accepted architecture: [ADR-013](../../architecture/adr-013-monotonic-duplicate-reference-eligibility.md), [ADR-014](../../architecture/adr-014-discovery-credit-requires-native-earliest-evidence.md), [ADR-009](../../architecture/adr-009-web-corpus-import-job-lifecycle.md), [ARS-002](../../architecture/ars-002-web-corpus-import-api.md), and the [system architecture](../../architecture/yuhaul-system-architecture.md) all preserve same-ID eligibility while excluding self-matches and deny discovery credit absent independent evidence. Existing implementation/test reports in the bundle log and ARS-002 are evidence only, not Product Acceptance; this reconciliation does not independently verify implementation.
- **Route identity:** The user's decision that stable route identifiers distinguish routes and display names may repeat is reconciled with the accepted [Route Identity design amendment](../../design/amendment-route-uuid-identity-duplicate-names.md), [ADR-011](../../architecture/adr-011-stable-uuid-route-identifiers.md), [ARS-001](../../architecture/ars-001-route-and-playlist-api-contracts.md), and [ARS-004](../../architecture/ars-004-route-uuid-schema-api-migration.md). BR-003 remains implementation-independent; UUIDs and short-label disambiguation are accepted design/architecture realizations, not additional BR wording. This closes the documented design/architecture conflict but does not claim UI conformance verification.

## Open Questions

- Every Anchor AC has a requirement in the canonical baseline above. BR-009 AC6 recency meaning and BR-010 pairwise provenance scope are resolved by user approval. Current accepted authority also settles import input/lifecycle, durable recency and its Settings presentation, route identity, and same-ID candidate eligibility. ADR-014's documentation reconciliation is closed; the older corpus-import design amendment still requires Designer-owned status maintenance. The remaining semantic questions are:
  - **Retention signals and policy — product authority, with Designer/Compliance/Architect reconciliation:** BR-022 requires a `MUST` only when reliable provider evidence permits measurement, but the accepted, separately maintained (and not listed in the canonical BR/OC tables above) [Retention/Value Signals](retention-signals.md) and [Retention-Signal Configuration](retention-signal-configuration.md) documents describe designated-playlist membership as a primary/unconditional signal. The owner must confirm whether playlist membership itself satisfies the evidence condition and which provider signals qualify. Separately, those requirements call retention data durable while the [proposed compliance analysis](../../architecture/yuhaul-youtube-compliance.md) treats provider data as subject to refresh/deletion and the accepted [system architecture](../../architecture/yuhaul-system-architecture.md) describes durable retention observations. A retention-policy amendment is needed before these claims can be reconciled; BR-022's priority correction does not extend the retention period or settle policy.
  - **Video-identifier syntax — product/design authority:** BR-007 requires a specific-video exclusion to contain a non-empty identifier, but the [Anchor](../../anchors/youtube-discovery-routing.md) and accepted [Admin Interface Design](../../design/yuhaul-admin-ui-design.md) specify no syntax or normalization. No stricter validation is asserted until that meaning is supplied.
   - **Remaining legacy authority / fully excluded evidence — product owner:** Legacy AC6 is now superseded by fixed continuation. Its other corpus/identity conflicts remain unresolved; this amendment does not retire the entire document. Requiring duplicate/provenance evidence for fully excluded inputs would need a separate product decision reconciling BR-008 AC7. Neither question blocks continuation for detected distinct matches or retirement of the misleading selectable setting. Architect owns compatibility realization under BR-008 AC10–AC11; exact API representation is a technical decision, not another product-policy question.
  - **Native reference eligibility — product owner:** Should a native video become an eligible duplicate reference only after it has been routed to a playlist, or can any persisted historical discovery serve as a reference? The accepted architecture and legacy requirement use the routed-only rule; canonical BR-008 AC5/BR-009 imply a broader historical corpus but do not state this boundary precisely. This determines whether an earlier A must have been accepted before later B/C can match it.
  - **Ingress deployment verification — security/deployment owner:** Traefik BasicAuth/TLS is selected by accepted ADR-010/ARS-003, but the required cluster configuration, credentials, TLS, redirect, and all-path behavior remain undeployed/unverified. This blocks untrusted-network exposure only; it is not an unresolved requirement meaning or a claim that the local import contract is incomplete.
