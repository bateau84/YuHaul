# YuHaul — Behavioral Requirements & Obligation Contracts

**Status:** accepted

Scheduled and manual production work should continue when a YouTube access token expires and stored refresh authorization works. For example, the next run renews access and discovers subscriptions without reconnecting. [BR-034](br-034-automatic-youtube-token-refresh.md) and [OC-006](oc-006-refresh-authorization-and-call-safety.md) require encrypted durable renewal, truthful status/failure meaning, concurrent-caller safety and no blind retry of uncertain playlist mutations. Missing/rejected refresh authorization still needs reconnecting. No user-owned choice blocks this bounded change; design/architecture documentation is reconciled, while implementation and assembled-path verification remain outstanding. No live recovery, date policy or coordinator is authorized.

For every new exclusion, the user must see why it skipped a route and which rule caused it, in production and simulation list/detail. For example, route A can fail its conditions while route B skips because its first causal title exclusion matched; B's skip is not proof that every route excluded the video. [BR-015 AC10–13](br-015-explainable-route-decisions.md) and [OC-005](oc-005-decision-evidence-attribution-and-availability.md) require new decisions to identify the actual first causal occurrence from the run's unchanged configuration, with its comparison and **its configured value, which is always shown**: the user decided on 2026-11-10 that the matched rule's value is their own configuration and is release-eligible. A generic skip alone is not enough. **Legacy boundary:** asked whether old exclusion records may say “rule unavailable”, the user answered “Yes, that is ok” (2026-11-07). Existing generic-only history stays explicitly incomplete and displays “rule unavailable”; it is never guessed or reconstructed. **Historical inputs (user decision, 2026-11-10):** inspection explains decisions from app-owned evidence and does not reproduce past provider-input comparisons. Past inputs are shown as current/local information, labeled as such, or as “unavailable”; no historical provider snapshot is retained ([BR-015 AC7](br-015-explainable-route-decisions.md)). Backtest/inspection never calls YouTube to fill gaps. BR-009's durable-title question for duplicate detection is separate and still open.

After Overview → Run Now, the user should be able to follow the specific run rather than guess from quota consumption. For example, a run can truthfully show “running — discovery” while selected inputs are unknown and counters are zero; a later saved failed status replaces active feedback, not with a success message. [BR-033 — Honest Manual Run Progress](br-033-honest-manual-run-progress.md) fixes these bounded semantics. It requires neither a progress percentage nor new telemetry, scheduling, or provider guarantees. No user-owned decision blocks this feature; the separate date-selection and proposed coordinator work remain outside scope.

A new video matching an earlier one still goes through eligible routes and playlist actions. For example, a different upload of the same song may be flagged as a duplicate and added to a matching playlist, while its pairwise provenance is retained. A duplicate match does not override exclusions, conditions, final routes, completed-action idempotency, or operational failures. The user's 2026-10-25 “Continue, yes” settles this policy; it does not create a selectable skip mode. [BR-008 AC9–AC11](br-008-exact-and-fuzzy-duplicate-detection.md) specifies continuation and compatibility with the retired setting. No user-owned choice remains for this bounded amendment; native-reference eligibility and fully excluded-video evidence are separate questions below.

For the user's own operational analytics, old activity should keep contributing rather than aging out. For example, 10 action executions followed by 2 later executions remain 12 in the lifetime count, while both periods are still available. [BR-023](br-023-historical-statistics-over-time.md) records the user's 2026-10-25 no-expiration preference. It does not authorize indefinite YouTube metadata, playlist-membership, or provider-derived metric retention; any required permission and a conflicting metric's product treatment remain separate decisions.

**Run Now resumes a manual run stopped by its time limit (user decision, 2026-11-10).** For example, run 30 stops at its time limit; the next Run Now continues run 30 under its original rules instead of starting run 31. [BR-017 AC7–12](br-017-manual-run-initiation.md) fixes which run resumes (the oldest; ties go to the lowest ID), one per press, and the exclusions: version-0 and legacy runs, other interruptions, scheduled, queue-retry, terminal and simulation runs. Send guards and recorded successes still block repeated playlist additions.

**Discarding a run that Run Now cannot resume (user decision, 2026-11-10).** If the oldest such run cannot be resumed safely (for example, its snapshot is missing), Run Now refuses with `resume_unavailable` and would keep refusing. The user can now discard exactly that run, after a confirmation that names it. The run becomes `failed` with a safe reason, and its unfinished videos go to the deferred queue, so the next new run continues them automatically (amended 2026-11-10 to match Stop; they previously went to the Error Queue). The discard makes no YouTube call, releases no send guard, leaves uncertain additions visible as uncertain, and the run never runs again. The next Run Now press continues with the remaining runs. A discard is refused for any other run, for an already ended run, or while a run, startup recovery or shutdown is in progress. See [BR-017 AC13–21](br-017-manual-run-initiation.md).

**A damaged time-limit run no longer stops startup (user decision, 2026-11-10).** For example, run 30's snapshot is missing and the process restarts. YuHaul starts and serves as usual; run 30 stays `interrupted` and unchanged, and the log names it and its cause. The user opens run 30, which shows that it can be discarded, and discards it. Any other damaged saved state still blocks startup, as before. All five conditions that make such a run unusable can be discarded, using the cause assignment in [run-initiation ADR-003](../../architecture/run-initiation/decisions/adr-003-discard-unusable-time-limit-run.md). See [BR-017 AC10, AC11 and AC22](br-017-manual-run-initiation.md) and [BR-011 AC7](br-011-processing-state-persistence.md).

**Stopping an active run (user decision, 2026-11-10).** The user can stop any active run, manual, scheduled, queue retry or simulation, for any reason, after confirming. For example, the user stops scheduled run 41 while it adds videos. Run 41 makes no further YouTube request and ends as "stopped by user", not failed, and it is never resumed. A prepared but unsent playlist addition has its guard released. An addition already sent with no answer is shown as uncertain and is never resent. Each of its 9 unfinished videos gets one pending deferred item, and the next new run, Run Now or scheduled, claims and processes them, although discovery does not report them as new. The same handoff now applies to discard. This closes the gap that stranded run 14: a known video with no queue item is reachable by no run. See [BR-035](br-035-stop-active-run.md). Stopping a simulation simply ends it, with no queue effects (the user's suggestion, adopted).

**Marking a stuck legacy run as ended (user decision, 2026-11-11).** Old production runs created before guarded sending (mutation-safety version 0), such as run 14, can be stuck as `running` or `interrupted` forever, because Stop, Discard, Run Now resume and startup recovery all exclude them. The user can now mark such a run as ended, after a confirmation that names it and says its unfinished videos will not be processed. For example, run 14 becomes `failed` with the reason "ended by user (legacy run)"; its videos, queue items, guards, actions and decisions stay exactly as they were, and no YouTube call is made. Marking it as ended does not process its backlog; once it is ended, the user can re-queue its stranded videos (BR-037, below). The action is refused for version-1 runs, simulations, terminal runs, and while a production run is active, during startup recovery or during shutdown; a repeat changes nothing. Run reads report an `endable` fact so the interface shows the action only where it applies. See [BR-036](br-036-mark-legacy-run-as-ended.md).

**Re-queuing stranded videos (user decision, 2026-11-11).** Run 14 and the failed runs of 2026-11-06 saved videos and then failed. Discovery skips known videos and no queue holds them, so no run would ever process them. The user can now start a one-off "Re-queue stranded videos" action. A preview shows how many videos will be re-queued, and how many will not because they are blocked, removed by the user, or still owned by a run that has not ended. After the user confirms, each stranded video gets one pending deferred item, eligible at once, and normal runs process them, a day's quota at a time. A video whose playlist addition may already have been sent (an unresolved send guard, an uncertain addition or ambiguous legacy evidence) is never re-queued: it stays blocked by the existing send safety rules, and the action lists it. The action makes no YouTube call, is refused while a production run is active, during startup recovery and during shutdown, and repeating it changes nothing more. For run 14, the user first marks it as ended (BR-036), then re-queues. Re-queued videos whose metadata has expired are never committed as rejected for that reason. See [BR-037](br-037-requeue-stranded-videos.md). This supersedes the 2026-11-10 decision to leave run 14's backlog alone.

The user's further decisions of 2026-11-11 on BR-037:
- A re-queued video that YouTube no longer returns (deleted or private) ends with the final outcome **"unavailable on YouTube"**. It is not put in the Errors queue as failed. It stays visible in the run's details and outcome counts as its own category ([BR-032](br-032-processing-outcome-distinction.md) AC1 amended).
- While the backlog drains, it may use each day's whole quota, so new uploads wait. No quota is reserved.
- Errors-queue entries stay where they are, because only 2 are live and the user retries them manually. Videos the user removed stay out. The preview also counts committed deferred or failed videos that have no queue item.
- **Prerequisite:** the Deferred view and `GET /api/deferred` must show the queue a page at a time before the action is offered, because about 70,000 items would otherwise load at once.
- [BR-035](br-035-stop-active-run.md) AC14 is adjusted so that a run claims deferred work while it has quota and leaves the rest pending, oldest first, instead of claiming every item at once.
- **Claiming after a provider failure (critic F3):** variant K. A provider failure that is not a quota refusal does not stop a run from claiming, so BR-035 AC14 stays as amended. The user accepted the trade-off: after such a failure, a run can claim and release much of the backlog in one pass without processing it, and a stop hands it all back. This churn is local work only; the claims and releases themselves make no YouTube call, and nothing is lost.
- **Erased veto evidence (critic F4):** a production check found that the version-0 runs in action execution, runs 17 and 21, have 0 open retry rows. F4 does not apply, and the *blocked* definition is unchanged ([BR-037](br-037-requeue-stranded-videos.md), Derived from).

**Searching for a video by title or video ID (user request, 2026-11-11).** The user can open a new Videos page and find a video YuHaul knows. A video ID, or a pasted `watch?v=`, `youtu.be/` or `shorts/` link, opens that video directly, even long after its title has expired. Other text of 3 or more characters finds videos whose title is still held and contains the text, ignoring case, 50 per page, with the total number of matches. For example, `lofi beats` says 3 videos match and lists them; a 3-month-old video whose title has expired is not among them, but pasting its `youtu.be` link opens it with title "unavailable" and its full outcome and run history. The video view shows title and channel (labelled current/local), latest production outcome, queue state and every run that decided it, linked to its decision detail, with simulation runs labelled. **Most important limit:** YuHaul holds titles for only 30 days without refresh, and the corpus keeps only fingerprints, which are never shown or searched as titles. So name search covers only videos whose titles are still held, and the page says so. Search makes no YouTube call, changes nothing and keeps no title longer. ID lookup answers within 1 second and each name-search page within 2 seconds at the 95th percentile with 150,000 known videos that all hold a title ([QS-001](qs-001-video-search-response-time.md)). See [BR-038](br-038-video-search-by-title-or-id.md). The user may change the defaults; whether name search should also match fingerprints is an open, non-blocking question below.

The user's further decisions of 2026-11-11 on BR-038:
- A link pasted without `http://` or `https://` is not recognized, unchanged. It is searched as ordinary text.
- Name search shows the total number of matches (new BR-038 AC18).
- On mobile, Videos is reached through the "More" menu, as the admin interface design proposed. This confirms the design; it adds no acceptance criterion.
- QS-001's load is 150,000 held titles, instead of 50,000.


**A final outcome is never reprocessed or overwritten (user decision, 2026-11-12).** Only videos without a final outcome are ever routed again. Accepted, rejected, excluded and unavailable on YouTube are final; deferred, failed and not yet evaluated are not. For example, a rejected video whose stale deferred item is claimed by a run with new routes is not evaluated and stays rejected; an accepted video never becomes rejected, deferred or not yet evaluated ("this also goes the other way around"). A partly done video, such as one added to "Lofi" but deferred for "Study", is finished by adding it to "Study" only, under the decision that added it to "Lofi", whatever the routes say now; the "Lofi" success is never undone. Queue items of a final video are closed with their history kept. Dry runs and backtests may still evaluate final videos but change nothing. See [BR-039](br-039-final-outcomes-are-never-reprocessed.md); BR-032 AC7, BR-035 AC14, BR-037 AC11 and OC-002 Guarantee 8 now point to it. **Conflict with current source:** a deferred-queue claim resets the video's outcome to not yet evaluated and re-routes it under the receiving run's configuration (`internal/queue/retry.go`, near line 230).

**Deferred queue button renamed (user decision, 2026-11-10).** The deferred queue's “Discard” button is now called “Dismiss”, which its own confirmation already says. This keeps it apart from discarding a run. Only the label changes; the action is still the removal in [BR-014](br-014-failed-work-retention-and-retry.md) AC4. No requirement names that button, so the change is recorded here and in the [log](log.md), and the admin interface design must apply it.

**Backtest date range (user decision, 2026-11-10).** The Backtest date controls filter retained videos by YouTube **published** date: UTC days, both chosen days included, and no range means no filter. [BR-027 AC8–13](br-027-historical-backtesting.md) covers videos without a published date, reversed ranges, counts and the saved range. The assigning session proposed the UTC, inclusive and no-range defaults; the user did not object, and the assignment records them as accepted.

**Run 14 (user decision, 2026-11-10, superseded 2026-11-11):** left as it is; no recovery and no backfill. The [run 14 recovery proposal](../run14-recovery/index.md) stays declined. On 2026-11-11 the user approved re-queuing stranded videos ([BR-037](br-037-requeue-stranded-videos.md)), so run 14's backlog can now be processed by normal runs after run 14 is marked as ended.

**Discovery/processing coordinator — proposal, not accepted.** User direction of 2026-11-10: both jobs run automatically on separate schedules, and exhausting the quota is acceptable because work continues after the quota resets. This is recorded as direction for the [proposed coordinator](../../architecture/discovery-processing-coordinator/index.md). It does not amend BR-016, BR-017 AC2/AC6 or the quota requirements, and no requirement exists for it yet.
